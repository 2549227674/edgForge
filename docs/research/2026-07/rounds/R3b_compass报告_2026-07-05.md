## 模块 1 · RTX 6000D / RTX PRO 6000 96GB 卡与软件生态（最高优先级）

### SM 架构版本（两卡并答）
两张卡均为 GB202 派生的 **sm_120（compute capability 12.0）**，与消费级 RTX 5090 同物理硅片（GB202），仅配置/校验不同。
- **RTX PRO 6000 96GB（全球版，R-Max 默认）**：188 SM / 24,064 CUDA core / 96GB GDDR7 ECC / 512-bit / **官方 1.8 TB/s（NVIDIA Workstation Edition datasheet，2026，官方）**。
- **RTX 6000D 84GB（中国版，库存回退）**：156 SM / 19,968 CUDA core（较全版少 17%）/ 84GB GDDR7（28×3GB）/ 448-bit clamshell。

**带宽冲突（须修正 v3.2 决策）**：v3.2 文档记 6000D "~1.1TB/s"，但媒体一手推算为 **~1,568 GB/s（VideoCardz，28Gbps×448-bit 数学一致，2026-春，媒体推算）**，另 getdeploying 给 ~1,398 GB/s 估值。证据强度：NVIDIA 未发布 6000D 官方 datasheet，但 28Gbps×448bit 的算术自洽度高于文档的 1.1TB/s。**建议采用 ~1.5–1.57 TB/s**。96GB 卡 1.8TB/s 为官方值，可信度最高。

### SM120 vs SM100（B200/B300）kernel 兼容性
- SM120 与 SM100 **不向后兼容**：为 SM100 编译的 kernel 在 SM120 上失败（Pulsed Media wiki，2026，社区；"This breaks DeepSeek models in vLLM"）。
- **FP4/NVFP4 GEMM 路径**：vLLM issue **#31085**（github，2026，官方 issue）记录 SM120 未被 MXFP4 后端选择逻辑识别（代码只匹配 `is_device_capability_family(100)`），导致回退到 Marlin 而非原生 NVFP4 kernel，日志 "Your GPU does not have native support for FP4 computation…Weight-only FP4 compression will be used leveraging the Marlin kernel"。已有 commit（e502098 "Add NVFP4 MoE CUTLASS support for SM120"、c0dfc89 "SM120/NVFP4: add device guard and runtime SM dispatch"）为 SM120 补齐原生路径。
- **SM100 独有、SM120 缺失**：TMEM/部分 sparse-attn 路径与 B200/B300 的 SM100 家族绑定；FP4 tensor-core 指令在 SM120 上需专门 dispatch 才能走原生路径，否则退化。两卡此项行为**一致**（同为 sm_120）。

### PyTorch / vLLM / flash-attention 支持（2026-07）
- **PyTorch**：sm_120 需 nightly **cu128/cu129** 或更新；stable ≤2.4.1（仅到 sm_90）报 "NVIDIA RTX PRO 6000 Blackwell…is not compatible"（Medium/allenkuo，2026，社区）。推荐 Python 3.13 + cu129。
- **flash-attention**：issue **#1987**（Dao-AILab，2026，官方 issue）确认 sm_120 官方支持缺失（README 仅 Ampere/Ada/Hopper）；Unsloth 已在 Blackwell（sm_100+）**跳过 flash-attn 安装**（unsloth PR #5420）。
- **CUDA 版本（host ≤13.2 约束下）**：Unsloth 官方文档明确警告 **"Do NOT use CUDA 13.2 as you may get gibberish outputs. Use below CUDA 13.2 or CUDA 13.3"**（unsloth.ai/docs，2026，官方）；HF 讨论区实测 Qwen3.6-35B-A3B UD-IQ4_XS 在 CUDA 13.2 + llama.cpp 输出乱码。**结论：镜像锁 CUDA 13.0/13.1**（既满足 host ≤13.2，又规避 13.2 bug）。两卡一致。

### MIG 支持
- **RTX PRO 6000（96GB，全系 Workstation/Max-Q/Server）**：支持 **Universal MIG，最多 4 个隔离实例**，每实例独立显存/缓存/计算核（NVIDIA 官方 datasheet + MIG User Guide，2026，官方）。启用前提：DisplayModeSelector 切 compute 模式、vBIOS 达标、驱动 **580.95+ / CUDA 13.0+**、ReBAR 开启（Exxact 支持文档，2026，社区/OEM）。
- **RTX 6000D（84GB）MIG 状态**：**no reliable source found**（NVIDIA 无 6000D 官方规格页；6000D 为 Server Edition 功率限制版，MIG 理论上应保留但未见一手确认）。
- 96GB 单卡切 4×MIG 做"多租户并发模拟"有一手依据，可作为新并发主线实验槽；6000D 待实测。

### AutoDL 实例细节
- **passthrough / profiling 权限**：无 AutoDL 官方对 6000D/6000 的一手声明（**no reliable source found**）。通用原理：PCIe passthrough 下 ncu/nsys 通常可采集硬件计数器；**vGPU 虚拟化下 CUDA profiler 无法采集硬件计数器**（NVIDIA vGPU 文档 5.8 条 "CUDA profilers cannot gather hardware metrics on NVIDIA vGPU"，官方）。
- **vGPU-32/48 底层硅片**：AutoDL 无公开声明（**no reliable source found**）。须实机 `nvidia-smi -q` 自查，并预设 vGPU 层无法做精细 profiling。

### 对 PiLoop v3.2 的直接结论（≤10 条）
1. 两卡均 sm_120，Module 1/2 全部 kernel 结论可共用，差异仅带宽/显存/核数/MIG 确认度。
2. **修正 v3.2 带宽**：6000D ≈1.5–1.57 TB/s（非 1.1TB/s），96GB =1.8 TB/s（官方）。
3. NVFP4 原生 kernel 在 sm_120 需最新 vLLM（含 SM120 CUTLASS commit），否则回退 Marlin 掉速——务必验证 vLLM build 已带 SM120 dispatch。
4. 镜像固定 CUDA 13.0/13.1；**严禁 13.2**（乱码 bug + host 约束双重原因）。
5. flash-attn 在 sm_120 不可靠，训练/serving 应依赖 vLLM/Unsloth 自带 attention 后端而非 flash-attn。
6. MIG 多租户并发实验仅 96GB 卡有一手依据；6000D 待首次实测确认后再排期。
7. vGPU-32/48 层不做 ncu/nsys 硬件计数分析，仅用于 smoke-test/pipeline debug。

## 模块 2 · DSpark on Blackwell 单卡（R-Max 旗舰实验）

### vLLM 合并状态（子代理一手核实，2026-07-05 抓取）
存在**三 PR 链**，而非单一 PR：
| PR/issue | 内容 | 状态 |
|---|---|---|
| **#46995**（benchislett/NVIDIA，"[Spec Decode] DSpark"）| **核心实现**：引入 `method:"dspark"` 枚举、DSparkSpeculator、非因果 sparse-MLA attention、单 CUDA-graph capture | 即官方推文所指 "DSpark Core PR"；页面渲染为 Open（合并事件存疑，见下）|
| **#47093**（mgoin/Red Hat，speculators checkpoint 支持，stacked on #46995）| 解析 speculators 格式 checkpoint（d2t/t2d、DFlash 1+N block）| **已于 2026-07-02 合并入 main**（commit 2b753ad，101/107 检查通过，官方）|
| **issue #46910**（"Support DSpark for DeepSeek V4"）| 功能请求 | **仍 OPEN**（证实 report-1 说法正确；report-1 与 compass "已 natively merged" 均部分成立——核心代码已入 main，但功能追踪 issue 未关）|

- **最低可用版本**：**仅 vLLM nightly**（`uv pip install vllm --extra-index-url https://wheels.vllm.ai/nightly`，官方推文 + RedHatAI 卡一致）；最低 commit：post-`2b753ad`（2026-07-02）。**无稳定 release tag 含 method:dspark**（no reliable source found）。
- **已知 bug #47418**（2026-07-02 opened）："DeepSeek-V4-flash-DSpark 的 spec 功能运行失败"——主线对 DeepSeek-V4 checkpoint 仍不稳。

### SM120 可行性
- **官方仅在 8×B300（SM100）验证**（vLLM X @vllm_project，2026-06，官方："verified on NVIDIA 8×B300 GPUs"）。**无任何官方声明 DSpark 为 SM100 独占**。
- DSpark "复用现有 SparseMLA 后端而非自定义 attention kernel"（官方推文 + #46995 设计说明），原理上不绑定 SM100。
- **社区实测已在非 SM100 跑通**：
  - **sm_120 / RTX PRO 6000 96GB**：`fraserprice/DeepSeek-V4-Flash-Abliterated-DSpark`（HF 卡，社区）——FP8 权重+FP8 KV、`num_speculative_tokens=4–5`、TP=2，DSpark 解码 **1.08×–1.24× 快于 stock MTP**（2–4× RTX PRO 6000 sm_120 / 自定义镜像 voipmonitor/vllm:...cu132-20260629 / 2026-06-27~29 / 社区）。**但明确注明"No released engine ships DSpark yet, so it runs on a purpose-built vLLM image"——非合并主线，且为缩减实现（无 confidence-scheduled verification）**。
  - **sm_90 / H100 NVL**：PR #46995 评论区实测 57.2% 接受率、平均接受长度 3.86 tok/step（2× H100 NVL / #46995 cherry-pick / 2026-06-29 / 社区）。
- **BF16 fallback 路径**：主线**无一手来源**（no reliable source found）；所有实测均 FP8 权重+FP8 KV。

### 关键陷阱：DeepSeek-V4 单卡不可行
DSpark 深度绑定 DeepSeek-V4（V4-Pro 1.6T MoE / 49B 激活，V4-Flash 亦 889B 级）。官方 recipe 需 4×GB300 或 8×B300，社区 sm_120 实测需 **~180GB 总 VRAM（多卡 TP）**。**单张 84/96GB 无法承载 V4-Pro/Flash**。可行路径：GLM-5.2 / Qwen3 speculator（`mgoin/GLM-5.2-speculator.dspark-preview`、`deepseek-ai/dspark_qwen3_8b_block7`）。

### 单卡实验配置与 τ 观测
- Qwen3-8B/14B、Gemma4-12B（BF16）+ 对应 dspark draft/speculator，在 8k/32k context × 并发 1–16 下，84/96GB 单卡可承载（weights+draft+KV）。
- **τ 观测**：主线 vLLM 已暴露 `spec_decode_num_accepted_tokens_per_pos` / `num_drafts` 计数器（RedHatAI GLM-5.2 卡，官方），τ=1+Σ(per-position acceptance)。**无需 rafaelcaricio fork 的直方图**——主线计数器已等效。

### 参数表（method=dspark）
| key | 取值 | 备注 |
|---|---|---|
| `method` | `"dspark"` | 必填，无自动检测 |
| `num_speculative_tokens` | 4/5/7 | 官方示例用 7 |
| `draft_sample_method` | `greedy`/`probabilistic` | DeepSeek 卡用 greedy；GLM/概率路径早期有 bug 后修 |
| `attention_backend` | `FLASH_ATTN` | 稠密/Qwen3/GLM 目标用；DeepSeek-V4 走 SparseMLA 时可省 |
| `model` | speculator HF 路径 | V4 自带 draft 可省；Qwen3/GLM 需指定 |

- **prefix-caching 交互**：官方称 DSpark "works with prefix caching and FP8 KV cache"。compass 引 vLLM #38182（MTP 使 prefix-cache 命中 92%→71%）——DSpark 是否有同类降级**无一手来源**（no reliable source found），须实测。
- **三推测范式对比**：Qwen3.6 MTP（method:mtp）× 标准 draft spec × DSpark speculator，在同一张卡同一 Qwen3-8B/14B 上做"三范式×并发"同图对比**可行**。

### 对 PiLoop v3.2 的直接结论（≤10 条）
1. DSpark 核心代码已入主线（#47093，2026-07-02），但仅 nightly，DeepSeek-V4 checkpoint 有 open bug #47418。
2. **矛盾（与 v3.2 冲突）**：v3.2 指定 6000D 承载"native vLLM DSpark 实验"，但 DeepSeek-V4 需 ~180GB，**单卡不可行**；R-Max DSpark 实验须转向 Qwen3-8B/GLM speculator。
3. sm_120 可跑但迄今均用自定义镜像，主线 #47093 在 sm_120 上未经官方验证——**高风险项**，须自建 build 并验证 SM120 dispatch。
4. τ 观测用主线 spec_decode 计数器即可。
5. 三推测范式（DSpark speculator × MTP × 标准 draft）同图对比可行，作为 R-Max 亮点实验。
6. 全程锁 FP8+FP8 KV（无 BF16 fallback 依据）。

## 模块 3 · NVFP4 量化层（跨格式三层量化矩阵新成员）

### PTQ 工具链
- **NVIDIA ModelOpt（modelopt）**：支持 NVFP4 PTQ，`NVFP4_DEFAULT_CFG`，导出 TensorRT-LLM/vLLM/SGLang/HF（Spheron/NVIDIA 文档，2026，官方/社区）。pin `nvidia-modelopt≥0.17`。
- **TensorRT-LLM**：支持 Qwen3 NVFP4（**blocksize=16**，权重+激活），`trtllm-build` 流程；ModelOpt 修复过 Qwen3 MoE 导出 issue（TRT-LLM changelog，官方）。sm_120 支持须验证 build。
- **vLLM 直 serve NVFP4**：vLLM≥0.9.1 可直接 serve RedHatAI/*-NVFP4；Qwen3.6-35B-A3B-NVFP4 用 llm-compressor，`vllm serve RedHatAI/Qwen3.6-35B-A3B-NVFP4 --reasoning-parser qwen3 --moe_backend flashinfer_cutlass`（HF 卡，官方）。

### 精度证据
- **大模型恢复率高**：Red Hat Developer（2026-02，官方）报 NVFP4 大 dense/MoE 恢复率 >99%（Qwen3-235B-A22B），MMLU/HumanEval 接近 BF16，9 项基准均值内比 FP8 差 <0.5 分（4 项反超 FP8）。NVIDIA 称 Qwen3.6-27B-NVFP4 精度损失 <1%（Flowtivity 引 NVIDIA，社区）。
- **小模型退化显著**：arXiv **2606.05682**（"Beyond Output Matching"，2026，论文）报 Qwen3-4B-Thinking-2507 NVFP4 PTQ：AIME25 **79.6%→62.9%**、GPQA-D **63.2%→58.8%**、LiveCodeBench-v5 **62.2%→55.4%**，退化集中在中/高难度题（易题仍饱和）。QAD 可恢复至 68.5%/59.5%/57.9%。
- **agent/tool-call 任务的 FP4 行为无公开数据（no reliable source found）——正是项目待填补的空白，可作为独特贡献点。**

### 位预算机制（免责声明用一页）
| 格式 | 机制 | 位预算 |
|---|---|---|
| **NVFP4** | E2M1（1 符号+2 指数+1 尾数）+ 两级 scale + 16 元素微块 | 权重~4-bit，激活亦 4-bit（W4A4）|
| **GGUF Q4_K_M** | k-quant 块量化，混合精度（重要层升 8/16-bit）| 权重~4.5-bit 有效，激活运行时 dequant |
| **RKLLM W8A8** | 8-bit 权重 + 8-bit 激活，NPU 定点 | W8A8 |
三者位预算/激活精度/硬件路径（Blackwell tensor-core vs llama.cpp CPU/GPU vs RK3588 NPU）均不同，**不可直接比较**——报告须显式声明。

### 现成 NVFP4 repo（HF，均已核实模型卡）
- `RedHatAI/Qwen3-14B-NVFP4`（apache-2.0，8988M 参数，vLLM≥0.9.1，2025-11 更新，官方卡）
- `RedHatAI/Qwen3-30B-A3B-NVFP4`、`RedHatAI/Qwen3.6-35B-A3B-NVFP4`
- `nvidia/Qwen3.6-27B-NVFP4`（19.7GB，2026-06-26 发布）
- `unsloth/Qwen3.6-27B-NVFP4`

### 对 PiLoop v3.2 的直接结论（≤10 条）
1. 直接用现成 NVFP4 checkpoint（RedHatAI/nvidia/unsloth 系列）省自校准时间。
2. 报告必写"三量化格式不可直接比较"免责声明（附上表）。
3. NVFP4 在 4B 小模型退化明显（AIME −17pp），量化矩阵对比须注明 scale 依赖与题目难度分层。
4. **agent/tool-call FP4 行为是项目独特贡献点**，应设计专门评测。
5. serve NVFP4 MoE 用 `--moe_backend flashinfer_cutlass`，并验证 sm_120 原生路径（否则退 Marlin）。

## 模块 4 · 84/96GB 训练与剪枝

### 大 LoRA 实操
- **Unsloth 官方明确不推荐 Qwen3.5 系列（含 27B/35B-A3B）用 QLoRA（4-bit）**，"due to higher than normal quantization differences…use bf16 for LoRA or full fine-tuning"（unsloth.ai/docs，2026，官方）。
- **Qwen3-30B-A3B 16-bit LoRA 用 63GB**（Unsloth grouped_mm + Triton MoE kernel，官方）。
- 84/96GB 单卡可承载 **27B bf16 LoRA** 并留 seq/batch 余量；96GB 多约 12GB 头寸（可提升 seq 或 batch）。
- **社区先例（OOM 边界）**：H100 80GB 上 35B-A3B LoRA 在 max_seq=4096 时反向激活已近 74GB 上限（Medium/Shaaf Salman，2026，社区："CUDA OOM at MAX_SEQ_LENGTH=4096…~74GB after weights loaded"）——84GB 稍宽，96GB 明显更稳。
- Gemma4-31B LoRA 参照同量级（Gemma4-26B-A4B 51.6GB 全精度）——bf16 LoRA 单卡可行。

### 全参对比
Qwen3-4B / Gemma4-E4B 全参微调在 84/96GB 可行；优化器建议 **adamw_8bit**，seq 上限视激活而定。LoRA-vs-full 对比实验设计可参照 Unsloth 官方 notebook。

### 32k 长上下文 SFT
2B/4B 模型 16k–32k agent-trace SFT 在 84/96GB 可行，用 Unsloth **gradient checkpointing（"unsloth" 模式）+ Flex Attention**（官方称 >6× 更长 context、>35% VRAM 降低）。

### LLM-Pruner Taylor（~80G 显存需求）
- LLM-Pruner 官方 repo（horseee，NeurIPS 2023）支持 Llama-3/Qwen 等，`--pruner_type taylor --taylor param_first`，Discovery/Estimation/Recover 三阶段。
- **~80G 数字针对较大模型**（Taylor 需一阶梯度，显存随模型规模线性增长）；**Qwen3-1.7B/4B Taylor 剪枝显存需求远低于 80G**，单张 84GB 宽裕。
- Qwen3 架构适配：社区研究（arXiv 2603.08083 HFPrune）已在 Qwen3-1.7B 上做 Taylor 剪枝对比，证明可行。
- **替代路径**：NVIDIA ModelOpt/NeMo 提供 Qwen3-8B 深度剪枝（36→24 层 ≈6B）+ 蒸馏 pipeline（官方 NeMo notebook，2-GPU PP，可裁剪至单卡工作流）；mcore_minitron/FastNAS 单卡（非 8 卡 TP）可行。

### on-policy / GKD 蒸馏
- **TRL GKDTrainer 存在**（TRL 库，2026）。
- 84GB 单卡 "teacher 9–12B（FP8/NVFP4 serving）+ student 4B LoRA" 在线蒸馏**无直接一手先例**（no reliable source found）——正是 P2 待验证流程。
- 离线参考：NVIDIA **Open-SWE-Traces** 蒸馏框架（见模块 6）提供 teacher-trace 离线蒸馏路径。

### 对 PiLoop v3.2 的直接结论（≤10 条）
1. 27B/35B-A3B 一律 **bf16 LoRA，禁 QLoRA**（Unsloth 官方警告）。
2. 84GB 跑 35B-A3B LoRA 时 seq 上限约 4k（对标 H100 80GB OOM 先例）；96GB 略宽可推更长。
3. LLM-Pruner 80G 针对大模型；1.7B/4B 需求低，单卡宽裕——可安排为 6000D 五大任务之一。
4. Qwen3 深度剪枝优先走 NVIDIA NeMo/ModelOpt 单卡工作流。
5. **GKD 在线蒸馏（teacher FP8/NVFP4 + student 4B LoRA）是 P2 待验证空白**，无先例须自建。

## 模块 5 · 术语与话语层（支持 "Loop Engineering" 清理）

### "Loop Engineering" 批评溯源
- **命名与引爆**：该词于 **2026 年 6 月第二周由 Peter Steinberger 引爆**、次日经 Google 的 **Addy Osmani** 撰文《Loop Engineering》结构化命名；引爆帖据 Tosea.ai 报道 "reportedly crossed 6.5 million views in days"（社区）。核心口号来自 Claude Code 负责人 **Boris Cherny（Anthropic）**："I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops."；Peter Steinberger："You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."
- **四层谱系**：prompt → context → harness → loop engineering。Osmani 原文定位："Loop engineering sits one floor above the harness…but it runs on a timer, it spawns little helpers, and it feeds itself."（addyosmani.com/blog/loop-engineering）。
- **"造新词/换皮"批评核心**：loop/harness 均非新概念，上溯 **ReAct（2022）、Reflexion（2023）、AutoGPT、SWE-agent/Terminal-Bench harness**。学术界已用中性术语 **"agentic harness engineering"**（arXiv **2604.25850**，"Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses"，论文）与 **"The Last Harness You'll Ever Build"**（arXiv 2604.21003）。PostHog 生产实测该 loop 带来 "an 11% performance improvement and a 3-year-old defect fixed…hands-off"（dev.to，社区）。

### 成熟术语定义与代表文献
| 术语 | 一句话定义 | 权威来源 |
|---|---|---|
| **agent harness** | 包裹单次 agent 运行的环境/工具/脚手架/护栏 | MindStudio blog；arXiv 2604.21003（论文）|
| **agent runtime** | agent 执行的运行时层（调度/状态/恢复）| Verdent/MindStudio（社区）|
| **agentic workload** | 以 agent 为中心的工作负载类型（NVIDIA/vLLM 官方文案常用）| NVIDIA RTX PRO 6000 产品页（官方）|
| **context engineering** | "填充上下文窗口、放入恰当信息的精细艺术与科学" | Karpathy X 帖（官方，见下）|
| **evaluation harness** | 评测脚手架（连接模型与沙箱任务）| Terminal-Bench/Harbor；lm-eval-harness |

### "context engineering" 接受度（决定是否可安全使用）
- **定义（逐字）**：Andrej Karpathy 于 **2025-06-25** X 帖定义："in every industrial-strength LLM app, context engineering is the delicate art and science of filling the context window with just the right information for the next step"（@karpathy，官方）。该帖回应 Shopify CEO **Tobi Lütke**："I really like the term 'context engineering' over prompt engineering. It describes the core skill better: the art of providing all the context for the task to be plausibly solvable by the LLM."
- **背书与接受**：Simon Willison 预言该词会"沾住"；**Gartner 明确宣布 2026 为 "The Year of Context"**，称 "Context is emerging as one of the most critical differentiators for successful agent deployments"，将 context engineering 列为 2026 breakout AI capability（Taskade/Joe Reis 引 Gartner）。
- **造词争议**：Karpathy 明确回应 "I'm not trying to coin a new term. I just think that when people mention 'prompts', they tend to oversimplify…"（36Kr 引，官方）。**结论：可安全使用，无造词污名。**

### 对 PiLoop v3.2 的直接结论（≤10 条）
1. **移除自造 "Loop Engineering" 品牌**，改用 harness / agent runtime / agentic workload / context engineering。
2. **context engineering 最安全**：有 Karpathy/Lütke/Gartner 权威背书，无造词争议。
3. 简历/README 映射表：
   - "Loop 工程/优化循环" → **agentic workload optimization** + **agent harness engineering**
   - "上下文拼装/信息注入" → **context engineering**
   - "评测环路" → **evaluation harness**
   - "推理/算子协同优化" → **inference optimization / kernel & operator optimization**（保留业界通用词）
4. 引用 Karpathy（2025-06-25）、Anthropic（Boris Cherny loops）、LangChain（write/select/compress/isolate 分类）、arXiv 2604.25850 作权威锚点。
5. 避免在正式文档中把 loop engineering 当作既有学科术语——它是 2026 年才流行的营销/口号词，学术等价物是 "agentic harness engineering"。

## 模块 6 · v2 遗留核查

### Terminal-Bench 2.1
- 修复 2.0 中 **89 个任务里的 28 个**（PR **#53**，tbench.ai/news/terminal-bench-2-1，官方）；三类缺陷：外部依赖漂移、资源不匹配、规格-验证错配。修复后 **无任务未解**。
- **数据集可拉取**：Harbor Hub `terminal-bench/terminal-bench-2-1`（`harbor run -d terminal-bench/terminal-bench-2-1`，官方）。
- 影响幅度：frontier agent 分差最多 **12.1pp**（Claude Code+Opus 4.6）；但小模型影响小——OpenThoughts 报 Qwen3.5-27B 在 2.0→2.1 仅变 3.0pp（arXiv 2606.24855）。

### MLC-LLM Qwen3/Gemma
- MLC 走 TVM Unity/OpenCL，Orange Pi 5 **Mali-G610** 路径成熟（历史：Llama3-8B 2.3 tok/s、Llama2-7b 2.5 tok/s、RedPajama-3b 5 tok/s @ Orange Pi 5，blog.mlc.ai/2024-04，官方）。
- **2026 年 Qwen3/Gemma4 在 Mali 路径的新测无一手来源**（no reliable source found）；MLC 模型库以 q4f16_1 为主。须自测。

### RKLLM prompt cache C API（rkllm.h）
- 结构体：`RKLLMPromptCacheParam { int save_prompt_cache; const char* prompt_cache_path; }`；`RKLLMInferParam` 含 `prompt_cache_params` 指针与 `keep_history`（1 保留/0 丢弃）（airockchip/rknn-llm rkllm.h，官方）。
- 函数（DeepWiki API Reference + docs.rs 确认）：`rkllm_load_prompt_cache(handle, prompt_cache_path)`、`rkllm_release_prompt_cache(handle)`，返回状态码 0=成功。
- v1.3.0：缓存文件默认存 **7 天**（可配）后自动删除（NotPunchnox/rkllama，社区）；已加 Qwen3.5/Gemma4/SmolLM3 支持。
- **限制**：多缓存文件管理无高级 API（须应用层自管路径/失效）；`rkllm_clear_kv_cache` 支持 keep_system_prompt 与 [start_pos,end_pos) 范围清除，但仅在 keep_history==0 且暂停生成时有效。

### Open-SWE-Traces（arXiv 2606.16038，NVIDIA）
- **207,489 条轨迹**，9 语言（Python/Go/TS/JS/Rust/Java/PHP/C/C++），来自 20,000 真实 PR（OpenHands + SWE-agent harness），Minimax-M2.5（thinking）+ Qwen3.5-122B-A10B（non-thinking）合成，SWE-rebench-V2 过滤许可证（MIT/Apache/BSD）。
- **HF nvidia/Open-SWE-Traces**（已核实卡）：subset openhands 105k + sweagent 102k；split minimax_m25 49.9k + qwen35_122b 55.5k；**18.3GB，CC-BY-4.0**，近 30 天下载 3,499。
- **Resolved/Unresolved 结论**：全量（含 unresolved）优于 resolved-only，"including trajectories with unresolved patches…is generally superior"（论文 Table 5 消融）。四配置存在跨 harness 惩罚（切换 agent 框架有一致性能下降）。
- Resolve rate：SWE-bench Verified **61.7%**、Multilingual **57.1%**、Pro **36.8%**（论文，官方）。

### pi-share-hf 清洗流
**无一手 repo 细节**（install/redaction rules/TruffleHog 集成/upload flow 均 no reliable source found）——须直接抓取实际仓库核实。

### llama.cpp ft-dspark 分支
- **Qwen3.6 MTP 已合并 llama.cpp 主线**（Unsloth 确认，"llama.cpp has merged MTP support"，官方）；27B MTP 160 tok/s、35B-A3B 240 tok/s @ RTX 6000（Unsloth，社区实测）。
- **DSpark 专用 `--spec-type draft-dspark` 分支无一手来源**（no reliable source found）；DSpark 目前实现集中在 vLLM，非 llama.cpp。

### 对 PiLoop v3.2 的直接结论（≤10 条）
1. Terminal-Bench 2.1 可用（Harbor Hub 拉取），**须用 2.1 重跑所有 agent 基线**。
2. RKLLM prompt cache API 签名已确认，可实现 save/load，但多缓存须应用层自管。
3. **Open-SWE-Traces 可直接用作 agent-trace SFT/蒸馏数据源**（CC-BY-4.0，18.3GB，含 thinking/non-thinking 双模）。
4. MLC Qwen3/Gemma4 2026 Mali 新测缺失，须自测后再纳入边缘对比。
5. pi-share-hf 清洗流与 llama.cpp DSpark 分支须一手核实（当前无据）。
