## 0. 执行摘要

### 0.1 总体判断

PiLoop v3 的重构方向成立，而且比 v2 更适合秋招与大四持续迭代：

1. **HF Agent Traces 生态已经可作为 workload 数据底座。** Hugging Face 已原生支持 Claude Code、Codex、Pi Agent raw JSONL trace，并提供 trace viewer；STS-Format 允许自建 harness 以 JSONL session header + message lines 的方式接入。公开数据集从 Pi/Fable、Claude Code、Hermes、OpenHands/SWE-agent、OpenTelemetry 观测 trace 到 kernel agent trace 都已出现。
2. **benchmark 底座可公私分层。** Terminal-Bench 2.0 是最贴近 PiLoop 的主 benchmark；SWE-bench Lite/Verified 适合小子集回归；KernelBench 家族适合项目 2；AgentWorldBench 需要纠偏为“世界模型评测/任务来源”，不能作为 agent 任务成功率 benchmark。
3. **并发轴不是锦上添花，而是系统差异化。** llama.cpp server 已具备 `--parallel`、continuous batching、prompt cache 与工具调用相关字段；Terminal-Bench harness 本身也支持并发 trials。与 RKLLM 的板端 HTTP server/单 NPU runtime 对照，可以形成“GPU continuous batching vs NPU queueing/fallback”的硬实验。
4. **小模型 agent SFT/蒸馏可做，但必须控制数据许可与长 trace 长度。** Qwen3 1.7B/4B 是 4060 8GB 的 P0/P1 主力；8B 需要短上下文、4-bit、LoRA/QLoRA 与小 batch；长 trace 需要截断、trim、packing、assistant-only loss 与工具 schema 压缩。
5. **DSpark/DeepSpec 的定位准确：用发布 checkpoint 做租卡实验；不要自训 draft。** DeepSpec 官方 README 说明默认 Qwen3-4B 数据准备 target cache 约 38TB，默认脚本假设单节点 8 GPU；但官方已经发布 Qwen3-4B/8B/14B 与 Gemma4-12B 的 Eagle3/DFlash/DSpark checkpoints。
6. **项目 2 的三 kernel 设计合理。** K1 RMSNorm/softmax 用 Liger/Triton 教程打底；K2 decode attention 连接 TPOT 与 KV-cache；K3 选 batched decode attention 优先于 KV-quant fused，因为 batched decode 更容易在 4060 上得到系统级回连，KV-quant fused 更适合 P2/stretch。
7. **RK3588 可跑 4B 档但不能承诺强 agent 能力。** RKLLM v1.3.0 已支持 Qwen3.5/Gemma4 等新模型与 OpenAI-compatible server demo；公开性能表显示 RK3588 上 Qwen3.5-4B W8A8 约 6.22 tok/s、内存 4576 MB。端侧 agent 应以“能力地板 + 升档率 + fallback router”叙事，而不是假设板端小模型单独完成复杂任务。
8. **国内 JD 抓取未能形成可复核词频样本池。** 本轮未找到足够公开、可稳定抓取、带日期的 2026-06/07 国内校招/实习 JD 样本，不能输出严肃词频百分比。报告仅给低置信度工具链映射与二次抓取方案。

### 0.2 P0/P1/P2 结论

- **P0（秋招前必须跑通）**：HF trace 归一化 + Pi trace hook + llama.cpp 并发 sweep + Terminal-Bench 2.0 小子集 + 自建端侧并发 benchmark + RK3588 Qwen3.5/Gemma4 小模型吞吐复测 + K1/K2 至少各一个 kernel。
- **P1（形成差异化）**：Qwen3-4B trace QLoRA SFT → GGUF Q4/RKLLM W8A8 → A/B/C 模型来源对照；Pi subagent fan-out 扩展；K3 batched decode；DSpark checkpoint 租卡并发实验。
- **P2/stretch（秋招后持续迭代）**：KV-cache quant fused kernel；Gemma4 MTP/draft 本地复现；KernelBench agent-assisted kernel optimization；自采 trace 数据集发布与上游 issue/PR。

## 1. 模块 1 · HF Agent Trace 数据集普查

### 1.1 HF Agent Traces 格式与 viewer 基座

**官方来源结论（高置信度）**：Hugging Face Hub 的 Agent Traces 文档说明，Claude Code、Codex、Pi Agent 的 raw JSONL sessions 可直接上传到 Dataset 或 Storage Bucket，并在 Data Studio/trace viewer 中查看 session timeline、prompts、assistant messages、tool calls、results。Pi Agent 默认本地目录为 `~/.pi/agent/sessions`；`pi-share-hf` 可帮助收集 Pi sessions、redact known secrets、运行 TruffleHog 与 LLM review 后上传。STS-Format 则规定首行 session header，后续 message lines 包含 role/content/reasoningContent/toolCalls/toolCallId/timestamp/model。

- Source type：官方文档；日期：2026-07-03 抓取；链接：https://huggingface.co/docs/hub/agent-traces 与 https://huggingface.co/docs/hub/session-traces-format
- 对 PiLoop 的意义：自采 Pi trace 不需要先发明完整格式；只需在 Pi session format/STS 外补 `harness_source`、`origin_dataset`、`concurrency_group`、`subagent_parent_id` 等 PiLoop 字段，便能兼容 HF viewer 与本项目 replay/schema。

### 1.4 面向 1.7B–8B 小模型 agent SFT 的推荐组合

#### 组合 A：许可相对友好的主线 SFT（P1 推荐）

- `nvidia/Open-SWE-Traces`（CC-BY-4.0）：提供大规模 SWE-agent/OpenHands 软件工程 trajectories。
- `trace-commons/agent-traces`（CC-BY-4.0）：提供真实 coding-agent sessions 与 command output。
- `lambda/hermes-agent-reasoning-traces` 或 filtered subset（Apache-2.0）：补多轮 tool reasoning。
- 自采 Pi traces（私有审查后发布 CC-BY/MIT 自定）：补齐 Pi-specific schema、short-context 与 subagent fan-out。

**配比建议**：先 40% Open-SWE + 25% Trace Commons + 20% Hermes filtered + 15% 自采 Pi；Qwen3-4B 上先 1–3k high-quality subset smoke test，再扩展。  
**许可结论**：可作为公开研究模型的相对安全组合；仍需在 model card 列数据来源与 license。

#### 组合 B：Pi/Fable 高信号但强许可约束（仅研究/AGPL 兼容）

- `Glint-Research/Fable-5-traces` 或 `armand0e/claude-fable-5-claude-code` 二选一。
- `lordx64/agentic-distill-fable-5-sft` 用于 tool-use format warmup。
- `armand0e/qwen3.7-max-pi-traces` 用于 Pi tool schema alignment。

**配比建议**：Fable 60% + Pi Qwen traces 25% + self traces 15%。  
**许可结论**：因 AGPL 与同源重复风险，不建议作为秋招公开权重主线；可以作为内部 ablation。

#### 组合 C：端侧 agent 自建差异化（P0/P1 最贴项目）

- `davanstrien/pi-traces` + `davanstrien/agent-race-traces` + 自采 Pi traces。
- 重点保留 `concurrency_group`、`subagent_parent_id`、工具 schema 复杂度、context budget、backend 路由选择。

**配比建议**：公开 Pi examples 20% + 自采 60% + Trace Commons 20%。  
**许可结论**：最适合发布 PiLoop 自采 trace 数据集与 benchmark；训练规模较小但最贴任务分布。

### 1.5 对 PiLoop v3 的直接结论（≤10 条）

1. HF Agent Traces + Pi session format 已足够支撑 PiLoop 的统一 trace schema，不必自造 viewer。
2. Fable 系列是高信号但高许可/同源风险数据，只可作为研究/ablation，不能做默认公开训练主线。
3. Open-SWE-Traces 是最大规模 SWE agent SFT 候选，但需要 OpenHands/SWE-agent → Pi schema adapter。
4. Trace Commons 与 Hermes traces 许可友好，适合与自采 Pi traces 混合。
5. `Infatoshi/kernelbench-mega-traces` 不喂方向 A 主模型，但对项目 2 的“agent-assisted kernel optimization”极有价值。
6. 所有 public trace 在训练前必须跑 PII/secret/path/license 审查；`pi-share-hf + TruffleHog + 人工抽样` 应成为数据管线强制门。
7. 小模型训练集不宜盲目追求百万行，先做高质量 1k–10k subset，并以工具调用成功率和端侧 benchmark 成功率作为选择标准。
8. trace schema 需要显式记录 harness、origin_dataset、license、tool_schema_hash、context_tokens、concurrency_group 与 subagent_parent_id。
9. Source-C 自训模型的目标应是“窄域 agent 行为稳定性”，不是通用能力超过官方基座。
10. 发布任何权重/数据集时必须写清数据来源、许可继承与排除项。

## 2. 模块 2 · Agent Benchmark 普查

### 2.1 Terminal-Bench 2.0

- 官方主页：https://www.tbench.ai/
- GitHub/文档：https://github.com/harbor-framework/terminal-bench 与 https://www.tbench.ai/docs
- 定位：Terminal-Bench 测试 AI agents 在真实 terminal 环境中完成任务的能力；任务包括编译代码、训练模型、设置服务器等。官方主页显示 terminal-bench@2.0 active，包含 89 个 high-quality tasks，任务域覆盖 software engineering、ML、security、data science 等。
- harness：包括 task dataset 与 execution harness；任务由 `task.toml`、`instruction.md`、`environment/Dockerfile`、`solution/solve.sh`、`tests/test.sh` 等组成。自定义 agent 可继承 `BaseAgent`/`AbstractInstalledAgent`，实现 `perform_task`，并通过 `--agent-import-path` 接入。
- 并发/资源：Harbor adapters 文档支持 `n_concurrent_trials`；README leaderboard run 示例包含 `--n-concurrent 8`。GPU tasks 可在 Docker compose 中声明 NVIDIA reservations，并在 `task.toml` 设置 gpus。
- Pi 官方关联：Pi/terminal agent 生态已经在 Terminal-Bench 上有公开表现；即使不使用官方 Pi 跑分，Terminal-Bench 2.0 也足以作为 PiLoop agent 成功率主 benchmark。
- 硬件可行性：4060 本地可跑无 GPU 或轻量任务子集；需要 Docker 与磁盘。重 GPU/ML training tasks 应放租卡或剔除。
- 置信度：高。

**PiLoop 接入建议**：P0 选 8–12 个任务，按“纯 shell/file edit、package install、small code fix、tiny ML、security toy”分层；每个任务跑 A/B/C 模型来源 × agent 优化开关 × 并发度 1/2/4。P1 再扩至 20–30 个。

### 2.2 SWE-bench Lite / Verified

- 官方主页：https://www.swebench.com/
- GitHub：https://github.com/swe-bench/SWE-bench
- 定位：评估模型解决 GitHub issues 并生成 patches 的能力。官方 leaderboard 包含 Verified、Lite、Full、Multimodal、Multilingual 等。
- 规模：Verified 为 500 human-filtered problems；Lite 为 300 个较低成本样本；Full 为 2294 个样本。
- 本地运行需求：官方文档提示 Docker 可复现实验；Lite evaluation 示例需要 x86_64、约 120GB storage、16GB RAM、8 CPU cores。4060 8GB 不是瓶颈，磁盘与环境构建时间才是瓶颈。
- PiLoop 可行性：不适合 P0 全量跑；适合 ≤5–10 个 Lite/Verified sample 作为“真实 repo 修复”硬证据。
- 置信度：高。

### 2.3 AgentWorldBench（Qwen）纠偏

- 论文/主页信息：AgentWorldBench 来自 5 个 frontier models 与 9 个 established benchmarks 的真实 agent-environment interactions；覆盖 MCP、Search、Terminal、SWE、Android、Web、OS 七域；评估 simulation/world model quality 的 format、factuality、consistency、realism、quality 等维度。
- 关键纠偏：AgentWorldBench 是 **Learning World Models for Agents / 世界模型评测**，不是端侧 agent 任务成功率 benchmark。它的价值在于任务 query 来源、环境观测分布与 world model 质量指标，不应被写成 PiLoop 的 success-rate 主 benchmark。
- 可复用部分：可从其来源基准（例如 Terminal-Bench 1.0/2.0、OSWorld-Verified、Tool Decathlon 等）借任务类别，设计自建端侧任务。
- 置信度：高。

### 2.4 Tool Decathlon / APEX-Agents / HLE / 其他 benchmark

#### Tool Decathlon / Toolathlon

- 论文：https://arxiv.org/abs/2510.25726
- 定位：多应用、长程、真实工具执行 benchmark；32 software applications、604 tools、108 tasks，平均约 20 turns；Claude-4.5-Sonnet 38.6%，DeepSeek-V3.2-Exp 20.1%。
- 相关度：高于普通 QA，但环境复杂、MCP 工具多，不适合作 P0 端侧小模型 benchmark。
- PiLoop 用法：P2 作为工具 schema 分层/压缩的压力测试参考。

#### APEX-Agents

- 论文：https://arxiv.org/abs/2601.14242
- 定位：投资银行、咨询、法律等长程跨应用任务；480 tasks；Pass@1；最高公开结果约 24%。
- 相关度：体现 agent 长程困难，但任务与端侧 terminal/code agent 差异大。
- PiLoop 用法：只做趋势引用，不纳入开发主线。

#### HLE / cais/hle

- 官方主页：https://agi.safe.ai/
- 定位：Humanity’s Last Exam，2,500 expert-level questions；2026-01-28 已发表于 Nature；可通过 `load_dataset("cais/hle")` 获取。
- 相关度：HLE 是知识/推理 benchmark，不是 agent success benchmark；只可作为模型基础能力背景，不作为 PiLoop agent 回归。

#### Mobile/Smartphone/OS agent benchmarks

- SPA-Bench：智能手机 agent benchmark，覆盖系统与第三方 app，中英任务，关注任务完成与资源消耗。
- Mobile-Bench-v2：VLM-based mobile agents benchmark，包含多路径、噪声、模糊指令等。
- 相关度：说明“端侧/移动 agent benchmark”存在，但主要是 Android GUI/VLM agent，不直接覆盖 RK3588 + terminal/Pi coding agent 的量化×并发×成功率联动。

### 2.5 是否存在端侧/资源受限 agent benchmark？

本轮未找到同时满足以下条件的公开 benchmark：

- 明确面向端侧小模型/本地推理；
- 同时报告量化档、并发度、TTFT/TPOT、成功率；
- 可在 RK3588 / RTX4060 / 租卡三档硬件上统一复现；
- 覆盖 terminal/code agent 或 Pi-like tool calling。

因此，“自建端侧特化 benchmark（并发×量化×成功率）”具有真实空白性。已有 mobile/OS/terminal benchmarks 可作为任务灵感，而不能替代 PiLoop 自建层。

### 2.6 对 PiLoop v3 的直接结论（≤10 条）

1. Terminal-Bench 2.0 是 PiLoop v3 agent 成功率主 benchmark，P0 必须接入。
2. SWE-bench Lite/Verified 只跑小子集，用于证明真实 repo 修复能力，不要变成主工作量黑洞。
3. AgentWorldBench 必须纠偏为世界模型评测/任务来源，不能写成 agent success-rate benchmark。
4. Tool Decathlon/APEX-Agents 证明长程工具 agent 仍很难，但对端侧 P0 过重。
5. HLE 不是 agent benchmark，可作为模型知识/推理背景，不进 PiLoop 主指标。
6. 端侧量化×并发×成功率公开 benchmark 缺口真实存在，自建 benchmark 是差异化点。
7. benchmark 层要分“公开公信力层”和“端侧特化快速回归层”，前者保证可引用，后者保证可迭代。
8. 所有 benchmark 都要记录硬件、模型来源、量化、后端、并发度、context budget、工具 schema 版本。
9. Terminal-Bench harness 的 concurrent trials 与 Pi subagent fan-out 可形成一致实验故事。
10. P0 不追求榜单分数，而追求 before/after 回归矩阵与 failure taxonomy。

## 3. 模块 3 · 端侧/本地并发推理现状

### 3.1 llama.cpp：本地并发主力

- 官方 repo：https://github.com/ggml-org/llama.cpp
- server 文档：https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md
- 并发能力：llama.cpp server 文档列出 parallel decoding / multi-user、continuous batching、function calling/tool use、speculative decoding、monitoring、JSON schema 等特性。
- 关键参数：
  - `--parallel N`：server slots / parallel sequences。
  - `--cont-batching`：continuous batching，文档显示为 enabled by default；可用 `--no-cont-batching` 关闭。
  - `cache_prompt`：OpenAI-compatible API 中默认 true，复用已有 prompt cache。
  - chat 字段包括 `parse_tool_calls` 与 `parallel_tool_calls`。
- `llama-batched-bench`：支持 `-npl 1,2,4,8,16,32` sweep；两种模式包括各序列独立 KV 与共享 prompt 后生成。适合直接做 batch/parallel scaling 诊断。
- 工具调用：server 文档已出现 function calling/tool use 与 parallel_tool_calls 字段，但具体模型工具调用质量仍取决于 chat template 与模型。
- 置信度：高。

**PiLoop 实验建议**：先用 `llama-server` 对 Qwen3-1.7B/4B GGUF Q4/Q8 做 `--parallel 1/2/4/8`，固定 prompt prefix 与工具 schema，记录 TTFT、TPOT、tokens/s、slot 利用率、失败类型。再用 `llama-batched-bench` 做合成基准，与 Pi fan-out live workload 对照。

### 3.2 vLLM / SGLang 在 4060 8GB 上的可用性

- vLLM 量化文档显示支持 AWQ、GPTQModel、BitsAndBytes、Marlin、FP8/W8A8、quantized KV cache 等；Ada 架构在多种量化路径中被列为支持硬件。
- vLLM FP8 KV cache 文档说明 FP8 KV 可减少 KV cache memory footprint，支持更多 tokens、更高吞吐/更长上下文；最佳效果需 calibration。
- SGLang 文档支持 AWQ、w8a8、fp8、torchao 等离线/在线量化路径，面向高吞吐/structured generation。
- 4060 8GB 判断：
  - Qwen3-1.7B/4B 量化模型可尝试本地 vLLM/SGLang；
  - 8B Q4/AWQ 在 8GB 下会被 KV cache、CUDA graph、framework overhead、长上下文挤压，建议 P1 只作为“能否启动 + 小并发”对照，不作为主力；
  - 8B 长上下文/并发 sweep 放租卡更稳。
- 置信度：中到高（特性高，4060 具体可用性需实测）。

### 3.4 多 agent 端侧推理研究线

- TraceLab（2026）：约 4,300 coding-agent sessions、350k LLM steps、430k tool calls；观察到长循环、长上下文短输出、工具调用 heavy-tail、高但不完美的 prefix cache hits；指出低开销工具调用、append-length prefill、语义工具延迟预测、human-paced gap 中 KV reuse 等优化机会。
- CacheFlow（2026）：batch-aware KV cache restoration；TTFT 降低 10–62%。
- SAW-INT4 / Adaptive KV / UltraQuant 等 2026 论文显示 KV-cache quantization、paged-layout fused rotation/quant、context-heavy agent workload 正在成为系统研究热点。
- PersistentKV（2026）：RTX3060 上对 GQA decode scheduling 与 KV paging 做优化，commodity GPU 场景相关。
- 结论：PiLoop 的 concurrency sweep、prefix cache、KV cache 与 K2/K3 kernel 回连，站在真实研究线上。

### 3.5 Pi subagent 并发扩展参考实现

- 官方站点：https://pi.dev/
- 官方 repo：https://github.com/earendil-works/pi
- 设计事实：Pi 默认极简，核心工具为 read/write/edit/bash；官方明确不内置 subagents/plan mode，但提供 TypeScript extensions、skills、prompts、RPC、SDK 等扩展位。
- 官方 example：`examples/extensions/subagent` 展示 specialized subagents with isolated context windows、separate Pi process、streaming、parallel streaming、per-agent turns/tokens/cost/context、abort；parallel mode 支持 task fan-out 与并发上限。
- PiLoop 路径：直接 fork/借鉴官方 subagent extension，而不是从零设计。

### 3.6 对 PiLoop v3 的直接结论（≤10 条）

1. `llama.cpp + --parallel + continuous batching + batched-bench` 是 4060 并发主实验后端。
2. vLLM/SGLang 在 4060 上只做 1.7B/4B 小模型对照；8B 并发 sweep 建议租卡。
3. RKLLM 需要被视作 NPU queueing/single-runtime 档；不要写成 continuous batching。
4. RK3588 的 4B W8A8 可行但慢，适合测能力地板与 fallback router，不适合承诺复杂任务独立完成。
5. Pi 官方 subagent extension 已给出并发 fan-out 参考，可直接作为第三支柱 P1 实现。
6. Prompt prefix 稳定化与工具 schema 精简应同时服务 agent 成功率与 prefix cache 命中率。
7. 并发实验必须记录 queue depth、slot 利用率、KV memory、context length 与失败模式。
8. 多 agent/KV-cache 论文支持 K3 batched decode/KV quant 作为项目 2 的研究线。
9. llama.cpp 的 `parallel_tool_calls` 不等于模型真的会正确并行工具调用，需要 benchmark 验证。
10. Concurrency Sweep 的封面图应区分 synthetic batched-bench 与 live Pi subagent workload。

## 4. 模块 4 · 小模型 Agent 微调/蒸馏管线

### 4.1 teich：可用性与证据边界

- 证据：多个 HF dataset README 明确写明 “generated using teich” 或推荐用 teich 转换；armand0e/qwen3.7-max-pi-traces、armand0e/gpt-5.5-agent、AletheiaResearch/GLM-5.2-Agent 都强调 raw trace files、training-ready tools schema、complete/recovered tool schemas。

- 置信度：中。

### 4.2 Unsloth + TRL v1.0：4060 8GB 可行配置

- Unsloth Qwen3 文档：支持 Qwen3/Qwen3 MoE fine-tuning and RL，宣称 2x faster、70% less VRAM、8x longer context；提供 Qwen3 0.6B/1.7B/4B/8B/14B/30B-A3B 等 Dynamic 4-bit；Qwen3 14B 可在 Colab 16GB T4 上运行示例；fine-tuning 示例建议测试 `max_seq_length=2048`，`load_in_4bit=True` 可减少约 4x memory。
- TRL SFTTrainer 文档：支持 standard/conversational datasets；auto chat template；`assistant_only_loss=True`；packing；PEFT LoRA；tool-calling datasets 可包含 `messages`、`tool_calls`、`tools` schema columns。
- 4060 8GB 判断：
  - Qwen3-1.7B：P0 主力，max_seq_len 2k–4k，batch 1–2 + gradient accumulation。
  - Qwen3-4B：P1 主力，4-bit QLoRA，max_seq_len 2k 起步；长 trace 先 trim。
  - Qwen3-8B：只做短序列/小样本 smoke 或租卡；本地 8GB 容易被长 trace 与 optimizer 挤爆。
  - Gemma4-E2B/E4B：作为 RK3588 Gemma4 对照值得尝试，但训练工具链成熟度需先验证。
- 长 trace 策略：按 task turn window 分块；保留 system + tools + recent messages + error snippets；assistant-only loss；工具 schema hash 去重；对失败修复轮次加权。
- 置信度：高（TRL/Unsloth 功能）；中（具体 4060 长 trace 配置）。

### 4.3 agentic distillation 公开先例与指标

- Tool knowledge internalization 论文（2026）显示，小模型可通过 QLoRA 学习工具知识与规划能力；Gemma4-E4B 和 Qwen3-4B 在约 1700 examples 上做 8-bit QLoRA，description-free inference 可减少 82.6% 输入长度并改善 planning scores；Qwen3-4B 内存低、速度快，但更易 catastrophic forgetting。
- 其他小模型 LoRA/QLoRA 论文说明 1.5B–4B 在 RTX4060 8GB 或生产 CPU/GGUF 档可形成窄域部署证据。
- 对 PiLoop 的指标设计：不要只看 loss；必须测：工具调用 JSON parse rate、tool name accuracy、argument exact/semantic match、execute-test-repair success rate、context budget 下成功率、量化后成功率下降、RKLLM/llama.cpp 部署后差异。
- 置信度：中到高。

### 4.4 微调后 → GGUF / RKLLM W8A8 链路

推荐链路：

1. Base model + LoRA/QLoRA SFT。
2. Merge LoRA；保存 tokenizer/chat_template。
3. GGUF 转换；Q4_K_M/Q5_K_M/Q8_0 对照；llama.cpp server 检查 tool_call 输出。
4. RKLLM-Toolkit W8A8 转换；选择 calibration prompts，必须包含工具 schema、短上下文、错误日志、subagent 汇聚 prompt。
5. 三档对照：Source-A 官方基座/官方量化；Source-B 第三方量化/微调；Source-C 自训自量化。

主要风险：

- chat template 不一致导致 tool calls 崩；
- tokenizer special tokens / EOS / `<tool_call>` format 丢失；
- 量化校准集不含工具 schema，导致 JSON/tool format 坍塌；
- 长 trace SFT 后在小模型上过拟合 Fable/Claude style；
- RKLLM runtime 对特定模型架构支持滞后。

### 4.5 结构化剪枝小实验

- 本轮未找到 2026 年面向 Qwen3/Gemma4 agent SFT 后结构化剪枝的稳定、低成本、一手实操流程。
- 可行降级：P2 做一次小型 ablation，如剪 MLP intermediate/channel 或套 LLM-Pruner/SparseGPT 类工具，在 Qwen3-1.7B/4B 上只测 5–10% sparsity/width reduction，指标为 RKLLM/llama.cpp latency、显存、工具调用成功率。
- 不建议秋招前把剪枝写成主成果；可以作为 TinyML 理论补洞的“可选实验”。
- 置信度：中。

### 4.6 对 PiLoop v3 的直接结论（≤10 条）

1. Qwen3-1.7B/4B 是方向 A 的现实主力；8B 本地只做短序列 smoke 或租卡。
2. TRL SFTTrainer 的 assistant-only loss、packing、tool-calling dataset 支持正好匹配 agent trace SFT。
3. Unsloth 提供 4-bit/QLoRA 工程可行性，但长 trace 仍必须做 trim/packing。
4. teich 值得纳入，但先做 spike，不能在计划中假设所有 API 已稳定。
5. agentic distillation 的核心指标是工具调用与任务成功率，不是通用 benchmark 胜负。
6. 微调后量化必须用 agent/tool calibration prompts，否则容易 tool format 坍塌。
7. Source-C 可能打不过官方基座，但可在窄域 trace 分布与短上下文工具调用上赢。
8. 剪枝是 P2 小实验，不应吞掉 P0/P1 时间。
9. 训练数据要按 license 分组，AGPL 数据训练出的模型必须单独标注/隔离。
10. 最有价值图表是“模型来源 A/B/C × agent 优化开/关 × 量化档 × 成功率/延迟”。

## 6. 模块 6 · Kernel 微基准生态

### 6.1 KernelBench 家族

- 官方 repo：https://github.com/ScalingIntelligence/KernelBench
- 定位：ICML 2025 benchmark，评估 LLM 生成高效 GPU kernels 的能力，可生成 CUDA/DSL 替换 PyTorch programs。
- 题目层级：L1 100 single-kernel operators；L2 100 simple fusion；L3 50 full model architectures；L4 Hugging Face model architectures。
- 指标：correctness vs randomized torch；performance vs torch；`fast_p` 表示 correct 且 speedup > p；`fast_0` 可视作 correctness。
- backends：cuda、triton、cute、tilelang、thunderkittens；也提到 AMD HIP。
- 官方提醒：不同硬件/cluster power/software version 影响 timing，应为目标硬件生成自己的 baseline。
- PiLoop 价值：题目/评测脚本可复用；但项目 2 的三个 kernel 必须来自项目 1 profiling 现象，而非随机刷 KernelBench。
- 置信度：高。

### 6.2 KernelBench-v2/v3/Hard/roofline 线索

- KernelBench-X（2026）扩展到 176 tasks/15 categories，指出 72% Fusion tasks 失败、46.6% correct kernels 慢于 PyTorch、跨硬件 variance 可达 21.4x、quantization 0/30 successes。
- SOL-ExecBench（2026）强调 Speed-of-Light bounds 与 SOL Score。
- KernelSkill（2026）显示 multi-agent kernel optimization 可在 KernelBench L1–L3 上提升成功率与 speedup。
- 对 PiLoop 的启发：
  - 不要只报“相对 PyTorch 加速”，还要报 roofline/带宽/occupancy/SM utilization；
  - quantized kernel 更难，P2 再做；
  - agent-assisted kernel optimization 可作为秋招后博客/实验，而非主线。

### 6.3 K1：RMSNorm / fused softmax

- 参考线：Liger-Kernel 论文/项目说明 Triton kernels 可提升训练吞吐并降低显存；RMSNorm/softmax/fusion 是新手到中级的合理入口。
- PiLoop 现象回连：decode 路径逐层 element-wise/normalization 占比、small batch 下 kernel launch overhead、memory bandwidth。
- 实验设计：
  - PyTorch eager/torch.compile baseline；
  - Triton implementation；
  - hand-written CUDA implementation；
  - shape sweep：hidden size、batch、seq/token；
  - ncu：occupancy、memory throughput、coalescing、register pressure。
- 置信度：高。

### 6.4 K2：single-token decode attention / GQA

- 现象回连：TPOT 随 context length 增加；KV-cache 显存与 bandwidth；GQA grouped heads；paged KV gather。
- 参考线：vLLM attention backend、FlashAttention minimal、PersistentKV、paged KV papers。
- 4060 实验设计：固定 Qwen3/Gemma-like head dims；batch=1；context length sweep 512/1k/2k/4k/8k；比较 contiguous KV vs paged/gather layout。
- 指标：μs/token、GB/s estimated, L2 hit, achieved occupancy, TPOT system impact。
- 置信度：中到高。

### 6.5 K3：batched decode attention vs KV-cache quant fused

**候选 A：batched decode attention（推荐 P1）**

- 优点：直接对应 Concurrency Sweep；能解释 batch 1→8 后 decode memory/compute behavior；更容易在 4060 上复现。
- 参考：llama-batched-bench、vLLM batched decode、PersistentKV commodity GPU scheduling。
- 输出：batch scaling curve + roofline + 回归到 llama.cpp/vLLM live workload。

**候选 B：KV-cache quant dequant fused（P2/stretch）**

- 优点：研究热；端侧/agent 长上下文强相关。
- 风险：KernelBench-X 显示 quantization 类任务极难；KV quant 与模型精度/布局/scale granularity 紧耦合；4060 工期风险高。
- 输出：先做 Q8_0/Q4_0 dequant micro-kernel，再考虑 fused attention。

**建议**：09_v3 把 K3 P1 写成 batched decode attention，把 KV-quant fused 写成 P2。

### 6.6 Nsight Compute / Proton / vGPU 限制

- NVIDIA 文档说明性能计数器可能因权限受限导致 ERR_NVGPUCTRPERM；Linux 下可能需要 sudo、CAP_SYS_ADMIN/CAP_PERFMON 或容器 cap-add。租用 vGPU 常见限制是无法采集完整 ncu counters。
- 策略：
  - 4060 本机做 ncu/nsys 主 profiling；
  - 租卡只做端到端吞吐与少量可用 metrics；
  - Triton Proton 用于 Triton kernel 内部 profiling，与 ncu 互补。
- 置信度：高。

### 6.7 对 PiLoop v3 的直接结论（≤10 条）

1. 三 kernel 必须从项目 1 profiling 抽取，KernelBench 只提供题目与评测参考。
2. K1 选 RMSNorm/softmax，保证快速产出 Nsight/roofline 证据。
3. K2 选 GQA single-token decode attention，连接 TPOT 与 KV-cache。
4. K3 P1 选 batched decode attention，直接服务 subagent 并发主线。
5. KV-cache quant fused 是 P2，不应压缩 P0/P1 工期。
6. 4060 本机是 ncu 主阵地；租卡/vGPU 可能无法采完整 counters。
7. 指标必须包含 correctness、speedup、roofline utilization、occupancy、bandwidth、端到端回归收益。
8. “agent-assisted kernel optimization”适合秋招后做 KernelBench 子集实验。
9. 报告中要避免只写“比 PyTorch 快 x 倍”，要解释硬件瓶颈。
10. K3 是三支柱交汇点：agent 并发产生现象 → kernel 解释优化 → 后端回归验证。

| 模型 | 量化 | RK3588 decode tok/s | 内存 | source type/date | PiLoop 判断 |
|---|---:|---:|---:|---|---|
| Qwen3.5-4B | W8A8 | 6.22 | 4576 MB | 官方 repo benchmark，2026-07-03 抓取 | 可测 4B 端侧 agent，但复杂任务需 fallback |

## 12. 结语

PiLoop v3 不应该被写成“堆工具的端侧部署项目”，而应写成一个围绕 agent workload 的系统协同优化项目：公开 trace 与自采 trace 提供真实工作负载，公开 benchmark 与自建端侧 benchmark 提供验证闭环，模型侧 SFT/蒸馏/量化与 agent 侧 Pi runtime 二开互相适配，并发场景把部署推理、agent runtime 与 kernel 优化真正连到一起。秋招前的目标不是把所有 P2 都完成，而是交付一条可复现、可解释、有 before/after、有失败分析、有公开证据的 P0/P1 主线。
