## 0. 执行摘要

### 0.1 本轮最重要的结论

1. **RTX PRO 6000 Blackwell 官方 compute capability 已钉为 12.0（sm_120）**；NVIDIA 官方 CUDA GPU 表把 RTX PRO 6000 Blackwell Server / Workstation / Max-Q 均列在 compute capability 12.0 下，而 B200 是 10.0、B300/GB300 是 10.3。这意味着 RTX PRO 6000 / 6000D 属于 Blackwell，但不能把 B200/B300 的 SM100/103 kernel 直接等同到 SM120。
2. **v3.2.1 patch 的“96GB 优先、6000D 兜底”应采纳**。RTX PRO 6000 96GB 的公开规格与可租价差使它明显优于 84GB 6000D：显存多 12GB、带宽约 1.79TB/s vs 6000D 约 1.1TB/s，推理 serving 与长上下文训练均受益。
3. **DSpark 已进入 vLLM 主线，但不是 vLLM v0.24.0 release 内的稳定功能**。vLLM v0.24.0 发布于 2026-06-29，包含 DeepSeek-V4 SM120 enablement 与 DFlash；DSpark PR #46995 于 2026-07-01 合入。因此执行侧应锁 #46995 之后的 main SHA，或等待下一个 release，而不是写“v0.24.0 原生支持 DSpark”。
4. **Qwen3-8B DSpark 路径最适合作为 R-Max P1 招牌实验**。Qwen3-8B target + `deepseek-ai/dspark_qwen3_8b_block7` draft 的显存账在 RTX PRO 6000 96GB 上很稳，在 6000D 84GB 上也稳；Qwen3-14B 稳但 32k×高并发要降档；Gemma4-12B DSpark 在 vLLM 中仍是独立 open PR，暂列 P1-touch / P2。
5. **NVFP4 量化档已具备官方工具链支撑**。TensorRT-LLM 官方文档列出 FP4、NVFP4 KV Cache、ModelOpt 离线量化流程，并在硬件矩阵中标注 Blackwell(sm120) 支持 NVFP4；HF 上已有多个 Qwen3 / Qwen3.5 / Gemma4 的 NVFP4 checkpoint。
6. **agent / tool-use / terminal benchmark 上的 FP4/NVFP4 行为保真证据仍未找到**。公开资料主要是困惑度、通用 benchmark 或吞吐；“同一 agent trace 在 W8A8 / GGUF-Q4 / NVFP4 三种量化范式下的工具调用成功率与失败模式”仍是 PiLoop 的空白实验位。
7. **Qwen3.5 大 LoRA 的显存数字有官方级来源**。Unsloth 文档给出 Qwen3.5 bf16 LoRA VRAM：0.8B 3GB、2B 5GB、4B 10GB、9B 22GB、27B 56GB，并写明 35B-A3B bf16 LoRA 可在 74GB VRAM 上跑；同时明确“不建议 Qwen3.5 全家族 QLoRA”。
8. **LLM-Pruner Taylor “80GB”本轮未能从公开网页完整复现**。GitHub issue #4 可见用户询问 Taylor pruning 的显存需求，但网页抓取不到维护者答复中的精确 80GB 数字。报告将 v3.2 的“80GB”标为“蓝图/compass 结论，待开工复验”，不再把它作为独立已核实事实。
9. **Loop Engineering 不应作为项目招牌术语**。本轮未找到一个权威、稳定的“Loop Engineering”学术或产业定义；成熟术语应替换为 `agent harness`、`agent runtime`、`agentic workload`、`trace-driven optimization`、`context engineering`、`evaluation harness`。
10. **Terminal-Bench 2.1 状态存在页面冲突**。tbench.ai benchmark 页面仍显示 “Tasks have not been uploaded yet”；但任务书与社区命令指向 Harbor 的 `terminal-bench/terminal-bench-2-1`。执行策略：P0 仍先用 2.0 或开工日 probe 2.1，能拉即切。

# 模块 1 · RTX 6000D / RTX PRO 6000 卡与软件生态

## 1.1 SM 架构版本：RTX PRO 6000 = sm_120；B200/B300 ≠ sm_120

NVIDIA 官方 CUDA GPU compute capability 页面给出：

- **NVIDIA RTX PRO 6000 Blackwell Server Edition / Workstation Edition / Max-Q Workstation Edition：compute capability 12.0**。
- **NVIDIA GB10：12.1**。
- **NVIDIA B200 / GB200：10.0**。
- **NVIDIA B300 / GB300：10.3**。
- Ada RTX 4060 / 4090 等为 **8.9**。

直接结论：

```text
RTX PRO 6000 Blackwell / RTX 6000D: sm_120 family
B200 / GB200: sm_100 family
B300 / GB300: sm_103 family
RTX 4060 / 4090: sm_89 family
```

这会影响 kernel 兼容性：

1. **Blackwell 不等于同一 kernel 路径**。SM100/103 数据中心 Blackwell 与 SM120 工作站/消费级 Blackwell 在可用低级指令、kernel tuning、TMA/TMEM 路径上不应默认等价。
2. vLLM PR #41834 明确说其 SM12x enablement 是给 RTX PRO 6000 Workstation、RTX 5090-class SM120、GB10/SM121 用户准备的 fallback/tuning stack，并提到这些用户不能使用 SM100-only TMEM / `tcgen05` kernels。
3. 因此，PiLoop 文档里应写：**“R-Max 是 Blackwell FP4/NVFP4 原生实验位，但 DSpark / DeepGEMM / FlashInfer / TensorRT-LLM 的具体 kernel 需确认是否走 SM120 可用路径。”**

## 1.2 RTX PRO 6000 96GB vs RTX 6000D 84GB

| 项 | RTX PRO 6000 Blackwell 96GB | RTX 6000D 84GB |
|---|---:|---:|
| 市场定位 | 全球版 RTX PRO 6000 | 中国出口合规裁剪版 |
| CUDA cores | 24,064 | 19,968（蓝图给定；公开第三方也称约少 20%） |
| 显存 | 96GB GDDR7 | 84GB GDDR7 |
| 位宽 | 512-bit | 448-bit |
| 带宽 | 约 1.79TB/s | 约 1.1TB/s |
| 功耗 | 600W | 600W（蓝图给定） |
| NVLink | 无 | 无 |
| compute capability | sm_120 | 预期 sm_120；NVIDIA 官方 CC 表未单独列 “6000D”，按同族推断 |
| R-Max 角色 | 默认主场 | 库存兜底 |

**判断**：v3.2.1 patch 是正确的。¥5.98/h vs ¥5.18/h 的差价极小，但 96GB 多 12GB 显存、带宽高约 45% 左右；对于 DSpark serving、NVFP4 serving、TensorRT-LLM demo、35B-A3B LoRA、长上下文 SFT，96GB 的冗余明显更值钱。

## 2.3 显存账：Qwen3-8B/14B、Gemma4-12B target + DSpark draft

> 说明：以下是工程估算，用于实验规划。实际显存会受 vLLM page size、KV dtype、CUDA graph capture、allocator fragmentation、activation scratch、vocab lm_head、trust_remote_code 等影响，开工需实测。

### 权重估算

| 配置 | target BF16 权重 | draft BF16 权重 | 权重合计 | 84GB | 96GB |
|---|---:|---:|---:|---|---|
| Qwen3-8B + dspark_qwen3_8b_block7 (~2.37B) | ~16GB | ~4.7GB | ~20.7GB | 稳 | 很稳 |
| Qwen3-14B + dspark_qwen3_14b_block7 (~3.42B) | ~28GB | ~6.8GB | ~34.8GB | 稳 | 很稳 |
| Gemma4-12B + dspark_gemma4_12b_block7 (~3.43B) | ~24GB | ~6.9GB | ~30.9GB | 稳，但 vLLM PR 未合 | 很稳 |

### KV 粗估

按 Qwen-style GQA 粗估：

```text
KV bytes ≈ tokens_total × layers × 2(K,V) × kv_hidden × bytes_per_elem
```

以 BF16 KV 粗估，Qwen3-8B 在 `8k context × concurrency 16` 下 KV 大约十几 GB 级；`32k × 16` 会接近或超过 60GB。加入权重、graph、runtime overhead 后：

| 配置 | 8k × batch 16 | 32k × batch 16 |
|---|---|---|
| Qwen3-8B DSpark | 84GB 可行，96GB 很稳 | 84GB 高风险；96GB 也需 FP8/NVFP4 KV 或降并发 |
| Qwen3-14B DSpark | 84GB 可行但需监控；96GB 稳 | 不建议；降并发或用 FP8 KV |
| Gemma4-12B DSpark | 合入前不做主图 | 合入前不做主图 |

### 推荐实验矩阵

| 阶段 | 模型 | 上下文 | 并发 | 目的 |
|---|---|---:|---:|---|
| P1-a | Qwen3-8B + DSpark | 8k | 1/2/4/8/16 | 招牌曲线：DSpark × concurrency |
| P1-b | Qwen3-8B + DSpark | 16k | 1/2/4/8 | 看长上下文收益与 prefill/TTFT |
| P1-c | Qwen3-14B + DSpark | 8k | 1/2/4/8 | 模型规模扩展 |
| P1-touch | Gemma4-12B + DSpark | 8k | 1/2/4 | 等 #47216 或 fork |
| 对照 | Qwen3-8B baseline | 8k | 1/2/4/8/16 | 非投机 baseline |
| 对照 | Qwen3-8B standard draft | 8k | 1/2/4/8/16 | 普通 draft speculative decoding |
| 对照 | Qwen3.6 MTP | 8k | 1/2/4/8 | MTP vs DSpark vs standard draft |

## 对 PiLoop v3.2 的直接结论（≤10条）

1. DSpark 已从“待合入”升级为 “vLLM main 已合入”，但 release 边界必须写清。
2. 执行侧应锁 **post-#46995 + #47093** 的 vLLM main SHA。
3. 第一张招牌图用 **Qwen3-8B + dspark_qwen3_8b_block7**，不要用 DeepSeek-V4 或 Gemma4 首发。
4. Gemma4-12B DSpark 等 #47216 合入后再进入主矩阵。
5. 96GB R-Max 允许 8k×16 DSpark 并发 sweep 更从容，84GB 也可跑但更容易受 KV/graph overhead 限制。
6. 32k×高并发不是 P1；先做 8k / 16k。
7. confidence scheduling 不应写成已可用；当前 main 重点是 fixed-γ DSpark。
8. prefix cache 与 DSpark 没有发现明确冲突，但必须实测。

# 模块 3 · NVFP4 量化档

## 3.1 TensorRT-LLM / ModelOpt 支持情况

TensorRT-LLM 官方 Quantization 页面明确列出：

- FP4
- FP8 Per Tensor
- FP8 Block Scaling
- FP8 Rowwise
- FP8 KV Cache
- **NVFP4 KV Cache**
- W4A16 / W4A8 GPTQ / AWQ

并说明：

1. TensorRT-LLM 可直接运行由 **NVIDIA Model Optimizer** 生成的 pre-quantized models。
2. 如果没有现成模型，可用 ModelOpt 离线量化。
3. 启用 NVFP4 KV Cache 需要先用 ModelOpt 离线量化，然后使用 `KvCacheConfig(dtype='nvfp4')`。
4. 当前文档指出：启用 NVFP4 KV Cache 时，TRT-LLM 只支持 FP8 weight/activation quantization，因此命令仍要求 `--quant fp8 --kv_cache_quant nvfp4`。
5. 硬件矩阵中 **Blackwell(sm120)** 对 NVFP4 / MXFP4 / FP8 / FP8 KV Cache 等给出支持。

示例命令：

```bash
git clone https://github.com/NVIDIA/Model-Optimizer.git
cd Model-Optimizer/examples/llm_ptq
scripts/huggingface_example.sh --model <huggingface_model_card> --quant fp8 --kv_cache_quant nvfp4
```

TensorRT-LLM build CLI 中也出现：

```bash
--gemm_plugin {auto,float16,float32,bfloat16,int32,fp8,nvfp4,disable}
--fuse_fp4_quant {enable,disable}
```

这说明 v3.2 的 “TensorRT-LLM 真机 demo” 有实质内容，不是只贴 JD 关键词。

## 3.3 精度证据

### 已有证据

1. NVFP4 / FP4 的公开论文和工具链主要报告：
   - 困惑度 / downstream benchmark。
   - Qwen / LLaMA 类模型的 accuracy retention。
   - RTX 5090 / RTX PRO 6000 上的吞吐提升。
2. ARCQuant 论文报告在 LLaMA 与 Qwen 上达到接近全精度 baseline，并在 RTX 5090 / RTX PRO 6000 上获得 up to 3× over FP16 的 practical benefit。
3. SOAR / MixFP4 / Quartet II / TetraJet-v2 等工作说明 NVFP4 正在成为 Blackwell 低精度推理/训练的重要方向。

### 未找到

```text

```

这保留了 PiLoop 的核心实验价值：

> “FP4 不只是通用精度是否掉点，而是工具调用格式、修复循环、长上下文压缩、失败恢复行为是否保真。”

## 3.4 三种量化格式的口径差异

| 格式 | 典型位置 | 数值机制 | 优点 | 不可直接比较点 |
|---|---|---|---|---|
| RKLLM W8A8 | RK3588 NPU | INT8 weight + INT8 activation / RKLLM toolkit | NPU 原生、端侧部署必需 | 8-bit 但受 NPU runtime、算子支持、校准集强影响 |
| GGUF Q4_K_M | llama.cpp / PC | group-wise mixed quant，通常 weight-only | 生态成熟、CPU/GPU/offload 友好 | 不是 activation FP4；kernel 与 KV cache 可独立配置 |
| NVFP4 | Blackwell / ModelOpt / TRT-LLM / vLLM | FP4 E2M1 + scale，常伴随 FP8/NVFP4 KV | Blackwell Tensor Core 原生、serving throughput 强 | 低 bit 不等于简单 4-bit；scale hierarchy 与 activation quant 机制完全不同 |

**报告声明建议**：

```text
本项目比较的是三种部署量化范式在同一 agent workload 下的系统表现，
不是比较三个“4-bit/8-bit 数字”的纯压缩率。
```

## 对 PiLoop v3.2 的直接结论（≤10条）

1. NVFP4 档应保留为 R-Max P1，工具链证据足够。
2. 先用现成 `nvidia/*-NVFP4` 或 `RedHatAI/*-NVFP4` checkpoint 做 serving，再决定是否自校准。
3. TensorRT-LLM demo 不应只跑 BF16，应至少跑 FP8+NVFP4 KV 或 NVFP4 model path。
4. Blackwell(sm120) 在 TRT-LLM 硬件矩阵中明确有 NVFP4 支持。
5. ModelOpt 离线量化流程可作为文档与实验脚本来源。
6. agent-task FP4 保真没有公开证据，是 PiLoop 的差异化点。
7. NVFP4 vs GGUF-Q4 vs W8A8 的报告必须强调“机制不可直接互比”。
8. RTX PRO 6000 96GB 比 6000D 更适合作为 NVFP4 serving 主卡，因为带宽差显著。
9. FP4 精度报告可引用通用 benchmark，但不能替代 agent benchmark。
10. P1 输出应是一张“量化范式 × agent 成功率/失败模式/吞吐”的矩阵，而不只是吞吐图。

## 5.2 原有概念谱系

### ReAct

ReAct 论文（2022）已经把 reasoning traces 与 task-specific actions 交织在一起：reasoning 用于追踪、更新 action plan，actions 用于与外部环境交互。现代 coding/terminal agent 的 “think-act-observe loop” 并不是新概念。

### PagedAttention / vLLM

vLLM / PagedAttention（2023）说明 serving 系统层已经把 KV cache、continuous batching、memory management 当作核心优化对象。agent runtime 的长上下文/多请求/多工具调用只是更复杂的 workload，不是独立新学科。

### Agent harness / evaluation harness

Terminal-Bench / SWE-agent / SWE-bench 系生态中，常用词是：

- harness
- evaluation harness
- agent runtime
- task environment
- verifier / oracle
- trace / trajectory

### Context Engineering

“context engineering” 已有 2026 年论文把它定义为设计、结构化和管理 agent 决策所需的信息环境；同时维基/社区资料追溯到 2025 年 Tobi Luetke 等行业使用。这个词仍较新，但比 “Loop Engineering” 更可解释、更贴实际工作。

## 5.3 成熟术语对照表

| 不建议用 | 替换词 | 含义 | 适用位置 |
|---|---|---|---|
