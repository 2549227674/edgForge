## 模块 1 · 租用 GPU 训练场地具体配置

### 1.1 显存-上下文预算（bf16 LoRA / QLoRA / 全参）
- **Unsloth 官方 VRAM 表（官方文档 unsloth.ai/docs，2026）**：QLoRA(4bit) 相比全参省约 75% 显存；LoRA(16bit) 比 QLoRA 多约 4× 显存。3B 模型 QLoRA 8GB 可训（社区教程，Llama-3.2-3B）。
- **Gemma 4 家族（Unsloth 官方文档 Gemma-4/train，2026）**：E2B LoRA 需 8–10GB；**E4B LoRA 需 17GB**；31B QLoRA 需 22GB；26B-A4B LoRA 需 >40GB。官方建议"训 E4B QLoRA 优于 E2B LoRA"（量化精度差异极小）。
- **长上下文 RL 参考（Unsloth 官方博客 Memory-Efficient RL，1×H100 80GB）**：Llama-3.1-8B QLoRA 4bit 借 Unsloth Standby 可达 **47,500 上下文**；Qwen3-32B LoRA 16bit **6,144 上下文**（1×H100 80GB）。
- **对 48G 单卡的推断**：4B bf16 LoRA @ 8k×batch1 可行；8B QLoRA @ 8k 可行；8B bf16 LoRA @ 8k 偏紧需梯度检查点（`use_gradient_checkpointing="unsloth"`）。具体 max_seq×batch 精确表官方未给 → **无可靠精确表，仅规划性估计**。

### 1.2 "Qwen3.5+ 不适合 QLoRA" 溯源
- **确认为 Unsloth 官方声明**（Unsloth 官方文档 Qwen3.5 Fine-tuning Guide）：原文 *"It is not recommended to do QLoRA (4-bit) training on the Qwen3.5 models, no matter MoE or dense, due to higher than normal quantization differences."*
- **适用范围**：整个 Qwen3.5 家族（MoE 与 dense 都不推荐）。
- **官方推荐替代**：bf16 setups（LoRA 或全参）。MoE 场景明确 *"MoE QLoRA 4-bit is not recommended due to BitsandBytes limitations"*；dense 27B 用 16bit LoRA 没问题。

### 1.3 Gemma4-E2B/E4B 工具链成熟度
- **Unsloth/TRL/PEFT 支持**：Unsloth 官方已支持 Gemma4 全家族训练与 Unsloth Studio。
- **已知关键坑（Unsloth 官方文档，实测级说明）**：Gemma-4 E2B/E4B 跨层共享 KV（`num_kv_shared_layers=20` 与 18）。当 `use_cache=False`（QLoRA 教程默认，且 `gradient_checkpointing=True` 会强制）时，KV-shared 层 fall through 到本地重算 K/V，**logits 变垃圾、loss 发散**。这是 chat-template/训练配置的硬坑。另 fp16(T4) 上 `attention_invalid_logits_value=-1e9` 溢出 fp16 上限 65504 → 需 bf16。
- MatFormer/PLE 结构特性：官方文档提到 E2B/E4B 为 VLM 架构、中心化 LM head（centroid），mlx-lm 因 VLM 权重布局无法直接加载（社区博客 hiesch.eu 实测）。

### 1.4 CPU+GPU 混合训练（16GB RAM + 8GB VRAM）真实收益
- ZeRO-Offload/FSDP cpu_offload/Unsloth offload 在此配置解锁的空间有限：**无针对 16GB RAM + 8GB VRAM 的公开实测速度惩罚数据 → 无可靠来源**。
- 定性判断：16GB 系统内存是硬约束，offload 4B bf16 全参不现实；更长上下文 8B QLoRA 靠 offload 理论可行但速度惩罚大。此配置更适合"冒烟测试"，与 v3.1 "本地 4060 冒烟 / 租用为主训练"的三层定位一致。

### 1.5 AutoDL 实务
- **可租卡型与价格（AutoDL 官网 autodl.com，2026，官方定价页）**：L20/48GB ¥3.68/时；RTX 5090/32GB ¥2.88/时；A800-80GB ¥4.98/时；RTX 4090/24GB ¥1.98/时；PRO 6000/96GB ¥5.98/时；H20/96GB ¥7.58/时。**未见"4090 48G"标准卡型**（4090 官方为 24GB）；48G 档主要是 L20。会员 95 折。
- **镜像/驱动约束（AutoDL 官方帮助文档 autodl.com/docs/gpu）**：Ampere 及以上（3090/4090/A100/A800/L20/H20/H800）需 CUDA 11.1+。内存按 GPU 数成比例分配，超内存上限进程会被 Kill。数据放 `/root/autodl-tmp/`（大容量高速），另有 20GB 免费存储。按秒计费，最低 0.01 元。
- **v1 报告提及的 CUDA 13.2 vs Qwen3.6 乱码冲突**：**已由 Unsloth 官方证实**（Unsloth Qwen3.6 文档）：*"Do NOT use CUDA 13.2 as you may get gibberish outputs. Use below CUDA 13.2 or CUDA 13.3."* → v1 结论得到一手来源支持。
- **一轮 4B×8k×3epoch SFT 成本估算**：L20 48G @ ¥3.68/时，若单轮约 6–10 小时 → 约 ¥22–37/轮。**此为规划性估计，无精确实测先例 → 标注估计**。

### 1.6 蒸馏在线教师配置
- 48G 上"教师 27B/31B Q4 推理 + 学生 4B 训练"同卡：**无直接公开先例 → 无可靠来源**。
- 反向证据：Gemma4-31B Q4（UD-Q4_K_XL）+ 训练态 4B 权重/优化器/激活，48G 极其紧张；NVIDIA Minitron/NeMo 官方蒸馏参考实现均用**单节点 8 卡 TP**（NeMo 官方教程 tutorials/llm/qwen/pruning-distillation）。→ 强烈建议两段式（离线生成 logits/文本，再训练），而非同卡在线教师。

### 对 PiLoop v3.1 的直接结论（≤10 条）
1. "Qwen3.5+ 不宜 QLoRA" 是 **Unsloth 官方**立场，覆盖整个 3.5 家族；v3.1 底座若含 Qwen3.5-2B/4B，训练走 **bf16 LoRA**。
2. Gemma4-E2B/E4B 训练首坑是 **KV 共享层 × use_cache=False → loss 发散**；必须验证 chat template 与 cache 配置，勿盲用通用 QLoRA 模板。
3. 48G 单卡足以承载 4B bf16 LoRA @ 8k×batch1 与 8B QLoRA @ 8k 的 agent-trace SFT（配 gradient_checkpointing="unsloth"）。
4. E4B 训练官方建议 **QLoRA(17GB) 或更优**，与 v3.1 "E2B 为主"不冲突，训练侧可优先 E4B 再蒸/转 E2B。
5. AutoDL 48G 档主力是 **L20 @ ¥3.68/时**，非 4090-48G（官方无此卡）；预算测算按 L20。
6. **CUDA 13.2 乱码坑得到 Unsloth 官方确认**（用 <13.2 或 13.3）；v1 结论成立。
7. 一轮 4B×8k×3ep SFT 估 ¥22–37（L20），属可承受"主训练场地"成本。
8. 在线教师同卡蒸馏无先例且显存紧 → **两段式离线蒸馏**为稳妥路径。
9. 16GB+8GB 混合训练无实测收益数据，定位应为**冒烟/验证**而非主训练。
10. 三层训练矩阵（本地冒烟/租用主训/边端仅推理证据）与所有一手证据自洽，予以保留。

## 模块 2 · NAS-lite 双路线可行性

### 2.1 路线 A（真 NAS）
- **OFA（github.com/mit-han-lab/once-for-all）**：**基本停止维护**。仅 v0.1（2020-06-16），依赖陈旧（PyTorch 1.4、Horovod）；Issue #94（2025-11-19）报告教程在现代 Colab 因 PyYAML API 变更报错。预训练 supernet 仍可下载作参考。**训练成本一手数据**：Cai et al. *Once-for-All*（ICLR 2020, arXiv:1908.09791）原文报告 OFA supernet 在 ImageNet 上训练约需 **1.5 天 × 32× V100（≈1,200 GPU-hr）** —— 绝非单卡可复现。
- **ProxylessNAS（github.com/mit-han-lab/proxylessnas, arXiv:1812.00332）**：归档状态，README 明确 OFA 为其下一代。
- **MIT 6.5940（efficientml.ai / hanlab.mit.edu/courses/2024-fall-65940）**：末次开课 **2024 秋**（2025 秋因休假停开），讲义/视频公开。NAS 内容为经典 CNN/vision NAS + 硬件感知 NAS + zero-shot NAS，**概念可迁移但非 LLM-drafter 现成工具**。Lab3 具体讲义内容无法直接打开验证 → 部分标注不确定。
- **单卡 48G 一轮搜索成本（综合量级估计，非单一一手来源）**：给定预训练 supernet 的搜索/特化步骤便宜（<1 至数 GPU-hr，几美元）；从零训小型 vision supernet 约数十至上百 GPU-hr；<300M draft 模型一轮轻搜+短蒸约数十 GPU-hr。**均为量级估计**。

### 2.2 路线 B（Minitron 式剪枝搜索）
- **NVIDIA Model-Optimizer（github.com/NVIDIA/Model-Optimizer）**：**最活跃**。2026 活动含 [2026/05/13] Puzzletron（异构剪枝+NAS）、[2026/05/27] Nemotron-3-Nano 剪枝+两段蒸馏（官方声称 2.6× vLLM 吞吐）。三种剪枝模式：mcore_minitron / FastNAS / GradNAS。**Qwen3-8B 的 NeMo 剪枝-蒸馏教程存在**，参考实现用单节点 8 卡 TP。
- **LLM-Pruner（github.com/horseee/LLM-Pruner, NeurIPS 2023, arXiv:2305.11627）**：维护中，支持 Llama-3/3.1 等。**显存修正（重要）**：官方 Issue #18 实测 **Taylor pruner 反向传播需约 80G 显存**（作者建议用 CPU 估计重要度），**并非早前流传的 "20GB/单张 3090"**——该说法出处存疑，应弃用。低显存替代：**SlimGPT**（arXiv:2412.18110，7B@20% 仅约 7GB / 18 分钟）、**Olica**（github BetterTMrR/LLM-Olica，单张 16GB GPU 数分钟剪 LLaMA-7B）。→ Qwen3-1.7B/4B 单卡剪枝可行，但须选低显存方法或 CPU 估计重要度。
- **Sheared-LLaMA（github.com/princeton-nlp/LLM-Shearing, ICLR 2024, arXiv:2310.06694）**：可用参考实现。**成本一手数据**：剪枝后仅**续训 50B tokens（约为从零训最强 3B 模型预算的 5%）**；对照从零训 LLaMA2-7B 约需 184,320 A100 GPU-hr。剪掩码步轻，但续训 token 预算仍非单卡经济。
- **硬件在环 NAS 公开先例存在**：
  - **Puzzle（Bercovich et al., NVIDIA, arXiv:2411.19146, ICML 2025）**：蒸馏式 NAS，逐块搜索 + MIP 硬件约束，产出 Llama-3.1-Nemotron-51B。**成本一手数据**：原文 *"required just 45B training tokens, compared to over 15T tokens used for the 70B model it was derived from"*（论文声称 2.17× 吞吐、单 H100、保留 98.4% 精度）。
  - **CREST（arXiv:2606.15004, 2026, github.com/nesl/crest）**：编译候选→烧录真机→测真实延迟/能耗→反馈搜索循环，**正是"剪枝候选上板测延迟作搜索反馈"的一手先例**。
  - **HELP（Lee, Lee, Chong, Hwang, NeurIPS 2021 Spotlight, arXiv:2106.08630）**：延迟预测器替代实测，*"estimate the latency…on an unseen device with a few samples"*；"最多 2140× 降本"数字未在一手来源核到 → **待核**。

### 2.3 NAS × 投机解码交叉（tiny draft 结构搜索）
- **有明确研究先例**：
  - **STAR（OpenReview id pMdKnxkFRw, 2025）**：**最直接命中**，用 NAS + target-aware supernet 训练自动搜索 draft 模型架构（含目标硬件平台），VLM 上论文声称最高 3.8× 加速。
  - **Decoding Speculative Decoding（Yan, Agarwal, Venkataraman, UW-Madison, arXiv:2402.01528, 2024–2025）**：draft 模型**延迟**而非精度主导吞吐；深度是瓶颈 → **宽而浅** drafter 更优；用 Sheared-LLaMA 剪枝生成候选 drafter 配置（如 NoFT-Wide-796M/543M/290M）。论文声称重设计 drafter 吞吐 +111%、KV -37%。
  - **SDSL（arXiv:2603.11053, 2026）**：投机解码吞吐 scaling law，drafter 深宽设计。
  - **vocab 维度搜索**：无专门论文 → **无可靠来源**。

### 对 PiLoop v3.1 的直接结论（≤10 条）
1. 路线 A（OFA/ProxylessNAS）在 2026 **已停维、依赖腐化**，且 OFA supernet 训练约 1,200 GPU-hr（32×V100），只宜作概念参考，不建议投产复现。
2. 路线 B（Minitron 式）是 NAS-lite 的**现实可落地路径**，首选 NVIDIA Model-Optimizer（活跃）+ 低显存剪枝法（SlimGPT/Olica）。
3. **LLM-Pruner 的 Taylor pruner 需约 80G 显存**（非 20GB/3090），单卡剪 Qwen3-1.7B/4B 须选低显存方法或 CPU 估重要度。
4. 完整 Minitron/Sheared 质量恢复需大 token 预算（Sheared 续训 50B tokens、Puzzle 45B tokens）、非单卡经济 → v3.1 只做"轻剪+短蒸候选"以控成本。
5. **硬件在环 NAS 有一手先例（CREST）**，"剪枝候选上 RK3588 测延迟作搜索反馈"在方法学上成立，可作为 PiLoop 双向协同亮点。
6. **NAS × 投机解码交叉存在真实先例（STAR + Yan et al.）**，是叉乘的学术支撑，值得作 Direction 深挖点。
7. drafter 设计应偏**宽而浅**（Yan et al. 一手结论），直接指导 v3.1 draft 模型结构。
8. Puzzle 提供逐块蒸馏式 NAS 机器，可迁移到 drafter 搜索。
9. MIT 6.5940 Lab3 可作教学参考但非现成工具，迁移成本需自估。
10. 单卡一轮搜索成本为量级估计（数十 GPU-hr），预算规划按上限留冗余；HELP 类延迟预测器可替代真机实测以降本（降本倍数待核）。

## 模块 3 · RK3588 五通道并发实测细节

### 3.1 RKLLama multiload
- **NotPunchnox/rkllama（GitHub 仓库 README，2026）**：由 Daniel Ferreira 贡献 "multiload RKLLM models in memory"。语义：**多个不同模型可同时驻留内存并行执行（stream 模式并行，非 stream 走 FIFO）**；内存不足时卸载最旧模型。**注意：这是"不同模型"间并行，而非同一模型多实例**。
- **runtime 版本确认**：主分支 README 显示 **rkllm-runtime V1.3.0**、rknn-runtime V2.3.2（旧版 README 为 1.2.3）。
- **自动 Prompt Cache**：每个 chat session 自动存缓存，模型卸载后仍可快速恢复；默认保留 7 天（可配置）。

### 3.2 num_npu_core 多实例
- 转换时设 `num_npu_core=1/2` 后，**同时运行两个各绑不同核的 RKLLM 实例**：**无直接社区实测（吞吐/内存/驱动错误）→ 无可靠来源**。
- 佐证：RK3588 NPU 为**3 独立核**（Firefly 厂商文档 wiki.t-firefly.com），视觉侧 RKNN 已有"每核分配 5-6 路流"的多核分配实践（IEEKER 工业视觉案例），可类比但**LLM 侧多实例绑核无一手实测**。
- 转换约束：RK3588 LLM 仅支持 **W8A8**（不支持 W4A16；W4A16 是 RK3576），核数 RK3588=3（社区实测 tinycomputers.io，TinyLlama 1.1B 约 10-15 tok/s）。

### 3.3 MLC-LLM on Mali G610
- **官方 Orange Pi 路径（MLC 官方博客 blog.mlc.ai，2024-04）**：Llama3-8B 约 **2 tok/s**、RedPajama-3B 约 5 tok/s、Llama-2-13B 约 1.5 tok/s（Orange Pi 5, Mali G610, OpenCL）。**2026 是否仍维护 Qwen3/Gemma4 新模型编译支持：无 2026 一手实测 → 无可靠来源**。
- **驱动坑（社区 GitHub 指南 serialscriptr/Orange-PI-5-Pro-MLC-LLM）**：需 libmali-valhall-g610 + mali_csffw.bin 固件 + mesa-opencl-icd；OpenCL 默认选到通用 ARM 设备而非 Mali，需手动指定 device；曾多次硬锁内核。
- **量化格式差异**：MLC 用 **q4f16_1**，与 v3.1 的 GGUF/W8A8 基线不同，跨引擎对比需注意口径不一致。

### 3.4 llama.cpp on RK3588 CPU 并发
- **A76×4+A55×4 上 --parallel 2/4 实测、big.LITTLE taskset 影响、1.7B/4B Q4 CPU 单/并发数字**：**无 RK3588 专项一手实测 → 无可靠来源**。
- 可迁移的通用 llama.cpp 经验（社区 carteakey.dev）：Intel 混合核 E-core 拖累 TG 20-30%，应 taskset 绑 P-core；ARM big.LITTLE 类比 → 应绑 A76 大核。

### 3.5 rk-llama.cpp（invisiofficial）
- GGUF-on-NPU fork 成熟度、支持模型、vs RKLLM 速度：**无可靠一手来源**（v3.1 已将其定位为"experimental 第五通道"，与证据现状一致）。

### 3.6 RKLLM prompt cache API
- **v1.3.0 cache save/preload 接口**：rkllama 层面已暴露自动 prompt cache（README 确认，见 3.1），多轮 agent 场景切换会话可快速响应（README 明确提到在 Openclaw 大上下文会话 + 其他 agent/工具间切换不影响性能）。底层 `rkllm_load_prompt_cache` 类 C API 的精确签名 → 未获一手文档 → **部分无可靠来源**；但"持久多 agent KV"想法在 rkllama 应用层有可迁移实现（跨会话缓存复用、卸载后恢复）。

### 对 PiLoop v3.1 的直接结论（≤10 条）
1. RKLLama multiload 确认为 **rkllm-runtime v1.3.0**，语义是**不同模型并行驻留**（stream 并行/非 stream FIFO），非同模型多实例——修正对"多实例"的期待。
2. `num_npu_core` 绑核双实例**无一手实测**，属五通道中风险最高项，需自行上板验证再纳入方案。
3. RK3588 LLM 仅 **W8A8**，与 v3.1 "Gemma4-E2B W8A8 自转"一致，予以确认。
4. MLC/Mali 路径**量化格式 q4f16_1** 与 GGUF/W8A8 口径不同，跨引擎对比须显式声明基线差异。
5. MLC 官方 2024 数据（8B~2 tok/s）偏低，2026 对 Qwen3/Gemma4 支持无一手证据 → Mali 作"第三引擎"应先做可行性验证。
6. CPU 并发（--parallel）无 RK3588 专项数据，须自测；通用经验建议 taskset 绑 A76 大核。
7. rk-llama.cpp 成熟度无可靠来源，维持"实验第五通道"定位。
8. RKLLama **自动 prompt cache**（7 天保留、跨会话恢复）可直接支撑"持久多 agent KV"构想。
9. 视觉侧 RKNN "每核分流"实践可作 NPU 多核并发的类比参考，但 LLM 侧需独立验证。
10. 五通道中，multiload（不同模型）与 prompt cache 证据最实；绑核多实例、Mali、rk-llama.cpp 三项证据最弱，优先级应据此排序。

## 模块 4 · PC 混合推理 × 并发交互（补 v1 模块 3 缺口）

### 4.1 -ngl（部分 offload）× --parallel 交互
- **8B/12B Q4 在 "8GB VRAM + 16GB RAM" offload×并发 1/2/4 的公开数据**：**无此精确配置一手实测 → 无可靠来源**。
- 机制层面（社区指南 carteakey.dev / DocShotgun HF 博客）：CPU 段权重在并发下由 prompt processing 的 op-offload（默认 batch≥32 触发，将 CPU 权重拷到 GPU 批处理）分摊；`-ub`(physical batch, 默认512) / `-b`(logical, 默认2048) 在 CPU+GPU 混合大模型下默认偏小，建议调大以提 prefill。

### 4.2 --n-cpu-moe
- **机制（社区实测/指南）**：将 MoE 专家权重驻留 CPU RAM，dense/attention 层留 GPU；每 decode step 从 RAM 拷热专家到 GPU 用完即弃。`--n-cpu-moe` 从最高编号层开始计数。
- **实测数据**：RTX 3060 12GB 上 Qwen3.6-35B-A3B（MoE）用 `--n-cpu-moe 32` 起步可跑（社区 knightli.com，2026-05-26，build b9297）；Qwen3.5-35B-A3B Q4_K_M + `--n-cpu-moe 99` + `-ub 2048` 在某配置约 **350-400 tok/s prefill、15 tok/s 生成**（社区 GitHub Discussion #21112，含 102K 上下文）。
- **MoE-hybrid vs dense-hybrid 差异**：MoE 每 token 只激活部分专家，offload 后每 token 仅拷热专家（top-k），故 MoE-hybrid 远比 dense-hybrid 划算——dense 每 token 读全部激活权重，spill 到 RAM 即大幅掉速。

### 4.3 KV-cache 放置
- **--cache-type-k/v 量化 KV**：llama.cpp 支持 KV 量化（如 q8_0/q4_0），社区实测常与混合 offload 组合（Discussion #21112 用 `-ctk q8_0 -ctv q8_0`）。KV 是否可独立于权重放置：llama.cpp 默认 KV 随层放置；细粒度独立放置无专门一手文档 → **部分无可靠来源**。

### 4.4 16GB RAM 共驻预算
- OS + Pi(Node) + llama-server + CPU 层权重 + page cache 的实测占用先例、swap 触发后的性能悬崖数据：**无此精确共驻场景一手实测 → 无可靠来源**。
- 通用警告（社区指南 carteakey.dev）：`--n-cpu-moe` 过高会试图把 ~全部专家载入 RAM，60GB 模型在 64GB 机上会硬崩；建议 `--no-mmap` 避免 decode 期页错误抖动，并用 llama-fit-params 先探安全值。

### 4.5 vLLM --cpu-offload-gb / swap-space
- 2026 状态、是否值得作 PC 层对比：**无 2026 专项一手评测 → 无可靠来源**。定性：vLLM 面向吞吐/服务端，PC 单用户 8GB VRAM 场景 llama.cpp 更成熟，**建议 PC 层以 llama.cpp 为主，vLLM 暂排除或仅作参考**。

### 对 PiLoop v3.1 的直接结论（≤10 条）
1. PC 层"CPU 16GB + GPU 4060 8GB 混合"下，**MoE-hybrid（--n-cpu-moe）远比 dense-hybrid 划算**，v3.1 若跑 MoE 类应优先此路径。
2. `--n-cpu-moe` 实测：35B-A3B 在 12GB 卡可跑（社区 b9297），但 16GB RAM 是硬约束，需 llama-fit-params 探安全值防硬崩。
3. `-ub/-b` 默认偏小，混合模式下应调大 `-ub`(如 2048) 显著提 prefill。
4. 8GB VRAM+16GB RAM 精确 offload×并发数据缺失，须自测建立本地基线。
5. KV 量化（`-ctk/-ctv q8_0`）可与混合 offload 组合省显存，但独立放置无一手文档。
6. `--no-mmap` 推荐用于持久 server，避免 decode 页错误抖动。
7. 16GB RAM 共驻（含 Pi/Node）无实测，swap 悬崖须实测标定，是 PC 层最大不确定性。
8. vLLM PC 层**暂排除**，以 llama.cpp 为主引擎。
9. dense 8B/12B Q4 在 8GB 卡必然大量 offload 到 16GB RAM，spill 掉速明显，量化档要偏保守。
10. v3.1 "PC = CPU16GB+GPU4060 8GB 混合推理平台"重定义与证据一致，予以保留。

## 模块 5 · DSpark GGUF 语义 & 租用 GPU 路径验证

### 5.1 ankk98/dspark-gemma4-12b-block7-Q4_0-GGUF 真实语义
- **HF 一手核实（HF connector，模型卡）**：作者 ankk98，**license MIT**，库 gguf，下载 1.5K/likes 3，更新 2026-06-30。tags：`speculative-decoding` `dspark` `gemma4`，**base_model: deepseek-ai/dspark_gemma4_12b_block7**（量化自该 base）。
- **运行机制判定**：DSpark 是 DeepSeek 的**半自回归投机解码框架**（semi-autoregressive drafter，用非因果滑窗注意力并行提议多 token 再一次验证；vLLM 官方 X @vllm_project 与 vllm-ascend RFC #11163 确认语义）。**block7 = block size 7**。此 GGUF 是 block-diffusion/半自回归 draft 语义，**并非标准 draft-model spec decode**。
- **关键结论**：stock llama.cpp **不原生支持** DSpark/gemma4 半自回归 block 验证语义（类比 Gemma4 assistant drafter：`Gemma4AssistantForCausalLM` 未注册进 convert_hf_to_gguf.py，需 fork，如 AtomicBot-ai/atomic-llama-cpp-turboquant 的 `--mtp-head`/`gemma4_assistant` 支持）。DSpark 官方一等实现在 **vLLM**（见 5.2）。→ 该 GGUF 更可能需专门 fork 或仅作权重容器，**stock llama.cpp 加载运行 DSpark 语义无一手证据**。

### 5.2 rafaelcaricio vLLM fork & 上游 PR 状态
- **DSpark 已合入 vLLM 主线（vLLM 官方 X，2026）**：*"@deepseek_ai's DSpark speculative decoding now runs natively in vLLM"*；用法 `--speculative-config '{"method":"dspark","num_speculative_tokens":7,...}'`；DeepSeek-V4-Pro-DSpark 在 8×B300 官方声称 ~250 tok/s@bs1、平均接受长 ~5、比 MTP 高 12-42% 接受率。
- **Issue #46910/#46931**：#46931 [Performance]: DSpark 被 **Closed as duplicate of #46910**（vLLM 官方 issue tracker）。
- **rafaelcaricio fork（PR rafaelcaricio/spark_vllm_docker#1 + rafaelcaricio/vllm#1）**：面向 DGX Spark/GB10；实测 DSpark-5 约 **63.4 tok/s = 1.59× MTP-1 单流**（该 fork PR 实测），但该 port 存在 τ 缺陷（tau ~2.5 vs 应 ~4.4）。暴露 τ histogram/SPS 曲线。安装需同时 clone docker stack + vllm-side PR。
- **注意**：DSpark/DFlash 的 NVFP4 路径为 **Blackwell 独占**（AEON-7/vllm-dflash README：H100/A100/L40/RTX40 及一切 pre-Blackwell **不支持**）。→ 对租用 4090/A100(Ada/Ampere) 是硬约束。

### 5.3 DeepSpec eval.py 跑 dspark_qwen3_8b_block7（Ada/Ampere BF16）
- 依赖与坑、Ada/Ampere 新实测：**无 Ada/Ampere BF16 路径专项一手实测 → 无可靠来源**。已知硬约束：DSpark 的 NVFP4 内核 Blackwell 独占，Ada/Ampere 只能走 BF16 fallback（若实现支持），性能与官方 B300 数字不可比。

### 5.4 Qwen3.6 MTP 本地路径（4060 对比）
- **llama.cpp MTP 状态（社区 gist + Unsloth 官方，2026）**：MTP 经 **PR #22673（2026-05-16 合入）** 进入 llama.cpp 主线，**无需 fork**。支持 Qwen3.6-27B（dense）与 35B-A3B（MoE），需 **MTP-converted GGUF**（含 NextN 头）。
- **b9553 回归**：**存在 build 特定回归**——gemma4-assistant/MTP draft 在 **b9553 可用**，在 b9702/b9717 报 "invalid vector subscript"（HF 社区 discussion，实测，RTX 4070 Ti SUPER，已上报 issue #24795；b9553 用旧 flag 名 `--model-draft`/`-ngld 99`）。→ b9553 是已知可用锚点。
- **4060 8GB 可行组合**：Qwen3.6-27B 对 8GB 显存偏大，需大量 offload；更现实的是**较小档 + MTP**。社区实测 27B dense 无 MTP ~13 tok/s、有 MTP ~28-30 tok/s（c1，dredyson.com/HN）；35B-A3B MoE 无 MTP 更快。**4060 8GB 直接跑 27B 不现实，宜用小档 Q4 + n-cpu-moe/offload**；预期 MTP 加速 1.4-2.2×（Unsloth 官方声称）。
- **重要冲突提示（社区实测）**：单流 llama.cpp draft-spec 对 3B-active MoE 在消费级 Ampere（RTX 3090）**net loss**（thc1006 基准，19 配置无一净加速）；而 vLLM MTP k=1 + `--no-enable-prefix-caching` 在同卡 flip 为 +27.5% 解码速率。→ **MTP 收益强依赖引擎/并发/前缀缓存配置，非普适**。

### 对 PiLoop v3.1 的直接结论（≤10 条）
1. DSpark 是 **DeepSeek 半自回归投机解码**（block-diffusion 语义），**非标准 draft spec**；ankk98 GGUF 的 base 为 deepseek-ai/dspark_gemma4_12b_block7，MIT license。
2. **stock llama.cpp 无 DSpark 半自回归 block 验证一手支持**；DSpark 官方一等公民在 **vLLM 主线**。
3. **DSpark 已原生合入 vLLM**（method=dspark），官方 8×B300 声称 ~250 tok/s@bs1、接受长 ~5。

5. rafaelcaricio fork 实测 DSpark-5 ~1.59× MTP-1（DGX Spark），但 τ 有缺陷；暴露 τ/SPS 指标可复用。
6. #46931 已作为 #46910 重复关闭，跟踪 #46910 为准。
7. Qwen3.6 MTP 已入 llama.cpp 主线（PR #22673，无需 fork），但 **b9553 是已知可用 build**，b9702/b9717 有回归。
8. **4060 8GB 跑 Qwen3.6-27B 不现实**，宜小档 Q4 + offload + MTP；预期 1.4-2.2× 但须实测。
9. **MTP 收益非普适**：消费级 Ampere 单流对 A3B MoE 可能 net loss，收益强依赖引擎/前缀缓存 → v3.1 必须本地 A/B 实测再定。

## 模块 6 · 编译器三级方案落地细节

### 6.1 torch.compile/Inductor 基线
- **dump Triton 代码（PyTorch 官方文档 docs.pytorch.org，2026）**：`TORCH_LOGS="output_code"`（或 `TORCH_COMPILE_DEBUG=1`）打印 Inductor 生成的 Triton/C++ 代码；日志末尾给出 `torchinductor_<user>` 目录，内含 `output_code.py`。`TORCH_LOGS` 还支持 `kernel_code`（逐 kernel）、`autotuning`、`post_grad_graphs` 等。
- **生成质量**：Inductor 对 pointwise/reduction（含 RMSNorm/softmax 类）擅长融合；但 GEMM/mm/addmm 常 fallback 到 cuBLAS（`extern_kernels.mm`），不自行生成（PyTorch 论坛实测）。→ decode-attention 若走 SDPA 也可能走外部 kernel。
- **公平计时**：需 CUDA warmup（首次调用初始化 CUDA context 会扭曲计时）、`torch.cuda.synchronize()`、autotune warmup；compile cache 会影响二次计时。

### 6.2 TVM MetaSchedule 单 kernel 调优（Ada 消费卡）
- **2026 sm89 支持**：TVM MetaSchedule 为搜索式 auto-tuning，`MetaScheduleTuneTIR`/`MetaScheduleTuneIRMod`（支持 op_names 选择性调优）+ `MetaScheduleApplyDatabase`（官方文档 tvm 0.24.dev）。CUDA target 走 `tvm.cuda(0)` + `Target.from_device`。**sm89/Ada 专项支持无独立声明，但 CUDA backend 通用可用**。
- **单 RMSNorm/GEMM 调优先例**：官方教程 customize_opt 有单 TIR 函数 tune 示例（默认 `trials=2000`）。**调优时长量级**：整模型 tuning 约数百分钟（论文 Table：ResNet-50 约 220 min MetaSchedule）；单 kernel 相应缩短至数分钟-数十分钟量级（估计）。
- **选择性单 kernel**：用 `MetaScheduleTuneIRMod` + `op_names` 只调目标算子（如单 RMSNorm/GEMM）。

### 6.3 MLC-LLM 模型编译流程
- **三步（官方文档口径）**：convert_weight / gen_config / compile。Qwen3/Gemma4 在 2026 的支持矩阵**无一手完整声明 → 部分无可靠来源**；Mali OpenCL 后端见模块 3。
- **自定义（微调）权重过 MLC**：MLC 支持从 HF 权重 convert_weight 再 compile，理论上微调权重可走 MLC → **若可行，则 Source-C（自训）模型也能走 Mali 通道**（三引擎×三源叉乘成立），但 Qwen3/Gemma4 新架构编译支持需实测确认。

### 6.4 cuDNN Graph API / CUTLASS 3.x epilogue fusion 入门只读材料
- 供文档 11 参考（一手来源）：PyTorch 官方 "Triton Kernel Compilation Stages" 博客、"Using User-Defined Triton Kernels with torch.compile" 教程、Lei Mao "PyTorch Triton Kernel Transparent Tracing" 博客、TVM 官方 MetaSchedule/customize_opt 教程。cuDNN Graph/CUTLASS 官方文档本身为一手权威入门。

### 对 PiLoop v3.1 的直接结论（≤10 条）
1. torch.compile 基线用 `TORCH_LOGS="output_code"` 一键 dump Triton/C++，产物在 `torchinductor_<user>/output_code.py`。
2. Inductor 擅长 RMSNorm/softmax 类融合，但 **GEMM 多 fallback cuBLAS**，K3 单 kernel 调优价值主要在非 GEMM 算子。
3. 公平计时须 CUDA warmup + synchronize + 处理 compile cache。
4. TVM MetaSchedule 可用 `op_names` 做**单 kernel 选择性调优**，Ada 走通用 CUDA backend。
5. 单 kernel 调优时长约数分钟-数十分钟量级（整模型数百分钟），K3b 可承受。
6. MLC 三步流程明确，自定义微调权重理论可过 MLC → **Source-C 模型可上 Mali 通道**（叉乘成立，待实测）。
7. Qwen3/Gemma4 的 MLC 编译支持矩阵无一手完整证据，须实测确认。
8. 三级编译（torch.compile 基线 / MLC 上板 / TVM 单 kernel）与证据自洽，予以保留。
9. K3a（批量 GQA decode）走 torch.compile+Inductor 融合基线合理；K3b（in-kernel KV dequant）宜用 TVM 单 kernel 调优。
10. 文档 11 只读材料清单以 PyTorch/TVM 官方 + Lei Mao 博客为一手入门。

## 模块 7 · Direction-B 研究包

### 7.1 Subagent 实现深潜
- **pi-dispatch（gist nidhishs, 一手源码）**：pi.dev 扩展，subagent 编排即代码——**fan-out / join / race-and-cancel** 作为 JavaScript 而非工作记忆。
- **Pi subagent（nicobailon/pi-subagents, 一手仓库）**：进程模型——spawned child 不继承 pi-subagents skill，fork child context 过滤掉 parent-only 编排消息；默认 child **不注册 subagent 工具**并收到"你不是 orchestrator"边界指令；例外是 resolved builtin tools 含 subagent 的 fanout child。**maxSubagentDepth 防失控**：默认限 2 级（main→subagent→sub-subagent），更深被阻止；嵌套显示为树，可按 id targeting；`PI_SUBAGENT_DEPTH` 内部自动传播。async 完成事件 `subagent:async-complete`。
- **oh-my-pi（can1357/oh-my-pi, 一手仓库）**：`task` fan-out 到隔离 worktree，每 worker 独立工具面，最终 yield **schema-validated 对象**（无 prose 解析、无 sibling 合并冲突）；RPC/ACP 经 stdio。角色 `smol` 供廉价 subagent fanout；advisor 角色独立 context 旁路审查；`(a | b)` 括号+竖线并行 fan-out。
- **三方接口对比**：pi-dispatch（编排即 JS：fan-out/join/race）；pi-subagents（深度守卫 + async 事件 + context 过滤）；oh-my-pi（隔离 worktree + schema 校验返回 + ACP/RPC）。

### 7.2 Context compaction 实现
- **Claude Code auto-compact（一手 issue + 社区 claudefa.st）**：默认阈值约 **~83.5%** context 使用触发（环境变量 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 可设 1-100 覆盖，如 90/70）；策略为摘要历史、保留关键决策/状态、释放 token。社区痛点（issue #25679/#28728/#41818）：默认接近满才触发会中断任务，要求可配置更早阈值。Claude Cookbook 给出手动 compaction pattern（`context_token_threshold` + `<summary>` 标签）。
- **oh-my-pi/其他 harness**：oh-my-pi 有 `/compact` 分发路径（TUI/ACP/RPC 共享 parseSkillInvocation）。
- **学术侧**：agent context/history summarization 2026 单一权威综述未系统检索到 → **部分无可靠来源**；"compaction × prefix cache 命中率"有相关证据：vLLM #38182 报 MTP 开启使前缀缓存命中率 ~92%→~71%（社区实测），说明 **history 结构变化直接冲击 prefix cache 命中**，可类比 compaction 对 cache 的影响。

### 7.3 Tool schema 简化研究
- 小模型 tool-call 成功率 × schema 复杂度的论文/实验（description-free、schema 蒸馏、按需注入）：未检索到单一权威论文全文 → **部分无可靠来源**；v1 提及的"tool-knowledge-internalization"论文全文要点未获一手确认 → 标注待补。
- 可迁移一手证据：teich 包（Fable-5 生态）会解析并**内置精确 tool-schema 与 descriptions**，过滤 limit/model-switch（armand0e HF dataset 说明）→ 训练时 schema 内化有工程先例。

### 7.4 Pi session/trace event-stream API
- **oh-my-pi（一手 README/releases）**：RPC/ACP 经 stdio 或 Agent Client Protocol 连接编辑器/程序；SDK 可嵌入 Node。trace hook 正确挂点为 **RPC/ACP dispatch 路径**（parseSkillInvocation 等共享 helper 所在层）。async 完成事件 `subagent:async-complete` + `src/extension/index.ts` 注册的 notification handler 是 trace hook 的自然挂点。精确 event-stream schema 字段 → **部分无可靠来源，需读 SDK 源码确认**。

### 对 PiLoop v3.1 的直接结论（≤10 条）
1. 三种 subagent 实现各有侧重：**pi-dispatch=编排即JS**（fan-out/join/race）、**pi-subagents=深度守卫+async事件**、**oh-my-pi=隔离worktree+schema校验**。
2. **maxSubagentDepth 默认 2 级**是防失控标准设计（pi-subagents 一手），v3.1 直接采用。
3. oh-my-pi 的 **schema-validated 返回 + 隔离 worktree** 是避免并发合并冲突的最佳实践，推荐借鉴。
4. Claude Code auto-compact 默认 **~83.5%** 触发，可用 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 调；v3.1 compaction 策略可参此阈值设计。
5. **compaction/history 变化直接冲击 prefix cache 命中**（vLLM #38182 类比证据），设计 compaction 须同时评估 cache 命中率。
6. subagent context 过滤（移除 parent-only 编排消息）是 pi-subagents 一手实现，v3.1 trace 采集须注意此过滤。
7. trace hook 挂 **RPC/ACP dispatch 路径 + subagent:async-complete 事件**，是一手确认的正确挂点。
8. tool-schema 简化学术证据不足，但 teich 包"训练时内置精确 schema"提供工程先例，可作 schema 内化起点。
9. `smol` 角色供廉价 subagent fanout（oh-my-pi），可映射到 v3.1 边端小模型 subagent。
10. 精确 event-stream schema 字段需读 SDK 源码，列为待补一手项。

### 8.1 SWE-bench Pro 公开子集最小可跑

- **Docker/磁盘**：用预构建镜像（`--use_local_docker` beta）；本地跑 `swe_bench_pro_eval.py --num_workers`。**SWE-bench 通用建议 x86_64、≥120GB 空闲磁盘、16GB RAM、8 核**（SWE-bench 官方 swebench.com）；小子集（10-20 题）用 `--instance_ids` 限定。cache_level=env 约需 100-120GB。
- **SWE-rebench 替代**：nebius/SWE-rebench 提供 ~7,500 清洗镜像（Docker Hub swerebench），用其 fork 一行跑或抄 test_cmd/log-parser 改动（HF discussion，作者 ibragim-bad 一手回复）。

### 8.2 Terminal-Bench 2.1 集成
- **vs 2.0 差异（tbench.ai 官方 + Artificial Analysis）**：2.1 用 **89 任务**（2.0 也是 89 任务，2.1 为"改进版 inspired by Z.ai TB2.0 Verified"）；跨 SWE/ML/security/data science 类别，难度 easy→hard。
- **Terminus 2 harness 接自定义 OpenAI 端点（EvalScope 官方文档 evalscope.readthedocs.io）**：`terminus-2` agent 用你配置的 model；`eval_type='openai_api'` + `api_url` + `api_key` 指向任意 OpenAI 兼容服务（如 v3.1 自建端点）；`environment_type` 可选 docker/daytona/e2b/modal。**只有 terminus-2 用你的模型推理**（claude-code/codex 等用自己的 key）。
- **Harbor 跑法（tbench.ai 官方 docs/run-terminal-bench-2-1）**：`harbor run -d terminal-bench/terminal-bench-2-1 -a terminus-2 -m <model> -k 5`；`--include-task-name` 跑单任务；`-a oracle -l 5` 先验证下载/容器。**无 GPU 子集过滤**：用 `limit`/`--include-task-name` 手动筛，单任务各自容器。
- **单任务磁盘/时间**：无精确一手数字 → **无可靠来源**；每并发起一容器，按 Docker 资源调 `eval_batch_size`。

### 8.3 自建 benchmark 方法学参考
- **一手材料**：Terminal-Bench 2.0 论文（arXiv，89 任务，每任务独立环境+人写解+验证测试，"数小时人工+LM 辅助校验确保可解/真实/well-specified"）是"task spec + verifier + 统计约定"的优秀范本；Artificial Analysis 用 Terminus 2 harness + e2b sandbox、pass@1 averaged over 3 repeats。SWE-bench Pro 论文（Scale）与 SWE-bench Verified 结构（HF）可作 verifier 设计参考。EdgeAgentPerf/QCS-Bench 设计宜引用这些"每任务独立容器 + 二元 verifier + pass@1 多次重复取平均"约定。

### 对 PiLoop v3.1 的直接结论（≤10 条）
1. SWE-bench Pro 用 `ScaleAI/SWE-bench_Pro` + 预构建 `jefzda/sweap-images` 镜像，小子集用 `--instance_ids` 限 10-20 题。
2. 通用硬件底线 **≥120GB 磁盘/16GB RAM/8 核 x86_64**，v3.1 评测机须满足。
3. SWE-rebench（~7,500 清洗镜像）是低成本替代，一行跑。
4. Terminal-Bench 2.1 用 **89 任务**，经 EvalScope 或 Harbor 跑。
5. **terminus-2 接自定义 OpenAI 端点**（`eval_type='openai_api'`）是连 v3.1 自建端点的正确方式，其他 agent 用自己 key。
6. 无 GPU 子集须手动 `--include-task-name`/`limit` 筛，无内置过滤。
7. 单任务磁盘/时间无一手数字，须自测；每并发一容器。
8. Terminal-Bench 2.0 论文是自建 benchmark 的最佳方法学范本（独立环境+人写解+验证测试）。
9. verifier 设计引用 SWE-bench Verified 结构 + pass@1 多次重复取平均统计约定。
10. EdgeAgentPerf/QCS-Bench 应采"每任务独立容器 + 二元 verifier"设计，与主流一致。

## 模块 9 · 数据与合规收尾验证

### 9.1 Glint-Research/Fable-5-traces license 细读
- **HF 一手核实（dataset card + 文件树）**：**License AGPL-3.0**；188MB，4,665 行（fable5_cot_merged.jsonl 69.8MB），下载上月 51,152。
- **额外使用限制（README 原文）**：*"Check compatibility before using this data in commercial or closed-source training pipelines."*；数据源自 Glint Research 收集的 Fable 5 agent traces + TeichAI 生态。
- **关键合规事实（下游模型卡一手转述，如 lordx64/Qwable-v1、hotdogs/qwen3.6-27b-fable5-lora）**：底层是 Anthropic gated **claude-fable-5** 预览模型输出（2026-06-10 短暂开放，**2026-06-22 因美出口管制指令全球暂停**）；下游需自查 Anthropic usage policy 合规。**AGPL §13：网络服务使用须公开源码**。
- **"本地训练、不分发权重、只发评测报告"场景的义务边界**：AGPL-3.0 的 §13 约束主要触发于"网络可访问服务"；纯本地训练+不分发权重+只发评测报告，**AGPL 分发义务通常不触发**（仅条款事实，非法律意见）；但底层 claude-fable-5 来源的 Anthropic policy 合规仍需自查。→ 与 v3.1 "能力轨（含 Fable-5，权重不发布）"定位**一致且更稳妥**。

### 9.2 Open-SWE-Traces 按 resolved 过滤
- **HF/arXiv 一手核实（nvidia/Open-SWE-Traces + arXiv 2606.16038）**：**207,489 条轨迹**，9 种语言（Python/Go/TS/JS/Rust/Java/PHP/C/C++），源自 20,000 真实 PR（OpenHands + SWE-agent harness）；Minimax-M2.5 生成 thinking 轨迹、Qwen3.5-122B 生成 non-thinking。**resolved 标签**：Table 1 的 Resolved/Unresolved/Unknown 指 issue 解决状态（字段在轨迹元数据）；四配置 = {openhands, sweagent} × {minimax_m25, qwen35_122b}。**过滤自 SWE-rebench-V2 的宽松 license（MIT/Apache/BSD）**。License CC-BY-4.0。
- **resolved=true 比例/四配置差异/过滤后规模**：论文有 Table 1/2（Trajectories/PRs，PR 计数跨类不可横加），**精确 resolved=true 百分比未在检索片段中给出 → 部分无可靠来源，需读论文 Table**。验证效果：微调 Qwen3-30B-A3B 达 SWE-bench Verified 61.7%、Multilingual 57.1%、Pro 36.8%（论文声称）。

### 9.3 自采 trace 数据集发布规范
- **pi-share-hf 清洗流程细节**：未获一手文档 → **无可靠来源**。
- **HF trace 类数据集 dataset-card 推荐字段**：HF Agent Traces 文档（huggingface.co/docs/hub/agent-traces）为一手规范；Fable-5 生态实践显示 trace 保留 native agent-event 格式（多轮 prompt/response/tool call/command output/retry/session 元数据）可在 HF Agent Traces / Data Studio 查看。**subagent 并发标注的 schema 设计先例**：SALT-NLP/SWE-chat 有 conversations/sessions/commits 多表 + human vs agent 代码归属；AlinCiocan/fable-5-claude-code-traces 保留 session 级 workflow 元数据。→ 可迁移作并发标注 schema 参考。

### 9.4 Hermes filtered / GLM-5.2-Agent `<think>` 块处理
- **社区训练实践（保留/剥离 reasoning）**：Fable-5 训练模板保留 `<think>{thinking}</think>` + response_with_tool_calls（lordx64 dataset 一手模板）；保留 reasoning 对 agentic 蒸馏有益。**Hermes filtered / GLM-5.2-Agent 专项 `<think>` 处理的社区共识**：未获专项一手证据 → **部分无可靠来源**。可迁移：Gemma4 训练"保留 reasoning 至少 75%"（Unsloth 官方）说明混合 reasoning/direct 样本可平衡。

### 对 PiLoop v3.1 的直接结论（≤10 条）
1. Fable-5-traces 确为 **AGPL-3.0**（HF 一手），README 明确警告商用/闭源前查兼容性。
2. "本地训练+不分发权重+只发评测报告"通常**不触发 AGPL 分发义务**（仅条款事实）；但底层 claude-fable-5 的 **Anthropic policy 合规须自查**。

4. v3.1 "能力轨权重不发布"定位与 AGPL + Anthropic policy 双重约束**一致且稳妥**，予以保留。
5. Open-SWE-Traces **207,489 条**，resolved 标签在轨迹元数据（Table 1），license **CC-BY-4.0**（比 Fable-5 宽松）。
6. resolved=true 精确比例须读论文 Table，四配置（2 harness × 2 模型）差异同；过滤后规模需自算。
7. Open-SWE-Traces 过滤自宽松 license（MIT/Apache/BSD），**适合合规轨（权重可发布）**。
8. HF Agent Traces 格式 + SALT-NLP/SWE-chat 多表 schema 是自采 trace 发布的一手参考，可加 subagent 并发标注。
9. 训练保留 `<think>` 块对 agentic 蒸馏有益（Fable-5 模板一手 + Gemma4 "保留≥75% reasoning" 官方）。
10. pi-share-hf 清洗流程无一手文档，列为待补项。
