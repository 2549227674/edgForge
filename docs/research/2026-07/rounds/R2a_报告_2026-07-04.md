## 0. 执行摘要

### 0.1 本轮核实后的总体裁决

1. **训练主场升到 32–48G 是正确方向**。Qwen3.5 的“不宜 QLoRA”不是传闻，而是 Unsloth 官方文档明确写法；Qwen3.5-2B/4B 的 bf16 LoRA 显存门槛分别约 5GB/10GB，长上下文主要受激活与 batch/packing 影响，48G 明显优于本地 8GB。来源：[Unsloth Qwen3.5 fine-tune](https://unsloth.ai/docs/models/qwen3.5/fine-tune)。
2. **Gemma4-E2B/E4B 工具链已可作为主力候选，但要严控 chat template / thinking block**。Unsloth 官方支持 Gemma4 E2B/E4B/26B-A4B/31B 微调、GGUF 导出，并提示思考块训练和导出后退化常见坑。来源：[Unsloth Gemma4 fine-tune](https://unsloth.ai/docs/models/gemma4/fine-tune)。
3. **RK3588 五通道并发的“多模型驻留 / Prompt cache / tool calling”有 RKLLama 证据，`num_npu_core` 分核并发暂无公开实测**。RKLLama README 明示 `rkllm-runtime V1.3.0`、多模型驻留、stream 模式下不同模型并行、非 stream FIFO、prompt cache 自动保存恢复；但没有证明两个 RKLLM 实例各绑不同 NPU 核可稳定同时推理。来源：[RKLLama README](https://github.com/NotPunchnox/rkllama)。
4. **PC 档混合推理必须以 llama.cpp 为主引擎**。llama.cpp server 官方参数已经覆盖 `--parallel`、continuous batching、`--batch-size`、`--ubatch-size`、`--gpu-layers/-ngl`、`--cpu-moe`、`--n-cpu-moe`、KV cache 类型；但公开资料没有给出“8GB VRAM + 16GB RAM 下 `-ngl × --parallel` 曲线”，这正是 PiLoop 应自测的空白。来源：[llama.cpp server README](https://github.com/ggml-org/llama.cpp/tree/master/tools/server)。
5. **DSpark GGUF 语义得到新证据：ankk98 的 GGUF 不是普通 draft，而要求 llama.cpp `ft-dspark` 或含 `draft-dspark` 的 release**。这修正了 v3.1 中“可能只是普通 draft”的疑虑：该模型卡明确写 `LLM_ARCH_DSPARK` 与 `--spec-type draft-dspark`。但 stock llama.cpp 主线是否已包含该分支，仍需以本地构建验证。来源：[ankk98 DSpark GGUF model card](https://huggingface.co/ankk98/dspark-gemma4-12b-block7-Q4_0-GGUF)。
6. **Terminal-Bench 2.1 的文档已经存在，但任务页当前显示“Tasks have not been uploaded yet”**。因此执行策略应是：先用 Terminal-Bench 2.0 建立管线，2.1 一旦任务数据可用再切换。来源：[Terminal-Bench 2.1 benchmark page](https://www.tbench.ai/benchmarks/terminal-bench-2-1)、[How to run Terminal-Bench 2.1](https://www.tbench.ai/docs/run-terminal-bench-2-1)。
7. **SWE-bench Verified 弃用的“OpenAI 官方页”本轮未从 OpenAI 域名抓到可靠页面**。可核实的是：SWE-bench Pro 论文明确 1,865 题、public/held-out/commercial 三分区；第三方百科条目声称 OpenAI 于 2026-02 弃用 Verified，但不应在正式文档里写成“已独立核实官方声明”。建议写为“有强二手信号，官方原文待补证”。来源：[SWE-bench Pro paper](https://arxiv.org/abs/2509.16941)。
8. **编译器三级方案可落地，但 TVM MetaSchedule 更适合 P2 单算子实验**。TVM 文档明确 MetaSchedule 会搜索 TIR schedule 并在真实硬件上测量，支持选择性 operator tuning；MLC-LLM 编译流程可作为 RK3588 Mali/OpenCL 通道的实验路径，但未找到 2026 年 RK3588 + Qwen3/Gemma4 的官方 tok/s。来源：[TVM MetaSchedule](https://tvm.apache.org/docs/deep_dive/tensor_ir/tutorials/meta_schedule.html)、[MLC compile models](https://llm.mlc.ai/docs/compilation/compile_models.html)。
9. **Trace 公开数据发布规范已有 HF 官方路线**。HF Agent Traces 原生支持 Claude Code / Codex / Pi JSONL，Pi session 目录为 `~/.pi/agent/sessions`，并提示用 `pi-share-hf` 进行 secrets redaction、TruffleHog 与 LLM review。来源：[HF Agent Traces docs](https://huggingface.co/docs/hub/agent-traces)。

## 1. 租卡训练主场的具体配置

### 1.1 Qwen3.5：bf16 LoRA 是主路，QLoRA 明确不推荐

**关键证据。** Unsloth Qwen3.5 微调文档明确写道：Qwen3.5 因 custom Mamba Triton kernels 需要 Transformers v5，并且“**It is not recommended to do QLoRA (4-bit) training on Qwen3.5 models, no matter MoE or dense, due to higher than normal quantization differences.**”同页给出 bf16 LoRA 显存需求：0.8B≈3GB、2B≈5GB、4B≈10GB、9B≈22GB、27B≈56GB，并写明 35B-A3B bf16 LoRA 可在 74GB VRAM 上工作。来源：[Unsloth Qwen3.5 fine-tune](https://unsloth.ai/docs/models/qwen3.5/fine-tune)。

**对 PiLoop 的含义。**

| 模型 | Unsloth 官方 bf16 LoRA VRAM 口径 | 32G 单卡 | 48G 单卡 | 建议 |
|---|---:|---|---|---|
| Qwen3.5-2B | ~5GB | 8k 很有希望，16k 需小 batch + checkpoint | 8k/16k 都应进入正式实验 | Source-C 边缘档强候选 |
| Qwen3.5-4B | ~10GB | 8k 可行性高；16k 需实测 | 16k 主力测试 | 租卡主战模型之一 |
| Qwen3.5-9B | ~22GB | 8k 紧，batch 极小 | 8k 可试，16k 不宜当 P0 | 只做上探/对照 |
| Qwen3.5-27B | ~56GB | 不可行 | 48G 不足 | 保持 teacher / judge / 推理，不训练 |
| Qwen3.5 MoE 35B-A3B | 官方称 74GB bf16 LoRA | 不可行 | 不可行 | 仅云端推理对照 |

**结论强度：高。** 这是官方文档直接约束，v3.1 的“Qwen3.5-2B/4B 租卡 bf16 LoRA only”应保留。

### 1.2 Gemma4-E2B/E4B：工具链可用，注意 MatFormer/PLE 与 thinking 数据格式

Unsloth Gemma4 微调文档明确支持 Gemma4 E2B/E4B/26B-A4B/31B，支持 text / vision / audio / RL；官方提示：

- E2B/E4B 是 dense + PLE，128K 上下文；26B-A4B 是 MoE，256K 上下文；31B dense，256K 上下文。来源：[Unsloth Gemma4 run](https://unsloth.ai/docs/models/gemma4/run)。
- E2B 4-bit 约 4GB、8-bit 约 5–8GB、BF16/FP16 约 10GB；E4B 4-bit 约 5.5–6GB、8-bit 约 9–12GB、BF16/FP16 约 16GB。来源：[Unsloth Gemma4 run](https://unsloth.ai/docs/models/gemma4/run)。
- full fine-tuning 可行但约 4x VRAM；MoE 模型建议 LoRA 而不是全参；若显存允许，优先 16-bit/bf16 LoRA。来源：[Unsloth Gemma4 fine-tune](https://unsloth.ai/docs/models/gemma4/fine-tune)。
- 训练数据必须明确决定是否保留 thinking blocks；生产助手建议只训练 final visible answer；multi-turn 不要把早先 thought blocks 喂回历史。来源：[Unsloth Gemma4 fine-tune](https://unsloth.ai/docs/models/gemma4/fine-tune)。
- Unsloth 支持保存到 GGUF；导出后能力变差常见原因包括 chat template / EOS 不一致。来源：[Unsloth Gemma4 fine-tune](https://unsloth.ai/docs/models/gemma4/fine-tune)。

**建议配置。**

| 模型 | 32G | 48G | 训练定位 |
|---|---|---|---|
| Gemma4-E2B | bf16 LoRA 8k/16k 均应可试；全参 2k/4k 小实验可作为对照 | bf16 LoRA 长上下文主力；全参微调短上下文对照 | RK3588 主力候选的训练源 |
| Gemma4-E4B | bf16 LoRA 8k 可行性高；16k 需实测 | bf16 LoRA 16k 主力 | PC 档 Source-C 主力候选 |
| Gemma4-26B-A4B | 只可低比特推理，不建议训练 | 48G 对 BF16 不足，MoE LoRA 也紧 | teacher/judge/云档 |
| Gemma4-31B | 只可低比特推理 | 48G 对 BF16 不足 | teacher/judge/云档 |

**结论强度：高。** 官方文档直接支持 Gemma4-E2B/E4B 微调、GGUF 导出与思考块格式注意事项。

### 1.3 Qwen3-1.7B/4B/8B：仍可保留 QLoRA，但长上下文 SFT 应优先租卡

本轮重点是 Qwen3.5+ 与 Gemma4；Qwen3 本身没有出现“不宜 QLoRA”的同等官方禁忌。对 Qwen3-1.7B/4B/8B 的保守策略：

- **本地 4060 8GB**：只做 1.7B/4B QLoRA pipeline 冒烟、数据清洗、mask 检查、短上下文过拟合测试。
- **32G 租卡**：4B 8k LoRA / QLoRA 正式训练；8B 4k–8k 试跑。
- **48G 租卡**：4B 16k、8B 8k 进入主实验；8B 16k 作为 P1/P2 上探，不应写成保证。

**证据强度：中。** Qwen3.5 的明确禁忌不能自动外推到 Qwen3；但长上下文 agent trace 的激活显存决定了租卡比本地更稳。

### 1.4 CPU16GB + GPU8GB 混合训练：可做诊断实验，不作训练主路

DeepSpeed 官方 ZeRO-Offload 文档说明 ZeRO-Offload 将 optimizer memory 和 computation 从 GPU offload 到 host CPU，可在单 V100 32GB 上训练 10B GPT-2，并用 DeepSpeedCPUAdam 加速 CPU Adam。来源：[DeepSpeed ZeRO-Offload tutorial](https://www.deepspeed.ai/tutorials/zero-offload/)。Unsloth 官方长上下文博客说明其 gradient checkpointing 可把 activations offload 到 CPU RAM，并通过 CUDA streams 降低 overhead。来源：[Unsloth 500K context blog](https://unsloth.ai/blog/long-context)。

但 PiLoop 本地 PC 只有 **16GB 系统内存 + 8GB VRAM**，现实约束是：

- OS、Pi/Node、tokenizer、dataset loader、page cache 都会占系统内存；真正可给 offload 的空间不足。
- PCIe 往返会拖慢迭代，尤其在长上下文 SFT 中更明显。
- 能解锁的更像是“4B QLoRA 更稳、max_seq 稍增、避免 OOM”，不是“8B bf16 LoRA”或“4B 全参”。

**建议实验。**

| 实验 | 目标 | 期望结果 |
|---|---|---|
| Qwen3-4B QLoRA 2k/4k，本地无 offload vs paged optimizer/offload | 看 OOM 边界 | 验证 offload 是否扩大可训 seq |
| Qwen3-4B QLoRA 4k，小样本 100–300 条 | 看吞吐下降 | 记录 tokens/s、step time、CPU RAM 峰值 |
| 不做 Qwen3.5 QLoRA | 避免官方禁忌 | Qwen3.5 只放到租卡 bf16 LoRA |

**结论强度：高。** Offload 技术存在，但 16GB RAM 的物理账决定它不是主路。

### 1.5 AutoDL 实操：价格未核实，成本只能用公式

本轮未找到 AutoDL 当前卡型价格的可靠静态页面。AutoDL 市场页需要前端渲染，搜索结果也没有稳定可引用的 2026-07 价格。为了避免编造，本文不给“4090 48G/L20 48G/A100 40G 每小时多少钱”的数字。

**建议在项目文档里写成实操 checklist：**

1. 用户手动截图 AutoDL 市场页，记录卡型、显存、系统内存、CUDA/驱动、镜像名、单价、时间戳。
2. 每轮训练报告只记录：`card_hourly_rate × wall_clock_hours + storage/network`。
3. 第一轮不要估大：先 1k sample、max_seq=4096、1 epoch，拿到真实 tokens/s 再估算 8k×3epoch。
4. 明确规避 CUDA / Transformers / Unsloth 组合坑：Qwen3.5 文档要求 Transformers v5；vLLM 对 Qwen3.5 的支持文档提示过版本限制，因此训练镜像优先用 Unsloth 官方推荐栈，而不是盲目追 CUDA 最新。

**结论强度：高（未找到可靠价格）。** 不写死价格，写“成本公式 + 实测日志”更可信。

### 1.6 在线 teacher + student 同卡：48G 只适合小 teacher 或离线蒸馏

如果 teacher 是 27B/31B，bf16 推理权重本身就约 54–62GB 级别，不适合 48G 单卡。Q4 teacher 可能压到十几 GB，但长上下文 KV、student 4B bf16 LoRA 的激活/优化器、dataset pipeline 会共同挤占显存与内存。

**建议：**

- P0/P1：两阶段离线蒸馏。先用云端 teacher 生成 / 过滤轨迹，再训练 student。
- P2：48G 上做“小 teacher 9B/12B Q4 + student 2B LoRA”的在线对照，只验证流程，不写成正式训练主路。
- 真实 judge 可独立跑 API / 云端，而非与 student 训练同卡。

### 1.7 对 PiLoop v3.1 的直接结论

1. Qwen3.5-2B/4B 只走 bf16 LoRA，保留“租卡主场”裁决。
2. Qwen3.5 QLoRA 禁忌是 Unsloth 官方出处，不再写成社区经验。
3. Gemma4-E2B/E4B 可进入训练候选，且应成为 RK3588/PC 的主力 Source-C 候选。
4. Gemma4 训练数据必须显式处理 thinking blocks；生产短答模型建议剥离早先 thought blocks。
5. 本地 16GB RAM + 8GB VRAM 混合训练只做 P2 诊断，不做主路。
6. AutoDL 成本不要写死，等用户截图/实测后更新。
7. teacher + student 同卡在线蒸馏不作为 48G P0；离线生成再训练更稳。
8. 48G 的最大质量收益是 8k–16k 长上下文 agent trace SFT，不是“能跑更大模型”本身。
9. Qwen3-4B/8B 可继续 QLoRA/LoRA 双路，但 Qwen3.5 只保留 bf16 LoRA。
10. 08_v3 中训练矩阵应加“模型 × seq × batch × tokens/s × peak VRAM/RAM”的实测表模板。

## 2. NAS-lite 双路线可行性

### 2.1 路线 A：真 NAS 只适合 TinyML / 小视觉模型 / 极小 draft 原型

Once-for-All（OFA）官方 repo 仍是硬件感知 NAS 的经典可复用代码库，README 中展示了 elastic resolution / width / depth / expand ratio / kernel size 的子网采样与搜索空间。来源：[Once-for-All GitHub](https://github.com/mit-han-lab/once-for-all)。这类路线与 MIT TinyML Lab3 谱系一致，适合做“我会硬件感知搜索”的小实验，但不适合直接套到 1.7B–4B LLM。

**可行实验设计：**

- 在 48G 单卡上不必训练大型 supernet；只跑 OFA/ProxylessNAS 风格小视觉模型或 <300M drafter toy。
- 产出不是 PiLoop 主线性能，而是 `docs/nas_lite_route_a.md`：搜索空间、约束、latency lookup、结果可视化。
- 简历中只有实际跑过才写；未跑只放大四 roadmap。

**结论强度：中高。** OFA 是可靠实现，但迁移到 LLM 主线不直接。

### 2.2 路线 B：Minitron 式结构化剪枝搜索更贴 PiLoop 主线

本轮找到的可用公开实现和论文信号：

- LLM-Pruner：README 描述三阶段 Discovery / Estimation / Recover，可在 3 分钟 pruning + 3 小时 post-training 的量级上做结构化剪枝实验，支持 LLaMA/Gemma 等；但 README 未显示 Qwen3 原生支持。来源：[LLM-Pruner GitHub](https://github.com/horseee/LLM-Pruner)。
- Sheared-LLaMA / LLM-Shearing：思路是从强 base model 裁剪出更小模型，再用动态数据加载与剪枝恢复。来源：[LLM-Shearing GitHub](https://github.com/princeton-nlp/LLM-Shearing)。
- 2026 论文方向显示 width/depth/dynamic pruning 都在继续演化，并已扩展到 Qwen3 / MoE；不过本轮未取得足够稳定的一手 URL 来支撑具体论文题名和数值，正式文档不应引用占位 arXiv 编号。处置：P2 只写“以 LLM-Pruner / Sheared-LLaMA 谱系为工具起点，自行在 Qwen3/Gemma 上复现实验”，等二次检索补齐论文证据后再加入具体论文。

**现实判断。** 对 Qwen3-1.7B/4B 做 width/depth 候选搜索 + 小蒸馏恢复，在 48G 单卡上比“LLM NAS”诚实得多。主要工程风险是工具适配 Qwen3 架构；可以从 Gemma/TinyLlama 支持路径借鉴，不保证开箱即用。

**硬件在环方案。**

1. 定义候选：层数裁剪、MLP intermediate size 裁剪、attention head/group 裁剪、RMSNorm/embedding 保持。
2. 每个候选只做 1k–5k trace 的恢复蒸馏。
3. 导出 GGUF / RKLLM W8A8。
4. 在 RK3588 上测 latency、TTFT、成功率、失败分类。
5. 用 `score = success_rate - α·latency - β·memory - γ·fallback_rate` 选 Pareto 前沿。

**公开先例。** 传统硬件感知 NAS 有 latency-in-the-loop 先例；LLM 剪枝候选直接下 RK3588 NPU 做搜索反馈，本轮未找到可靠公开先例。这是 PiLoop 的差异化点。

### 2.3 极小 draft 模型架构搜索：有交叉价值，但证据不足

投机解码相关论文普遍关注 draft length、acceptance、partial verification、MTP 训练，而不是“NAS 搜 drafter 架构”。本轮可引用的相邻方向包括 FastMTP（MTP head 对齐推理模式，平均约 2.03× speedup）和 SpecDec++ / PACER 的 adaptive candidate length，但未找到成熟的“为 DSpark / MTP 做硬件感知 drafter NAS”的开源管线。来源：[FastMTP](https://arxiv.org/abs/2509.18362)、[SpecDec++](https://arxiv.org/abs/2405.19715)。

### 2.4 对 PiLoop v3.1 的直接结论

1. NAS-lite 路线 A 可规划入库，但不进 P0/P1 开发。

## 4. PC 混合推理 × 并发交互

### 4.1 llama.cpp 是 PC 混合推理主引擎

llama.cpp server README 明确支持：

- parallel decoding and multi-user；
- continuous batching；
- OpenAI-compatible API；
- monitoring endpoint；
- function calling / tool use；
- speculative decoding；
- `--batch-size` logical max batch size，`--ubatch-size` physical max batch size；
- `--gpu-layers/-ngl` 控制进入 VRAM 的层数；
- `--cpu-moe` / `--n-cpu-moe` 控制 MoE weights 留在 CPU；
- `--cache-type-k/v` 支持 f16、q8_0、q4_0 等 KV 类型。

来源：[llama.cpp server README](https://github.com/ggml-org/llama.cpp/tree/master/tools/server)。

### 4.2 `-ngl × --parallel`：公开数据缺口成立

本轮未找到“RTX 4060 8GB + 16GB RAM，下 8B/12B Q4，扫描 `-ngl` 与 `--parallel=1/2/4`”的可靠公开数据。相关研究只证明 CPU/GPU 混合推理是有效方向，例如 PowerInfer 利用激活稀疏性在消费级 GPU + CPU 上服务大模型，但它不是 llama.cpp 的通用 offload 曲线。来源：[PowerInfer paper](https://arxiv.org/abs/2312.12456)。

**因此 PiLoop 自建曲线有价值。** 建议矩阵：

| 模型 | 模式 | 扫描项 | 指标 |
|---|---|---|---|
| Qwen3-4B Q4 | 纯 GPU | `--parallel 1/2/4/8` | TTFT, TPOT, tok/s, VRAM |
| Qwen3-8B Q4 | 混合 | `-ngl 16/24/32/all × --parallel 1/2/4` | CPU 段是否被并发摊薄 |
| Gemma4-E4B Q4 | 纯 GPU/混合 | 同上 | 工具调用成功率 + 延迟 |
| 12B Q4 | 混合上探 | `-ngl` 少量点 | 是否进入 swap、失败阈值 |

### 4.3 `--n-cpu-moe`：MoE 混合值得单独成表

llama.cpp 支持 `--cpu-moe` 和 `--n-cpu-moe N`，这使 MoE 的 CPU/GPU 混合不同于 dense 模型：dense 是层切分，MoE 是专家权重放置与 active expert 访问模式。Gemma4-26B-A4B / Qwen3-30B-A3B 在 8GB VRAM 上不应作为 P0，但可作为“MoE mixed inference 行为对照”。

**建议：** 先用能跑的 MoE 小模型或 Gemma4-E4B 非 MoE做 pipeline；MoE 上探只记录 `tokens/s + page fault/s + RAM + swap`。

### 4.4 KV cache 放置与量化

llama.cpp 参数支持 `--cache-type-k`、`--cache-type-v` 选择 q8_0/q4_0 等；这直接服务 K3b “in-kernel KV 反量化”与系统端 `--parallel` 并发。需要注意：KV 量化可能降低质量或工具调用稳定性，必须纳入成功率回归，而不是只看 tok/s。

### 4.5 16GB RAM 共驻预算

16GB RAM 同时承担：OS、桌面/驱动、Pi Node 进程、llama-server、CPU 层权重、KV cache、page cache、数据集/日志。Linux swap 一旦介入，延迟会出现悬崖。建议强制记录：

```bash
free -h
cat /proc/meminfo | egrep 'MemAvailable|SwapFree|Dirty|Writeback'
vmstat 1
pidstat -r -u -p <llama_server_pid> 1
nvidia-smi dmon -s pucvmt
```

### 4.6 vLLM PC 档：只做小模型纯 GPU对照，混合 offload 不作主线

本轮未能抓到 vLLM `--cpu-offload-gb` / `--swap-space` 官方参数页的稳定可引用证据。结合 8GB VRAM 约束，vLLM 对 PiLoop PC 档的定位应是：

- 4B AWQ/GPTQ 或较小模型的 scheduler / metrics 对照；
- 不承担 8B/12B 混合 offload 主线；
- 租卡上再测 vLLM/SGLang/DSpark。

### 4.7 对 PiLoop v3.1 的直接结论

1. PC 档必须定义为 CPU16GB + GPU8GB 混合平台，llama.cpp 是主引擎。
2. `-ngl × --parallel` 公开数据缺口成立，值得作为独立实验表。
3. `--ubatch-size` 和 `--batch-size` 要纳入调参，不只扫 `--parallel`。
4. KV cache q8/q4 与并发成功率必须同测。
5. MoE 混合用 `--n-cpu-moe` 单独成表，不和 dense 混在一起。
6. 16GB RAM 共驻预算必须记录 swap，swap 介入即标红。
7. vLLM 在 PC 只做小模型纯 GPU 对照；混合推理主路不押 vLLM。
8. K3b 与 PC 混合推理直接相连：KV 量化不是算子孤岛。

## 6. 编译器三级方案的落地细节

### 6.1 torch.compile / Inductor 基线：可作为每个 kernel 的第三基线

PyTorch `torch.compile` 官方文档页面在本轮可以打开但未解析到正文；可靠结论主要来自 PyTorch compiler 社区与 2026 论文：torch.compile 是 PyTorch compiler 核心优化工具，但也存在 correctness bugs，需要严格正确性对照。来源：[Demystifying correctness bugs in PyTorch Compiler](https://arxiv.org/abs/2604.08720)。

**建议 workflow：**

```bash
# 推荐在每个 kernel benchmark 中固定三基线
# 1. eager torch op
# 2. torch.compile(mode="max-autotune" 或默认) 后函数
# 3. hand-written Triton/CUDA kernel

export TORCH_COMPILE_DEBUG=1
export TORCH_LOGS="graph_breaks,recompiles,output_code"
python bench_rmsnorm.py --warmup 50 --iters 200 --verify 1
```

**公平计时规则：**

1. compile 首次开销不计入 steady-state；单独报告 compile time。
2. 先 warmup 至 kernel cache 稳定。
3. 每个 shape 用相同输入分布、相同 dtype、相同 stream sync。
4. 正确性测试包括随机 shape、边界 shape、极值输入、误差统计。
5. `torch.compile` correctness 必须与 eager 对齐，不可只看速度。

### 6.2 TVM MetaSchedule：P2 单 kernel 搜索实验成立

TVM 官方文档明确：MetaSchedule 是 search-based auto-tuning framework，会探索不同 TIR schedules（loop tiling、vectorization、thread binding 等），并在真实硬件上测量候选实现；它可用 `MetaScheduleTuneIRMod` 选择性调 `op_names`，并把 tuning record 持久化到 JSONDatabase。来源：[TVM MetaSchedule docs](https://tvm.apache.org/docs/deep_dive/tensor_ir/tutorials/meta_schedule.html)。

**对 PiLoop 的合理用法：**

- P0/P1 不做 TVM 编译器开发。
- P2 对 K1 RMSNorm 或一个小 GEMM/TIR 函数做 200–500 trials，比较 hand-written Triton vs TVM schedule。
- 输出 `docs/compiler_vs_handwritten.md`：schedule 搜索空间、最佳 schedule、为何赢/输。

**sm89/Ada 状态。** TVM 文档展示 `tvm.cuda(0)` 与 `Target.from_device(device)`；未找到专门针对 RTX 4060 sm89 的官方教程。建议以本地编译、CUDA toolkit、driver 为准，不承诺开箱。

### 6.3 MLC-LLM 模型编译流程：可服务 RK3588 Mali 通道

MLC-LLM 官方编译文档给出三步：

1. `convert_weight`：从 HF 格式转换权重，指定 `--quantization q4f16_1`；
2. `gen_config`：生成 `mlc-chat-config.json`；
3. `compile`：按 platform/device 编译模型库。

配置中包含 `quantization`、`context_window_size`、`prefill_chunk_size`、`tensor_parallel_shards` 等。来源：[MLC compile models](https://llm.mlc.ai/docs/compilation/compile_models.html)。

**注意口径差异：** MLC 的 `q4f16_1` 与 GGUF Q4、RKLLM W8A8 不同，不能直接比较“同为 4bit”；必须在 benchmark 里记录量化格式。

**自定义微调权重。** MLC 文档支持从 HF 格式模型转换权重；因此 Source-C merge 后如果仍是 Transformers-compatible 结构，理论上可走 MLC。Gemma4/Qwen3.5 的特殊结构支持需逐模型实测，不应先写成保证。

### 6.4 cuDNN Graph / CUTLASS 3.x epilogue fusion 只读清单

建议进入 11 号文档，不进入 P0 实操：

- NVIDIA CUTLASS 3.x GEMM / epilogue visitor tree / fused epilogue examples；
- cuDNN Frontend / Graph API；
- Triton persistent matmul / grouped GEMM tutorials；
- TVM TIR / TensorIR / MetaSchedule；
- PyTorch Inductor generated Triton code reading。

### 6.5 对 PiLoop v3.1 的直接结论

1. torch.compile 应作为 K1/K2/K3 的固定基线，不是单独项目。
2. 编译器输出代码必须纳入对照分析，而不仅是速度表。
3. TVM MetaSchedule 适合 P2 单 kernel 调优，不适合 P0。
4. MLC-LLM 可作为 RK3588 Mali 通道实验，但模型支持和 tok/s 需自测。
5. MLC `q4f16_1` 与 GGUF/RKLLM 量化不可混同。
6. 编译器实验的价值是“用与分析”，不是“自写编译器”。
7. 每个手写 kernel 必须报告 eager / compile / hand-written 三基线。
8. torch.compile correctness 风险要通过随机化测试规避。

### 7.1 Pi 官方 repo 与 session/trace 挂点

Pi repo README 显示：Pi 是 Agent Harness 项目，包含 `@earendil-works/pi-coding-agent`、`@earendil-works/pi-agent-core`、`@earendil-works/pi-ai`；仓库 MIT，2026-06-30 最新 release v0.80.3；README 也说明 Pi 默认没有内置强权限系统，需要容器/沙箱。来源：[earendil-works/pi README](https://github.com/earendil-works/pi)。

Pi session format 文档给出：

- session 文件位置：`~/.pi/agent/sessions/--<path>--/<timestamp>_<uuid>.jsonl`；
- session version 3；
- 消息里包含 `ToolCall`、`ToolResultMessage`、usage 中有 `cacheRead`、`cacheWrite`、cost；
- 支持 `CompactionEntry`、`BranchSummaryEntry`、`CustomEntry`、`CustomMessageEntry`；
- `buildContextEntries()` 会沿当前 leaf 到 root 构造 active context，并处理 compaction；

来源：[Pi session-format.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md)。

**直接挂点。** PiLoop 的 trace hook / compaction / subagent 标注应优先挂在 session manager 和 custom entries/messages，而不是外部解析终端日志。

### 7.3 context compaction：Pi 原生条目可用，prefix cache 命中率可量化

Pi session format 已有 `CompactionEntry`，字段包含 summary、firstKeptEntryId、tokensBefore；`buildContextEntries()` 会优先包含 compaction entry，再纳入保留区间。这给 PiLoop 的 context compaction 二开提供了强挂点。来源：[Pi session-format.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md)。

**实验设计：**

1. Baseline：默认 compaction。
2. Prefix-stable compaction：固定 system prompt + tool schema + repo map 前缀，把变动内容推后。
3. Tool-aware compaction：保留工具调用参数/结果摘要，截断 stdout。
4. Failure-aware compaction：保留最近失败 test、error stack、modified files。
5. 指标：`cacheRead/cacheWrite`、TTFT、成功率、重试次数、压缩后 token 数。

### 7.4 工具 schema 精简

本轮未找到 2026 年“tool schema 复杂度对小模型工具调用成功率”特别强的一手论文；但 HF Agent Traces / Pi session 数据和 Hermes filtered 的存在说明 tool calling trace 已成为训练数据方向。建议 PiLoop 自建实验：

- full schema vs minimal schema vs description-free schema；
- schema 按需注入 vs 全量常驻；
- 小模型工具调用 JSON valid rate、tool selection accuracy、参数字段缺失率。

### 8.3 SWE-bench Pro / SWE-rebench

SWE-bench Pro 论文明确：1,865 个问题，来自 41 个活跃仓库，分为 public（11 repos）、held-out（12 repos）、commercial（18 proprietary repos），面向 long-horizon enterprise-level tasks。来源：[SWE-bench Pro](https://arxiv.org/abs/2509.16941)。

### 8.4 自建 EdgeAgentPerf / QCS-Bench 方法论

近一年可参考的端侧/终端任务 benchmark 方向：

- TerminalWorld：从 80,870 条真实 terminal recordings 反向构造 1,530 个 validated tasks，Verified subset 200；强调真实终端工作流与 Terminal-Bench 相关性弱。来源：[TerminalWorld](https://arxiv.org/abs/2605.22535)。
- TUA-Bench：120 个真实 terminal-use tasks，覆盖五类任务，从 routine digital activities 到 scientific/engineering workflows。来源：[TUA-Bench](https://arxiv.org/abs/2606.28480)。
- Terminal Wrench：331 个 reward-hackable terminal benchmark environments，提醒 verifier 设计要防 reward hacking。来源：[Terminal Wrench](https://arxiv.org/abs/2604.17596)。

**PiLoop 自建 benchmark 必须包含：**

1. task spec 不泄漏 verifier；
2. deterministic verifier + reward hacking 检查；
3. before/after 只比较同一任务集；
4. 报告硬件、模型、量化、后端、版本、日期；
5. 指标包括成功率、重试、TTFT、TPOT、聚合吞吐、内存、失败分类；
6. 量化/并发/成功率三维联动是主差异化。

**非法律意见，只列事实。** 本地研究训练、不分发权重、不对外提供网络服务的风险显著低于发布派生权重或上线服务；若发布权重/服务，必须重新做许可审查。v3.1 双轨制合理：能力轨可用 AGPL 数据但不发布权重；合规轨用 CC-BY/Apache/MIT 数据发布。

### 9.4 Hermes filtered / GLM-5.2 `<think>` 块处理

Hermes dataset card 显示其是 multi-turn tool-calling trajectories，包含 step-by-step reasoning `<think>` blocks 和实际 tool execution results；filtered 版从 7,646 pruned 到 3,679，目标是 reasoning depth、structural integrity、tool-call validity。来源：[lambda/hermes-agent-reasoning-traces](https://huggingface.co/datasets/lambda/hermes-agent-reasoning-traces)、[DJLougen/hermes-agent-traces-filtered](https://huggingface.co/datasets/DJLougen/hermes-agent-traces-filtered)。AletheiaResearch/GLM-5.2-Agent 是 teich traces，319 JSONL，含 recovered/configured tools schema。来源：[AletheiaResearch/GLM-5.2-Agent](https://huggingface.co/datasets/AletheiaResearch/GLM-5.2-Agent)。

**训练处理建议：**

- 若目标是生产端侧 agent：默认剥离/不训练 `<think>`，只训练 visible action + tool call + final answer。
- 若目标是研究 reasoning distillation：保留 `<think>` 做单独模型或单独 ablation，不和发布权重混用。
- Gemma4/Qwen3.5 这类有 thinking/non-thinking 模式的模型，训练数据必须标注模式，避免把 thought block 误喂多轮历史。
