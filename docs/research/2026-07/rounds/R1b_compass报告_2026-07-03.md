# PiLoop v3 深度调研报告（时间基线 2026-07）

> [!NOTE]
> **历史调研归档**：本文保留 2026-07-03 的证据与判断，不是当前计划或执行卡。引用前先看 [`docs/research/README.md`](../../README.md) 的权威边界。

## 关键结论（TL;DR）
- 三大支柱的关键外部依赖均已用第一手来源核实为真实存在：teich（TeichAI/teich，agent SFT 数据管线）、Terminal-Bench 2.0/2.1（89 任务）、RKLLM v1.2.3（RK3588 仍单序列 W8A8）、DeepSeek DeepSpec（2026-06-27 发布，含 12 个可下载 draft checkpoint）、KernelBench 系列、Pi 子代理扩展生态——项目技术路线整体可行。
- 最大风险集中在三处：(1) Fable-5 系 Claude 蒸馏数据多为 AGPL-3.0 / 明确禁训练许可，直接用于 SFT 有合规冲突；(2) RK3588 上 Qwen3-4B W8A8 实测仅约 5.7 tok/s（单序列，无并发），端侧 4B agent 体验勉强；(3) DSpark NVFP4 生产路径仅限 Blackwell，Ada/Ampere 租卡上无实测数据。
- 自建"端侧并发×量化×成功率"benchmark 存在明确空白——现有 mobile/on-device agent bench（MobileWorld、MobileAgentBench 等）均不含量化维度与并发维度，这是 PiLoop v3 最具差异化的可发表点。

**推荐组合包（1.7B–8B 小模型 agent 行为 SFT）：**

1. **合规优先包（可商用/可公开权重）**：nvidia/Open-SWE-Traces（CC-BY，代码修复主干，占60%）+ Infatoshi/kernelbench-mega-traces（MIT，kernel编写，占10%）+ AletheiaResearch/GLM-5.2-Agent（通用agent，占15%）+ 自采Pi trace（占15%）。理由：全部许可允许训练与权重发布；Open-SWE提供resolved标签可做成功率筛选；避开所有AGPL/Fable数据。license合规=高置信。
2. **能力优先包（仅个人研究、权重不公开）**：Glint-Research/Fable-5-traces（AGPL，Pi coding主干40%）+ Crownelius/Complete-FABLE.5-2M（抽样20%）+ Open-SWE（30%）+ 自采Pi（10%）。理由：Fable-5是目前质量最高的Claude coding agent蒸馏，但**AGPL-3.0会传染到训练脚本与衍生权重，绝不可发布**；仅限本地实验。
3. **Pi行为专精包（方向B耦合）**：armand0e/qwen3.7-max-pi-traces + davanstrien/pi-traces + cfahlgren1 的 pi split + 自采Pi trace，全部 teich 原生、含 tools schema，用 `prepare_data` 加权混合（percentage 显式配比）。规模偏小需自采补充。

**关键红旗**：所有数据集经核实**均不含显式的子代理并发/concurrent tool-call 记录**——teich 导出时子代理是独立 trace 文件（child trace 带 parent_session_id），并不合并进 orchestrator session。因此 PiLoop v3 的 batch>1 子代理并发场景必须靠**自采 Pi trace**（用 pi-subagents / oh-my-pi 的 fan-out）补齐，公共数据无法覆盖。

**模块一 · PiLoop v3 直接结论（≤10条）**
1. 合规主干选 nvidia/Open-SWE-Traces（CC-BY，20万轨迹，带resolved标签）。
2. 所有 Fable-5 系（Glint / claude-fable-5 / lordx64 / 部分Crownelius）为 AGPL 或受限，权重发布场景禁用。
3. armand0e/claude-fable-5 与 Glint/Fable-5 是同一份数据，二选一。
4. teich 11列原生格式可直喂管线，非teich（Open-SWE/Mythos）需先转换。
5. 子代理并发数据必须自采，公共数据集零覆盖。
6. Mythos-25k（Apache）是唯一大规模可商用蒸馏，但无tools schema，只补通用能力。
7. kernelbench-mega-traces（MIT）与Project2直接相关，可双用。
8. 小规模Pi数据集（qwen3.7-max/pi-traces）适合方向B行为对齐，需扩量。
9. Fable-5模型2026-06-22因美出口管制全球下线，数据无法再生，注意存档。
10. 用 `prepare_data` 的 percentage/weight 显式配比，避免回填污染。

## 模块二 · Agent Benchmark 普查（验证基础）

1. **Terminal-Bench 2.0 / 2.1**：89 任务（4 Easy/55 Medium/30 Hard），16 类（软工、安全、科学计算、ML训练、数据科学、调试等），每任务=容器环境+指令+验证测试+人写参考解，Harbor 任务格式 + Terminus 2 中立 agent harness（也支持 Claude Code/Codex CLI/OpenHands/Mini-SWE-Agent）。v2.1 修复了 89 task 中的 28 个（外部依赖漂移/资源预算过紧/指令与测试不匹配），无未解任务。**接入自定义 agent/模型端点**：通过 Terminus 2 harness + e2b sandbox，pass@1 或 avg@5。**单任务资源**：SkillsVote 论文用 32 CPU/48GB RAM、4× 默认超时——**单任务子集可在租卡跑，4060 因是容器化 CPU-heavy 任务亦可跑部分子集**（非GPU瓶颈）。前沿模型<65%，小模型约15%。引用广度极高（被 AgentWorldBench、SkillsVote、多篇2026论文当标准）。Pi 官方分数：公开快照中 Claude 系（Mythos 5 88.0%、Fable 5 84.3%）领先——注意这些是模型分不是"Pi harness"分，需区分。置信=高。
2. **SWE-bench Lite/Verified/Pro（2026状态）**：**SWE-bench Verified**——500 个来自 12 个 Python repo 的 GitHub issue 任务，2024-08-13 由 OpenAI Preparedness 团队发布、经 93 名承包软件开发者人工验证；**2026-02-23 被 OpenAI 因测试缺陷与训练数据污染弃用**（Epoch AI 在自有基础设施上评测其中 484 个）。Lite 300 样本（11 repo）。**SWE-bench Pro**（Scale AI）1,865 真实任务/41 repo，抗污染，Pass@1；2026-06-28 标准化 public set 领先者 GPT-5.4(xHigh) 59.1%。**最小可跑子集实践**：SWE-bench Verified Mini（50 随机任务，HF可得）；SWE-bench Common（Lite∩Verified=93）；多篇论文用 200 子集控成本。**本地小模型评分先例**：Qwen-72B/GLM-Air 经 Kimi-K2 轨迹 bootstrap 后 SWE-Verified pass@1 达 43.0/35.2——4-8B 端侧模型直接跑 SWE-bench 分数极低，建议只做定性子集。置信=高。
3. **AgentWorldBench（Qwen，arXiv 2606.24597）**：**定位=世界模型评测（预测环境响应）而非 agent 成功率评测**——测的是模型能否预测环境的下一状态，5维度（Format/Factuality/Consistency/Realism/Quality）rubric 打分。9 个源 benchmark 覆盖 7 域（MCP/Search/Terminal/SWE/Android/Web/OS），含 Tool Decathlon、Terminal-Bench 1.0&2.0、OSWorld-Verified 等。**可复用部分**：其 task query 集（来自9个benchmark）与环境轨迹（>10M）可作为我的任务源；但其评分范式（world-model fidelity）与我要的 agent-success 不同，不能直接搬评分。权重与 benchmark 均 Apache 2.0。置信=高。
4. **其他 benchmark**：
   - **mercor/apex-agents**（arXiv 2601.14242）：长程跨应用专业服务任务（投行/咨询/法律），480任务公开集，Pass@1/Pass@8。**License明确禁止训练/微调/爬取，仅可评测**。与端侧agent场景相关性低（企业办公非端侧），不建议纳入。
   - **Tool Decathlon（Toolathlon）**：AgentWorldBench 9源之一，工具编排评测，可作任务源参考。
   - **cais/HLE（Humanity's Last Exam）**：通用推理/知识 benchmark，avg@1，被 Mercor/Applied Compute 当"能力未退化"对照（微调后 HLE 掉1.3% 不显著）——**适合作为方向A微调后"通用能力未塌陷"的回归对照**，值得纳入。
5. **端侧/资源受限 agent benchmark 是否存在**：**确认空白**。现有 mobile/on-device agent bench：MobileWorld（arXiv 2512.19432，116 GUI+45交互+40 MCP任务，SR%）、MobileAgentBench、MVISU-Bench、Mobile-Eval、AndroidWorld、EcoAgent（端云协同）——**全部评 GUI 成功率/步数/latency，无一个含"量化等级×成功率"或"并发 batch×成功率"联合维度**。**结论：PiLoop v3 自建"concurrency×quantization×success-rate"端侧 benchmark 是明确的可发表白空间。** 置信=高。

**模块二 · PiLoop v3 直接结论（≤10条）**
1. Terminal-Bench 2.1（非2.0）是当前应引用版本，28任务已修复。
2. TB子集可在租卡+4060跑，用Terminus 2 harness接自定义端点。
3. SWE-bench Verified已被弃用，改用Pro或Verified-Mini(50)控成本。
4. 端侧小模型跑TB/SWE分数极低，只做定性/子集对比，别报绝对分。
5. AgentWorldBench是world-model评测，只借任务源，不借评分范式。
6. HLE纳入作为"微调后通用能力未塌陷"回归对照。
7. apex-agents禁训练，且与端侧无关，不纳入。
8. 自建端侧benchmark填补"量化×并发×成功率"空白=核心差异化。
9. 自建bench任务源可从AgentWorldBench的9源+TB子集迁移。
10. 所有分数需标注 harness/版本/硬件/日期四元组。

## 模块三 · 端侧/本地并发推理现状（batch>1 主线）

1. **llama.cpp**：`--cont-batching`（连续/动态批处理，2026默认启用，env LLAMA_ARG_CONT_BATCHING）；`--parallel N`（slot数，决定并发交织能力，单请求无收益，只有真实并发流量才有吞吐增益）；`--ubatch`/`--batch-size`（物理/逻辑batch）。**统一KV(kv_unified)变化**：早期统一KV后被改为多独立cache，社区(Discussion #4130)仍在讨论refactor同时支持unified/split；`--kv-unified` vs `--no-kv-unified` 决定ctx-size如何在slot间分配（静态分区 M/N vs 动态）。`cache_prompt`默认true（复用公共前缀KV，但可能导致非确定性）。**slot save/restore**：/slot/save API存在；已知bug：Gemma SWA/hybrid + prompt cache + context checkpoints 近RAM上限会硬挂系统（Issue #24265，workaround: --cache-ram 0 --ctx-checkpoints 0）。**llama-batched-bench**用于并发吞吐曲线测量。**LLAMA_ARG_TOOLS内置agent工具**为实验特性。**消费卡并发1→16饱和点**：社区(paged KV Discussion #21961)在单A10G/Llama-3-8B-f16测得 unified 26序列OOM、paged扩到247序列且2.5×吞吐——4060/3090级公开饱和曲线数据有限，需自测。置信=中（4060具体曲线无一手数据）。
2. **vLLM/SGLang 在8GB卡**：4B–8B Q4/AWQ 在 4060(8GB) 下 VRAM 极紧张——Qwen3-Coder-Next 官方建议 vLLM≥0.15/SGLang≥0.5.8 且默认256K上下文需降到32K才能启动；实践上 **4060 8GB 只能作为极小并发(1-2)的Q4验证，真正的并发1→8对比应放租卡(4090/A100 48G)**。置信=中。
3. **RKLLM 并发能力**：v1.2.3 runtime **仍为单序列**（README/Radxa文档：RK3588 单序列 W8A8）。OpenAI兼容server方案：**GatekeeperZA/RKLLM-API-Server**（Open WebUI管理版，含model-aware sampling、context sliding window、110%上下文硬拒绝、SSE流式、KV cache多轮保留），**Luna-Inference/rkllm-server**。并发靠上层排队/多实例，非runtime原生。tool-call：server层解析<think>标签，OpenAI兼容端点支持function calling（v1.2.x改进了OpenAI兼容性）。prompt cache预加载：runtime支持cache reuse策略（v1.2.3优化了multimodal cache reuse）。置信=高。
4. **多agent边缘推理研究线**：**arXiv 2603.04428（Agent Memory Below the Prompt: Persistent Q4 KV Cache for Multi-Agent LLM Inference on Edge Devices，Yakov Pyotr Shkolnikov，2026-03）** 全文要点：Apple M4 Pro 10.2GB cache预算下，8K上下文FP16仅容3 agent；无持久化时每次eviction强制全量re-prefill（4K上下文15.7秒/agent）。方案=每agent KV持久化到磁盘Q4（safetensors）+ 直接reload进attention层，省O(n) prefill。三组件：block pool（per-agent隔离Q4 KV）+ BatchQuantizedKVCache（多agent并发推理，batch=2 interleaved chunked prefill）+ cross-phase context injection。Q4 KV perplexity影响：Gemma −0.7%、Llama +2.8%、DeepSeek +3.0%；Q4持久化容纳4×于FP16的agent数。开源 github.com/yshk-mxim/agent-memory（MLX，Apple Silicon）。**同线论文**：PolyKV（arXiv 2604.24971，共享非对称压缩KV池，K int8/V TurboQuant 3-bit）、KVFlow（NeurIPS 2025，2507.07400，多agent前缀缓存）、KVCOMM（NeurIPS 2025，2510.12872，跨上下文KV通信）、LRAgent（2602.01053，multi-LoRA KV共享）、RelayCaching（2603.13289）。置信=高。
5. **Pi 子代理并发扩展参考实现**：
   - **nicobailon/pi-subagents**：async 子代理委托（ping/status/spawn/interrupt/stop，v1方法），spawn异步，通过subagent tool executor，含spawn limits/child-safety depth；pi.events仅进程内。
   - **oh-my-pi (can1357)**：内置subagents，MIT，TypeScript；`omp --mode rpc`（NDJSON命令/事件帧）、`omp acp`（Agent Client Protocol over JSON-RPC）——**这是并发fan-out的可行接口**。
   - **ruizrica/agent-pi**：43扩展，6模式（含TEAM/CHAIN/PIPELINE多agent编排），agent-team dispatch、agent-chain顺序、pipeline-team 5阶段。
   - **nidhishs 的 pi-dispatch**：子代理编排as code（fan-out/join/race-and-cancel as JavaScript）——**最贴合"并发fan-out"需求**。
   - **ifiokjr/monopi**：含 subagents 包 + ant-colony swarm。
   - **可行路径**：Pi SDK（Node）嵌入 + `--mode rpc`/`acp` 由外部程序驱动并发；子代理默认不再spawn子代理（除非resolved builtin tools含subagent，受maxSubagentDepth约束）。置信=高。

**模块三 · PiLoop v3 直接结论（≤10条）**
1. RKLLM v1.2.3 端侧单序列，batch>1 只能靠上层多实例/排队。
2. 4060 8GB 只能跑并发1-2的Q4；真正并发1→8曲线放租卡。
3. llama.cpp `--parallel`+`--cont-batching`是本地并发主力，需自测饱和点。
4. Gemma SWA + prompt cache 近RAM上限硬挂系统（#24265），基准测试禁用checkpoint。
5. arXiv 2603.04428 是端侧多agent KV持久化的直接理论基础，可复现/对标（但其代码是MLX/Apple，需移植思路到RKLLM/llama.cpp）。
6. Q4 KV 持久化容纳4×agent、质量损失<3%，是自建bench的强baseline。
7. Pi 并发fan-out用 pi-dispatch 或 oh-my-pi RPC/ACP 模式实现。
8. 子代理并发数据自采时保留 parent_session_id 与 concurrent tool-call时序。
9. PolyKV/KVFlow/KVCOMM 是KV复用调度的对标文献群。
10. RKLLM-API-Server（GatekeeperZA）是端侧OpenAI兼容+tool-call现成方案。

## 模块四 · 小模型 Agent 微调/蒸馏管线（方向A）

1. **teich（TeichAI/teich）**：alpha但核心工作流稳定。API：`extract`/`load_traces`/`prepare_data`/`mask_data`。支持harness：claude_code（复制原生transcript JSONL）、pi、codex、hermes（含delegation子代理独立trace）、chat（OpenAI兼容直写结构化行）。**多轮tool-aware masking**：mask assistant reasoning/final answer/tool calls，忽略prompt/tool response；audit label防全mask行。**与TRL/Unsloth组合**：`prepare_data(datasets, tokenizer, max_length, drop_oversized_examples=True, trim_oversized_followups=True, tokenize=True)` → SFTTrainer → mask_data。加权混合传source mapping（percentage/weight/max_examples），显式配比不回填。**已知坑**：alpha阶段；oversized行处理需trim_oversized_followups=True让多轮行先丢final followup。置信=高。

## 模块六 · Kernel 微基准生态（Project 2 三kernel）

1. **KernelBench家族**：**原版**由斯坦福 Scaling Intelligence Lab 于 2024-12 发布（ICML 2025），250 任务：L1 单op 100 / L2 融合 100 / L3 全模型架构 50 / L4 HuggingFace 20，用 **fast_p** 指标评分（kernel 既正确又快于 PyTorch baseline 的任务占比）；README 自述为"评估 LLM 生成高效 GPU kernel 能力的 benchmark"；MIT 许可。**KernelBench-v2**（Lossfunk，Torch→Triton问题，自动检测CUDA/Triton，含Docker）；**Infatoshi/KernelBench-v3**（硬件中心，RTX3090Bench 43问题config、H100Bench 54、B200Bench 57、M4MaxBench 63；L1(15)简单op含matmul/softmax/conv/norm）；kernelbench.com/mega（roofline评分，speedup over reference）。**4060可直接复用**：v2的Triton问题 + v3的RTX3090Bench 43问题config（sm86近sm89，需重测baseline）；L1的softmax/norm问题=我的K1直接来源。原版fast_p可作评分。置信=高。
2. **decode attention参考实现**：FlagAttention、vLLM Triton attention backend（PagedAttention/ROPE/RMSNorm皆@triton.jit）、flash-attention-minimal、leandrolcampos/flash-attention。消费卡batched decode attention + paged KV gather公开微基准数据有限（no reliable source found for 4060-specific curves）。置信=中。
3. **KV-cache量化kernel**：llama.cpp Q8_0/Q4_0 KV实现（--cache-type-k/v，src/llama-kv-cache.cpp）；vLLM FP8 KV；dequant融合公开实现。**K3选型评估**：
   - "batched decode attention"：与Project1并发主线(batch>1)强耦合，roofline故事清晰，但消费卡baseline已被cuBLAS/FA高度优化，超越难。
   - "KV-quant dequant融合"：与模块三/五（Q4 KV persistent、arXiv 2603.04428）强耦合，差异化更高（端侧多agent场景独特），且llama.cpp已有Q4_0 KV可对标。
   - **建议K3选"KV-quant/dequant融合"**：更可行（有llama.cpp baseline）、更差异化（贴合端侧多agent持久化KV叙事）、与整个项目主线闭环。置信=中高。
4. **Liger-Kernel / Proton**：**Liger（linkedin，Triton）**——据 linkedin/Liger-Kernel README："With one line of code, Liger Kernel can increase throughput by more than 20% and reduce memory usage by 60%"，基准条件为 LLaMA 3-8B、batch size 8、bf16、AdamW、gradient checkpointing、8×A100 FSDP1（HF 在 4K 上下文 OOM，HF+Liger 可扩到 16K）；HF兼容RMSNorm/RoPE/SwiGLU/CrossEntropy/FusedLinearCrossEntropy，仅需Torch+Triton，TRL `use_liger_kernel=True`——**K1 RMSNorm/softmax的直接参考实现，4060可复现**（注意其官方吞吐/显存增益是 8×A100 多卡数据，4060 单卡增益需自测）。**Proton（Triton profiler）**：timeline view kernel launch/duration/gaps；**Proton vs ncu分工**：Proton做IR级/timeline快速定位（免root），ncu做硬件counter深挖（需root/--privileged）。置信=高。
5. **Nsight Compute在Ada(SM89)消费卡counter可用性**：ncu需root或--privileged Docker读硬件counter；共享云VM常无法获取（silent fail/无数据）；**租vGPU上ncu被禁用很普遍**——需bare-metal root SSH（如Spheron）。**4060(Ada SM89)本地有root则counter可采**（RTX 4070/5000 Ada为官方profiling示例硬件）。**结论：ncu深度profiling应放本地4060（有root），租vGPU只做吞吐/roofline粗测**。置信=高。
6. **"Agent辅助kernel优化"研究线2026快照**：CudaForge（training-free Coder-Judge，NCU反馈，o3达97.6%正确/1.68×，泛化A100/RTX6000/4090/3090，单kernel~26.5min/$0.3）、STARK（ICLR'26，多agent精炼）、KernelBlaster（memory-augmented in-context RL）、Astra（多agent）、KernelFalcon、GEAK（Triton AI agent）、KernelBand（RTX4090+H20+A100，CUDA12.1/Triton3.3）、SpecGen、CuTeGen。**4060最小可复现实验设计**：用CudaForge式Coder-Judge + 本地ncu反馈，对KernelBench-v3 RTX3090Bench的L1子集（15问题）跑，比较Pi小模型 vs 大模型的kernel优化能力——直接闭环Project1(Pi)+Project2(kernel)。置信=高。

**模块六 · PiLoop v3 直接结论（≤10条）**
1. K1(RMSNorm/softmax)直接参考Liger-Kernel Triton实现，4060可复现（增益自测）。

## 注意事项（Caveats）
- **许可冲突**：Fable-5系(Glint/claude-fable-5/lordx64/部分Crownelius)为AGPL-3.0或受限，训练脚本/衍生权重发布会被传染，仅限本地个人实验；组合包1(Open-SWE CC-BY + kernelbench MIT + Mythos Apache + GLM-5.2)是可公开权重的安全选择。
- **版本冲突**：RKLLM实际v1.2.3非v1.3.x；llama.cpp MTP有build regression(b9553 good/b9702+ broken)；Triton 3.6在RTX3090 fp16 matmul有正确性issue；CUDA 13.2会致Qwen3.6乱码(用<13.2或13.3)。
- **硬件×版本**：DSpark NVFP4限Blackwell，Ada/Ampere/L20无实测；ncu在租vGPU常被禁(需bare-metal root)；RK3588仅W8A8无W4A16。
- **数据真实性**：多个前沿实体(Fable-5/Mythos-5/GPT-5.5/Qwen3.7/GLM-5.2/DeepSeek-V4)为2026年模型，部分(Fable-5)已下线；DSpark所有性能数字为自报，无独立第三方验证。
- **缺一手数据处**：4060并发1→16饱和曲线、DSpark在Ada/Ampere实测、Jetson/地平线同类模型tok/s、RK3588 Gemma4 W8A8社区权重、4B剪枝→成功率先例、消费卡batched decode attention微基准——均标注"no reliable source found"，需自测或后续补充。

## 跨模块矛盾与风险检查清单
1. **AGPL数据 vs 权重发布**：Fable-5训练数据AGPL-3.0，若发布微调权重则违反许可——用组合包1规避。
2. **RKLLM单序列 vs batch>1主线**：RKLLM v1.2.3端侧单序列，与项目"并发batch>1一等公民"矛盾——端侧并发靠上层多实例/排队模拟，真并发放llama.cpp/租卡。
3. **DSpark NVFP4限Blackwell vs 全非Hopper租卡**：项目租卡为4090/A100/L20(全非Hopper也非Blackwell)——NVFP4路径不可用，只能跑BF16路径且无实测，风险高。
4. **RK3588 4B ~5.7 tok/s vs 4B端侧tier目标**：单序列体验勉强——降级到1.7B-2B为主力。
5. **Qwen3.5+不宜QLoRA vs 4060 8GB显存**：Qwen3.5+ QLoRA量化差异大官方不推荐，但bf16 LoRA 4B需10GB>8GB——4060上只能用Qwen3(非3.5)的QLoRA或更小模型。
6. **llama.cpp MTP build regression vs 用最新版**：Gemma4 MTP在b9702+ broken——须锁b9553，与"用最新版"惯例矛盾。
7. **ncu需root vs 租vGPU**：租vGPU的ncu常被禁——深度profiling必须放本地4060(有root)。
8. **CUDA 13.2 vs Qwen3.6**：CUDA 13.2致Qwen3.6乱码——环境须<13.2或13.3。
9. **Gemma SWA prompt cache vs 系统稳定**：#24265硬挂系统——基准测试须--cache-ram 0 --ctx-checkpoints 0。
10. **子代理并发数据零公共覆盖 vs 项目一等场景**：所有公共trace无并发子代理记录——必须自采。
11. **DeepSeek-R1-Distill garbage vs 端侧推理选型**：RKLLM输出garbage(#424)——端侧避用R1-Distill，选Qwen3系。
