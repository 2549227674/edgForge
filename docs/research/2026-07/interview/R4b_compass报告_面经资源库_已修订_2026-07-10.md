## MODULE 1 — 部署与推理服务（支柱一，P0 最核心）

### 1.1 Prefill vs Decode 瓶颈（P0）
- **(a) 权威讲解**：一手——HuggingFace 官方博客《Continuous batching from first principles》（huggingface.co/blog/continuous_batching）从算术强度角度拆解；中文——知乎《把 GPU 的账算清楚——LLM 训练与推理资源评估的完整公式体系》。补充实测论文《Memory-Bound but Not Bandwidth-Limited: The Physical AI Inference Gap in Batch-1 LLM Decode》（arXiv 2605.30571）给出 Qwen-2.5-7B 单 decode step 的 HBM 字节流量图。
- **(b) 白板要点**：
  - Prefill 一次性处理整个 prompt，做的是 [seqlen×d]×[d×d] 的大 GEMM，算术强度高 → **compute-bound**，决定 TTFT。
  - Decode 每步只生成一个 token（batch=1 时），要把全部权重从 HBM 搬到 SM 只做一次 [1×d]×[d×d] 的 GEMV，算术强度≈1 → **memory-bound**，决定 TPOT。
  - 会推导：decode 步时间下限 ≈ 模型权重字节数 / HBM 带宽（如 70B BF16=140GB，H100 3TB/s → ~47ms/step 下限）。
- **(c) 追问链与陷阱**：为什么增大 batch 能提升 decode 的 MFU？（把 GEMV 变 GEMM，算术强度上升，直到重新 compute-bound）→ 那 prefill 增大 batch 收益为何小？→ chunked prefill 如何让二者混合到同一 batch 提高利用率。
- **(d) 手撕参考**：无需手撕，但需能口算 roofline。

### 1.2 PagedAttention / Continuous Batching / Chunked Prefill（P0）
- **(a) 权威讲解**：vLLM 官方《Optimization and Tuning》(docs.vllm.ai/en/stable/configuration/optimization/)；PagedAttention 原论文（Kwon et al., arXiv 2309.06180, SOSP'23）；中文——Medium《Understanding vLLM Scheduling》。
- **(b) 白板要点**：
  - PagedAttention：KV cache 分固定大小 block + block table 逻辑→物理映射（类比 OS 分页）。原论文：传统系统碎片+预留浪费 60-80% 显存，vLLM 浪费 <4%，吞吐 2-4×。
  - Continuous batching：迭代级调度，完成即移出、等待即补入。
  - Chunked prefill：长 prompt 切 chunk 跨 step 处理，与 decode 混批。**vLLM V1 默认开启**；**默认 `max_num_batched_tokens` = 8192（在线 serving）/ 16384（离线）**〔修正：旧版/V0 为 512，勿再引用 512〕。
- **(c) 追问链与陷阱**：**"能否把 B 的 decode 插入 A 的 prefill chunk 之间？"**——能。V1 一个 scheduler step 可同时含 prefill chunk 与 decode，且**默认优先调度 decode**、再用剩余 token budget 填 prefill chunk（改善 ITL）。值调小→ITL 更好；调大→TTFT 更好；设成 ≈max_model_len 近似 V0（但 V1 仍优先 decode）。chunked prefill 不改变最终 KV cache 内容。
- **(d) 手撕参考**：无需手撕。

### 1.3 PD 分离（Prefill-Decode Disaggregation）（P0）
- **(a) 权威讲解**：Mooncake 论文（Qin et al., arXiv 2407.00079，Moonshot，FAST'25 Best Paper）；LMSYS《Deploying DeepSeek with PD Disaggregation...》(2025-05)；**AFD 一手：MegaScale-Infer（字节，arXiv 2504.02263）、Adrenaline（arXiv 2503.20552）、Step-3（StepFun）**。
- **(b) 白板要点**：
  - Prefill 集群（compute-bound）与 Decode 集群（memory-bound）物理分离，各自独立 batching/并行/资源配比。
  - Mooncake 核心 = KVCache-centric 全局调度 Conductor + 利用集群闲置 CPU/DRAM/SSD/RDMA 组分离式 KVCache + prediction-based early rejection。论文：长上下文吞吐较基线最高 +525%，Kimi 在 A800/H800 上较原 vLLM 方案分别多处理 115%/107% 请求。
  - 两队列调度：优先 decode（保 TBT SLO）不饿死 prefill（保 TTFT SLO）。
- **(c) 追问链与陷阱**：
  - **"AF 分离"= Attention-FFN Disaggregation (AFD)**〔修正：原标"待确认"，现坐实〕。把 **attention（memory-bound、依赖 KV）与 FFN/MoE（compute-bound、可批）放到不同 GPU 池**，各用适配并行/异构硬件；MegaScale-Infer 用 disaggregated expert parallelism + ping-pong 流水，~1.9× 吞吐/成本。
  - **PD 分离 vs AFD 的区别（加分点）**：PD 按"阶段"(prefill/decode)切；AFD 按"模块"(attention/FFN)切，可叠加。
  - 陷阱：PD 分离非总更优——短请求或 KV 传输开销大时收益反转（DistServe/HexGen-2）。
- **(d) 手撕参考**：无需手撕。

### 1.4 Prefix Cache 深挖（P0）
- **(a) 权威讲解**：一手——vLLM 官方《Automatic Prefix Caching》设计文档（docs.vllm.ai/en/stable/design/prefix_caching/）+ RFC #2614；SGLang RadixAttention 见论文《SGLang: Efficient Execution of Structured Language Model Programs》（Lianmin Zheng 等，arXiv 2312.07104，LMSYS/Stanford/UC Berkeley，NeurIPS 2024）与 LMSYS 博客(2024-01-17)。
- **(b) 白板要点**：
  - **vLLM APC（hash 方案）**：每个 KV block 由 `hash(tuple[parent_hash, block_tokens, extra_hashes])` 唯一标识。parent_hash 把前缀链入；block_tokens 减少碰撞；extra_hashes 含 LoRA ID / 多模态输入 hash / cache salt（多租户隔离）。只缓存满 block，维护全局 hash 表，像 OS 页一样管理，无需树。v0.11+ 默认 sha256。官方原话：*"We observe that every block in the KV cache can be uniquely identified by hash(prefix tokens, tokens in this block)."*
  - **SGLang RadixAttention（树方案）**：prompt 与生成结果的 KV 都保留在 **radix tree**（边可标注变长 token 序列），支持最长前缀匹配、插入、驱逐；**LRU 驱逐 + cache-aware 调度**提升命中率。树结构存 CPU，开销小。多模态用图像 hash 作 key。头条结果：吞吐较 SOTA 提升 5×–6.4×。
  - 共同点：**匹配都在 CPU 侧**做。
- **(c) 追问链与陷阱**：**"动态稀疏注意力下 prefix cache 还有效吗、如何适配？"**——需说明：稀疏/DSA 场景下每个 token 实际 attend 的 KV 集合依赖 top-k 选择，前缀完全相同的部分其 KV 本身仍可复用，但一旦下游 token 改变 query，top-k 选择集会变，故通常只能复用"密集前缀 KV"本身而选择逻辑需重算；这是开放工程点，面试宜讲清 trade-off。
- **(d) 手撕参考**：可手写一个基于 dict 的 block-hash 前缀匹配 demo（parent_hash 链式）。

### 1.5 投机解码家族（P0）
- **(a) 权威讲解**：一手——EAGLE 系列论文（EAGLE arXiv 2401.15077 / EAGLE-2 arXiv 2406.16858 / EAGLE-3 arXiv 2503.01840，Yuhui Li 等，SafeAILab/EAGLE GitHub）、Medusa、Lookahead Decoding（arXiv 2402.02057）、综述《Unlocking Efficiency ... Speculative Decoding》(arXiv 2401.07851)；实操——TensorRT-LLM《Speculative Sampling》文档。中文可配掘金/知乎投机解码综述。
- **(b) 白板要点/家系**：
  - **标准投机采样**：小 draft 模型自回归猜 k 个 token，大 target 模型一次并行验证，保持输出分布不变（lossless）。
  - **Medusa**：在 target 顶部训练 K 个并行 head，无需独立 draft，一次预测多 token。
  - **EAGLE(1/2/3)**：在 feature 层做自回归 draft。据 EAGLE 官方（13B）实测：*"3x faster than vanilla decoding, 2x faster than Lookahead, and 1.6x faster than Medusa"*（即约 **1.6× 快于 Medusa**，而非 2×）。EAGLE-2 引入 dynamic draft tree（依 draft 置信度调树结构，无需额外训练）；EAGLE-3 直接预测 token + 多层特征融合，据其论文相对 vanilla 达 3.0×–6.5×、较 EAGLE-2 再提升 20%–40%。
  - **Lookahead**：无 draft 模型，用 Jacobi 迭代 + n-gram trie 检索并行验证。
  - **n-gram / prompt-lookup**：用 prompt 自身作 draft 来源，代码/摘要类模板重复场景收益大。
  - **MTP**：训练时预测多个未来 token，推理时可复用于投机解码。据 DeepSeek-V3 技术报告 §5.4.3：*"the acceptance rate of the second token prediction ranges between 85% and 90% across various generation topics… delivering 1.8 times TPS (Tokens Per Second)"*。
- **(c) 追问链与陷阱**：draft-target 交互——接受率 α 与加速比关系；**负收益边界**：大 batch 服务场景下 GPU 已 compute-bound，投机解码增加的验证 FLOPs 反而拖慢（陷阱：投机解码在低并发/latency-sensitive 场景收益最大，高吞吐批量场景可能负收益）；7B 给 13B 当 draft 因开销过大反而慢于 vanilla。vLLM vs SGLang 实现差异需了解。
- **(d) 手撕参考**：可手写标准投机采样的 accept/reject 逻辑（含 residual 分布修正）。

### 1.6 MoE 推理（P0）
- **(a) 权威讲解**：DeepEP/EPLB GitHub（github.com/deepseek-ai/eplb）；综述《Taming the Titans: A Survey of Efficient LLM Inference Serving》(arXiv 2504.19720)；LMSYS large-scale EP 博客。
- **(b) 白板要点**：
  - **"3B Dense vs 32B-A3B（激活 3B）谁延迟低/更快？" 正确分析框架**〔修正框架〕：decode 是 memory-bound，瓶颈=从 HBM 搬多少权重。
    - **batch=1 单请求 decode**：A3B 每 token 也只激活 ~3B 专家参数，**激活量与 3B Dense 同量级、延迟≈可比**（A3B 略高，因 32B 模型层更多、有 router 路由开销、attention 更大）。**不要说"通常明显更高"**。
    - **batch>1**：不同 token 路由到不同专家，聚合起来实际搬运的专家权重远超 3B、逼近载入大部分/全部专家 → 此时 A3B 延迟才显著上升；但换来更强能力与更高吞吐上限。
    - **务必分清**：单请求延迟（batch=1 可比）vs 批量吞吐（A3B 更优）是两个问题。
  - 专家切换成本：token 路由的 all-to-all 通信 + 专家权重 gather。
  - **DeepEP**：MoE 的 EP 通信库，normal dispatch（prefill 高吞吐）/ low-latency dispatch（decode）。**EPLB**：冗余专家复制+放置解决热专家 straggler，分 hierarchical / global。
- **(c) 追问链与陷阱**：为什么 MoE decode 更依赖 CUDA Graph（DeepEP normal dispatch 的 symbolic shape 不兼容）；负载不均如何度量（mean/max 计算时间比）。
- **(d) 手撕参考**：无需手撕，理解 top-k gating + all-to-all 伪代码即可。

### 1.7 MLA 深挖（P0）
- **(a) 权威讲解**：DeepSeek-V2 论文 + DeepSeek-V3 repo MLA 实现（naive/absorb 两版）；解析《Understanding DeepSeek's MLA》(shashankshekhar.com)、TyphoonMLA(arXiv 2509.21081) naive/absorb 对比；中文——Oilbeater《DeepSeek MLA》。
- **(b) 白板要点**：
  - 低秩 KV 联合压缩：token 压到 512 维 latent，KV cache 只存 latent，大降带宽。
  - **矩阵吸收（matrix absorption）**：靠结合律 A@(B@C)，把上投影 W_UK/W_UV 吸收进 Q 和 O 投影，decode 时注意力**完全在 latent 空间算**、无需 materialize 完整 K/V。
  - **prefill 用 naive、decode 用 absorb**：absorb 减小 KV 载入（利于 memory-bound decode）但增大 attention FLOPs（不利 compute-bound prefill）。
  - **"3.4×"的正确出处与说法**〔修正措辞〕：据 **TyphoonMLA roofline**，**大 batch(>64) 下 naive 比 absorb 吞吐最高约 3.4×**（absorb 在 compute-bound 区 FLOPs 更多而饱和）。**不是"absorb 固定多 3.4× FLOPs"**。
- **(c) 追问链与陷阱**：decode 的 compute/memory 比随 seqlen/batch 如何变；scaling factor 仍是 1/√d_h（吸收只改乘序不改点积值）；MLA 双路径——prefill MHA-mode、decode MQA-mode。
- **(d) 手撕参考**：DeepSeek-V3 repo 官方 MLA 代码（naive+absorb 两版对照）。

## MODULE 2 — 算子 Kernel / GPU 架构（支柱二，P0）

### 2.1 CUDA Graph（P0）
- **(a) 权威讲解**：一手——vLLM《CUDA Graphs》设计文档(docs.vllm.ai/en/stable/design/cuda_graphs/)、SGLang CUDA Graph 文档、NVIDIA《CUDA Graph Best Practice》；深度——DEV《CUDA Graphs in LLM Inference: Deep Dive》、Spheron《torch.compile and CUDA Graphs》。
- **(b) 白板要点**：capture（dummy forward 录制 kernel 序列 + 内存地址）→ replay（一次 cudaGraphLaunch 替代上千次 kernel 提交）→ fallback（不支持时降级 eager）。捕获的是 tensor 地址与 shape。
- **(c) 追问链与陷阱**：
  - **"为什么更费显存？"** PyTorch 默认为每个 graph 分配独立私有内存池以保证 replay 时地址不变，多个 graph 间内存无法复用/合并；且需为多个 batch size 各捕获一份（每份 ~50-200MB）。
  - **"哪些动态情况不能复用？"** grid/launch config 随 max_ctx_seq_len、num_context_requests 变化的 prefill/mixed batch；地址失效（tensor 被 GC、重新赋值而非 in-place）会 illegal memory access。
  - **"适合哪个推理阶段？"** **Decode**——batch size 稳定、每序列恰好 1 query token，grid=(batch, heads) 固定；SGLang/vLLM 默认对 decode 开启，prefill 变长不用。
- **(d) 手撕参考**：无需手撕，能写 capture/replay 三段式伪代码即可。

### 2.2 CUDA 编译链（P0/P1）
- **(a) 权威讲解**：NVIDIA CUDA Compiler Driver NVCC 官方文档（nvcc flow）；MLIR 设计动机见 MLIR 官方 rationale。
- **(b) 白板要点**：nvcc 分离 host（交给 gcc/msvc）与 device 代码；device 编译 .cu → PTX（虚拟 ISA，机器无关）→ cubin（特定 SM 架构机器码）→ 打包成 fatbin（多架构）嵌入可执行文件。运行时 JIT 可从 PTX 编译。**.cpp 与 .cu 分别编译**再链接。PTX 是虚拟机器模型（无限寄存器等），保证前向兼容。
- **(c) 追问链与陷阱**：为什么设计 MLIR——多层 IR 便于领域方言与渐进 lowering，解决"编译器竖井"重复造轮子；PTX vs SASS 区别；undefined symbol 常因 host/device 分离编译或 extern C 名字修饰。
- **(d) 手撕参考**：无需手撕，能画编译流程图。

### 2.3 Tensor Core vs CUDA Core（P0）
- **(a) 权威讲解**：一手——NVIDIA WMMA/MMA 编程指南、NVFP4 技术博客(developer.nvidia.com/blog/introducing-nvfp4...)、《Pushing Intelligence to 4-bit》(NVIDIA Research)；已拥有的 siboehm SGEMM 与 GPU MODE 讲座补充。
- **(b) 白板要点**：矩阵乘用 **Tensor Core** 远快于 CUDA Core（数量级差异）；Tensor Core 做 D=A×B+C 的 16×16 分块 MMA。FP8（E4M3/E5M2）/FP4（E2M1）量化需硬件 Tensor Core 原生支持（Hopper FP8、Blackwell FP4）。
- **(c) 追问链与陷阱**：WMMA API 的 fragment/load/store/mma_sync；为什么 FP8 累加需提升到 CUDA Core 高精度（H800 Tensor Core FP8 累加仅 ~14bit）；哪些硬件支持（Hopper/Blackwell）。
- **(d) 手撕参考**：可手写 WMMA 版 16×16×16 tile matmul（GPU MODE 有例）。

### 2.4 Warp 原语（P0）
- **(a) 权威讲解**：NVIDIA《Using CUDA Warp-Level Primitives》博客与 Programming Guide。
- **(b) 白板要点**：`__shfl_sync`/`__shfl_down_sync`（寄存器级 warp 内数据交换，无需 shared mem）、`__ballot_sync`（每 lane 一 bit 投票汇成 mask）、`__any_sync`/`__all_sync`。用于 warp 内规约。
- **(c) 追问链与陷阱**：**"为什么跨 block 通信难？"**——block 间无硬件同步原语（除 cooperative groups grid sync）、调度顺序不确定、无共享 shared mem，只能靠 global mem + atomics 或多 kernel。shuffle 只在同 warp 32 lane 内有效。
- **(d) 手撕参考**：warp shuffle 版 block reduce（见 2.9 手撕库）。

### 2.5 Bank Conflict（P0）
- **(a) 权威讲解**：NVIDIA Programming Guide shared memory 章节；已拥有——siboehm SGEMM 长文（含 bank conflict 处理）、GPU MODE 讲座系列。
- **(b) 白板要点**：shared mem 分 32 banks，同一 warp 内多线程访问**同一 bank 的不同地址**会串行化（n-way conflict）；同地址广播不冲突。
- **(c) 追问链与陷阱**：避免手段——**padding**（如 [32][33] 加一列错开）、**swizzle**（地址异或重排）；转置 kernel 是经典冲突场景。
- **(d) 手撕参考**：手写带 padding 的 shared-mem 转置 kernel。

### 2.6 算子调优方法论（P0）

### 2.8 端侧算子排布（P0，直击项目）
- **(a) 权威讲解**：一手——MNN GitHub + 《【端智能】MNN CPU性能优化年度小结》(CSDN Taobaojishu)；中文——《nc4hw4排布配合neon加速im2col+gemm的卷积推理》(CSDN hsqyc)、《AI算法基础[2]：NC4HW4数据排布》(no5-aaron-wu.github.io)。
- **(b) 白板要点**：
  - **NCHW / NHWC / NC4HW4**：NC4HW4 = N(C/4)HW4，沿 C 方向取 4 个数按 W 排列，C 非 4 倍数补 0。为配合 SIMD（ARM NEON 单指令处理 4 个数）而生：卷积时不同 C 通道互不影响，正好作矢量不同元素，避免 NCHW 跳通道取数的 cache miss。
  - **"3 通道能用 NC4HW4 吗、为什么？"**——能，但需补 0 到 4 通道（第 4 通道填 0），首层 3 通道输入用 NC4HW4 有浪费，故很多引擎首层特殊处理；只有整网所有 Op 都用 NC4HW4 才免去布局转换开销（MNN 做法），中间遇不支持的 Op 前后插转换。
  - 分组卷积、NEON matmul（im2col+GEMM）+ 内存对齐、bicubic 插值 16 点权重。
- **(c) 追问链与陷阱**：NC4HW4 收益（树莓派实测 GEMM 提速数倍）vs 布局转换代价；ncnn/MNN/TNN 的排布与 NEON 优化差异。

### 6.3 量化理论速查（P1）
- **(a) 权威讲解**：中文——知乎《大模型量化技术原理：总结》《大模型量化领域梳理（二）：SmoothQuant、GPTQ和AWQ》；NVFP4 见 NVIDIA 博客 + 《Pushing Intelligence to 4-bit》+ zeroentropy NVFP4 页。
- **(b) 白板速查表**：
  - INT8/INT4（定点）；FP16（1-5-10）；**BF16（1-8-7，训练用因动态范围大=FP32 指数位，防溢出）**；FP8 两格式：**E4M3**（范围 ±448，精度高，前向/权重）与 **E5M2**（范围大，梯度）；**NVFP4**（E2M1 元素 + **两级 scale**：per-16-block 的 FP8 E4M3 scale + per-tensor FP32 scale；vs MXFP4 的 32-block+E8M0 power-of-2 单级 scale，NVFP4 块更小、scale 更细，Blackwell 原生支持）。

### 6.4 C++ 深八股（P1 Gap，速查级，候选人有嵌入式背景）
- **(a) 权威讲解**：中文——《C++ 八股整理》(知乎)、编程指北 csguide.cn《C++ 虚函数表》、《史上最全C/C++面经八股文》(CSDN)。
- **(b) 速查清单（须给正确答案）**：
  - **虚函数/vtable**：含虚函数的类编译期生成唯一 vtable（存 .rodata），对象头部有 vptr；vtable 按声明顺序存函数指针；派生类覆盖则替换对应槽位；调用多一次解引用+跳转。
  - **纯虚/抽象类**：`virtual void f()=0`，含纯虚函数的类不可实例化，作接口。
  - **析构函数抛异常**：可能致程序 terminate（尤其栈展开中二次异常）；析构不应抛。**基类析构须为 virtual**否则 delete 基类指针泄漏派生类资源。
  - **智能指针三种**：unique_ptr（独占，只移动不拷贝）、shared_ptr（引用计数，atomic 线程安全的计数但对象访问不安全）、weak_ptr（解 shared_ptr **循环引用**）。
  - **移动语义/右值/std::move**：右值引用绑定临时对象；std::move 是强制转右值引用（不真移动）；move 构造转移资源避免深拷贝。
  - **sizeof 内存对齐**：按最大成员对齐，手算 struct（如 char+int+char = 12 而非 6）。
  - **resize vs reserve**（前者改 size 构造元素、后者只改 capacity）；**emplace_back vs push_back**（前者原地构造省一次拷贝/移动）。
  - **MESI/false sharing/alignas**：伪共享——不同线程改同一 cache line 不同变量致失效抖动，用 alignas(64) 填充避免。
  - **协程**：有栈 vs 无栈，**C++20 是无栈协程**。
  - **四个编译阶段**：预处理→编译→汇编→链接。**undefined symbol** 常因未链接实现/名字修饰不符。
  - **new/delete vs malloc/free**（前者调用构造/析构且是运算符）；深/浅拷贝；栈/堆/静态区；GDB 常用（break/next/step/print/bt/watch）。
- **(c)(d)**：速查表即可，会手算 struct 对齐 + 手写 shared_ptr 计数骨架。
