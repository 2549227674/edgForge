## 逐项详解

### ✅ 1. Megatron 每层 4 次 all-reduce — 钉死
NVIDIA ADLR、HuggingFace Accelerate、Berkeley SC'21 论文三方一致：**每 transformer 层前向 2 次（attention 后 1、MLP 后 1）+ 反向 2 次 = 4 次**。机制是 f/g 一对共轭算子——g 在前向 all-reduce、前向对 f 是恒等；f 在反向 all-reduce、反向对 g 是恒等。**追问答法**：MLP 第一矩阵列切、第二矩阵行切（因 GeLU 非线性不能交换乘序），行切后各 GPU 持部分输出行 → g 做一次 all-reduce 合出完整输出。别只报"4"，要带 f/g 和列-行切的"为什么"。

### ✅ 2. NVFP4 / MXFP4 — 钉死
NVIDIA 官博 + zeroentropy + Modal + 多篇 arXiv 一致：
- **NVFP4**：元素 E2M1，**16 元素/块**，块级 scale 用 **FP8 E4M3**，外加 **per-tensor FP32** 第二级（两级微缩放），Blackwell 原生。
- **MXFP4**：元素 E2M1，**32 元素/块**，块级 scale 用 **E8M0（8bit 全指数，2 的幂）**，单级，OCP 多厂商标准。
- 记忆锚：NVFP4 "块更小(16)、scale 更精(E4M3 有尾数)、多一层 FP32"，故同模型下 ppl 更低但 overhead 略高。

### ✅ 3–7 其余钉死项
EAGLE 1.6×（EAGLE 论文自述，面试要说"据 EAGLE 官方"）；Medusa 60-80%/EAGLE 85-95% 接受率；PagedAttention 传统 60-80% 浪费、vLLM <4%（SOSP'23 原文）；chunked prefill V1 默认开+优先 decode（vLLM stable 文档）；MLA 吸收定性（absorb→decode、naive→prefill，靠 A@(B@C) 结合律）——**均可直接背**。

### ⚠️ 8. MLA "3.4×" — 调措辞
出处是 **TyphoonMLA(arXiv 2509.21081) 的 roofline**：batch>64 时 naive 比 absorb 吞吐**最高高 3.4×**（因 absorb 在 compute-bound 区 FLOPs 更多而饱和）。tensoreconomics 博客把它转述为"absorption 的 3.4× FLOP 惩罚"。
- **正确说法**："据 TyphoonMLA，大 batch 下 naive 比 absorb 吞吐最高约 3.4×，所以 prefill(compute-bound) 用 naive、decode(memory-bound) 用 absorb。"
- **别说**："absorb 固定多 3.4× FLOPs"（不是固定常数）。

### ⚠️ 9. vLLM max_num_batched_tokens 默认值 — 改数字
- 报告写的 **512 是 V0 chunked prefill 默认**；某些版本是 2048。
- **V1 现默认 8192（在线 serving）/ 16384（离线）**（vLLM/ROCm 官方文档）。
- 追问点不变：值调小→ITL 更好(prefill 少打断 decode)；调大→TTFT 更好；设成 ≈max_model_len 近似 V0 行为（但 V1 仍优先 decode）。

### ⚠️ 10. MoE 3B-Dense vs 32B-A3B — 调框架
更精确的分析：
- **batch=1 decode**：A3B 每 token 也只激活 ~3B 专家参数，**激活量与 3B Dense 同量级**，延迟≈可比（A3B 略高，因 32B 模型层更多、有 router/路由开销、attention 更大）。不宜说"通常明显更高"。
- **真正拉开在 batch>1**：不同 token 路由到不同专家，聚合起来实际要搬运的专家权重远超 3B、逼近载入大部分/全部专家 → 此时 A3B 的权重搬运和延迟才显著上升；但换来更强能力与更高吞吐上限。
- **面试要分清**：单请求延迟（batch=1 可比）vs 批量吞吐（A3B 更优）是两个问题；决定因素是 decode memory-bound 下"实际需搬运多少专家权重"。

### ⤴️ 11. AF 分离 → 坐实为 AFD
不再是"待确认"。**Attention-FFN Disaggregation (AFD)**，把 attention（memory-bound、依赖 KV cache）与 FFN/MoE（compute-bound、可批）放到**不同 GPU 池**，各用适配并行/异构硬件：
- **MegaScale-Infer（字节跳动，arXiv 2504.02263）**：disaggregated expert parallelism + ping-pong 流水，~1.9× 吞吐/成本。**是字节的论文，你的目标公司，值得重点讲。**
- **Adrenaline（arXiv 2503.20552）**：把 decode 阶段部分 attention 卸载到 prefill 实例提利用率。
- **Step-3（StepFun）**：AFD 系统级 co-design。
- **与 PD 分离的区别**：PD 按"阶段"(prefill/decode)切；AFD 按"模块"(attention/FFN)切。可作为 PD 分离的进阶对照，答出这层区分是加分。

### ⛔ 12. Claude Code 压缩阈值 — 只讲机制，别报具体数
各源严重不一致：GitHub issue 说硬编码 **95%**、claudefa.st 说 **~83.5%(此前~77-78%)**、另有 issue 报 **~76%**、hyperdev 猜 **64-75%**。**随版本频繁变、且可用 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 配置**。
- **面试安全说法**："触发是上下文使用率达某百分比阈值（社区观察在 ~75-90%、随版本变），会预留一段 buffer(~33-45k token) 给压缩调用本身，阈值可配置。"——**讲机制、给区间、点明可配置，不钉死单一数字**。
- **补充纠偏**：要区分两个东西——① Claude Code **CLI** 的内部 auto-compact 启发式（上面这个百分比，非官方公布）；② Anthropic **API** 官方的 `compaction_control`（cookbook），默认 `context_token_threshold=100,000` tokens，这是官方明确值、可放心引用。报告里把二者混在了 3.1 节，应分开。

## 给你的两条结论

1. **可直接背的高置信区**（第 1-7 项）覆盖了你支柱一/二最核心的追问，占面试命中的大头——这些放心钉进自测表。
2. **需谨慎的四项**（8/9/10/12）都不是"错"，而是"语境/版本/精确度"问题：MLA 3.4× 说清出处、vLLM 默认值改 8192、MoE 分清 batch=1 与大 batch、Claude Code 只讲机制。另有一项（11 AF 分离）是**意外收获**——从"待确认"变成一个能讲字节论文的加分点。
