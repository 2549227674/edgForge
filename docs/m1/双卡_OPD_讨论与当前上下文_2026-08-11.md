# M1 双卡 OPD 讨论与当前上下文

> 日期：2026-08-11
>
> 状态：**讨论稿，待独立技术复核；不是 owner 决策，不修改蓝图或 M1 执行卡的冻结口径。**
>
> 用途：记录截至暂停点的实测事实、原文约束，以及双卡 SFT/OPD 的候选技术方案，供从仓库重新建立上下文的评审者（包括网页版 Claude）提出方案。

## 1. 结论摘要

双卡对 OPD 最直接、最稳妥的收益，是将 teacher 与 student 分别固定在一张 GPU 上，解除原单卡方案中的显存共驻留冲突，并增加 teacher KV cache、生成 batch 和 student 训练的独立空间。

但“一卡 teacher、一卡 student”只解决共驻留问题，**不会自动提高 student 的单序列显存上限**。当前 E4B QLoRA 在单张 96GB 上已经于约 8K 序列 OOM；因此该双卡形态不能直接保证 16K OPD。若要求 student 的 OPD 也覆盖 16K，通常需要两张卡都用于 student 的序列/上下文并行，再把 teacher 放到第三张卡或外部服务；或者实现两卡共享、teacher sleep/wake 的高复杂度调度。

目前没有批准任何双卡方案。正式变更前，需要在新实例上分别重做 SFT 的 8K/16K 阶梯与 OPD 的 4K/8K/目标总长度阶梯，并回写 M1 执行卡的 owner 决策。

### 1.1 本文长度口径

- **SFT 4K/8K/16K**：渲染后的 `input_ids` 总长度，即 `max_seq_length`。
- **OPD prompt length**：送入 student 生成前的上下文长度。
- **OPD completion length**：student on-policy 生成的最大新 token 数。
- **OPD total length**：prompt + completion，训练 KL/loss 时 student 实际承载的序列长度。
- 本文“要求 OPD 覆盖 16K”统一指 **OPD total length ≤16,384**，不是 16K prompt 再加 completion。

当前已证事实只有：SFT total length 4,096 通过、8,153 OOM。OPD 的 4K/8K/10,240 均尚未进行专用 smoke，不能从 SFT 峰值直接判定。

### 2.3 4096 全量渲染暴露的数据问题

- 151,121 条可训练记录；
- 2,976 条因裁剪后没有监督 token 而显式丢弃；
- 0 条渲染失败；
- 保留 198,904,115 input token、163,325,436 supervised token；
- 排除可用 holdout 后，训练池为 149,696 条、197,029,223 token。

冻结 holdout manifest 是 1,500 条，其中 75 条在 4096 裁剪后没有监督 token，故可用于验证 loss 的实际 holdout 为 1,425 条；这解释了 151,121 − 149,696 = 1,425。

## 3. 原蓝图与 M1 执行卡的真实规定

### 3.1 文档层级

蓝图是稳定层，执行卡是滚动层；执行卡明确声明真实机器判断优先，建议项可以偏离，但事实/雷区的偏离必须留理由。参见 [`EdgeForge_蓝图终稿_v4-R2_2026-07-19.md`](../EdgeForge_蓝图终稿_v4-R2_2026-07-19.md)。

### 3.2 已规定事项

- E4B 是完整循环的贯穿轴，SFT 路线为 QLoRA→merge。
- 蓝图旧 M1 行中的 vGPU-32 已被 M1 卡 D-3 明确宣布过时；M1 改用 RTX PRO 6000 96GB。
- 蓝图决策 16 原设 OPD 为单张 Pro 6000 上 teacher FP8 与 student QLoRA 共存。
- M1 卡规定 16,384 只是候选长度，尚未获得显存许可；最终长度必须由 4K/8K/候选长度的显存阶梯 smoke 决定。
- T2 建议保持 NF4 QLoRA + bf16 LoRA，将 96GB 余量优先用于 batch、梯度累积和 `max_seq_length`，不静默切换全参或 bf16-LoRA。
- Gemma4 E4B 的跨层 KV 共享、bf16 mask 和冻结 chat/thinking 模板属于强制 smoke 项。

### 3.3 未规定事项

蓝图和 M1 卡都没有规定 DDP、FSDP、ZeRO、tensor parallel、sequence/context parallel 或 `device_map="auto"`。这些均是因单卡实测不足而提出的候选工程方案，不是既有决策。

M1 卡 fallback-B 的“双实例”是 OPD teacher server 与 student 分离的预案，不是双卡 SFT 分片方案。

## 4. 多卡术语与适用边界

- **DDP**：每张卡复制完整模型、处理不同样本。它增加吞吐，但单条 16K 样本仍必须在一张卡中完整放下，不能解决本次 OOM。
- **FSDP/ZeRO-3**：分片模型参数、梯度和优化器状态。它能释放模型状态显存，但长序列主要增长的是激活与 attention 中间量；QLoRA 底座已经是 4-bit，因此收益不等于把可训练长度直接翻倍。
- **层级 model parallel / `device_map`**：不同层放到不同 GPU，但各层仍处理完整序列；简单的自动设备映射不等于经过验证的多卡训练实现。
- **activation checkpointing**：以重算换取激活显存。但普通实现常关闭 `use_cache`，而 Gemma4 E4B 的 KV 共享路径已有 `use_cache=False` 导致 logits/loss 异常的先例，不能未经 loss smoke 直接启用。
- **sequence/context parallel**：沿 token/attention 维度切分同一长序列，最直接针对 16K 激活显存，但对 Gemma4、QLoRA、TRL 和当前 attention 后端的组合兼容性需要单独验证。

## 5. 双卡 OPD 候选方案

### 5.1 方案 A：teacher/student 专卡隔离

这是双卡 OPD 的最低风险方案。

| GPU | 角色 | 建议起点 |
|---|---|---|
| GPU0 | `gemma-4-31b-it` teacher vLLM server | FP8，TP=1，独占 GPU |
| GPU1 | C01-S student | NF4 QLoRA、bf16、SDPA、`use_cache=true` |

主要好处：

1. 消除 teacher 权重/KV 与 student 激活/优化器之间的显存抢占。
2. teacher 可提高 `gpu_memory_utilization`、KV cache 与生成并发。
3. 相比蓝图原设的“单卡 teacher+student 共驻留”，student 不再需要给 teacher 预留约 31GB；但当前 8K OOM 本身已经是在 student 独占单卡的 SFT smoke 中发生，因此方案 A 不会改善该 OOM 基线。
4. teacher server 走 localhost，避免执行卡跨实例 fallback 的网络不确定性。
5. 可使用 generation buffer，使生成 batch 与训练 microbatch 解耦。

局限：student 仍只有一张 96GB；当前单卡 8K 已 OOM，所以不能据此宣称 16K OPD 可行。

teacher server 可按 10,240 capacity 上限候选配置，但这只是为原卡目标预留服务容量，不代表 10,240 OPD 已通过；首次端到端 smoke 仍使用不超过 4,096 的 prompt+completion：

```text
CUDA_VISIBLE_DEVICES=0
quantization=fp8
tensor_parallel_size=1
gpu_memory_utilization=0.80~0.88
max_model_len=10240      # server capacity 候选；首轮请求 total length <=4096
max_num_seqs=8        # 稳定后再试 16
enable_prefix_caching=true
```

`max_model_len=10240` 对应执行卡原建议的 8,192-token prompt + 2,048-token completion。teacher 独占 96GB 后没有必要默认 TP=2；TP=2 会侵占 student 卡并引入额外通信。

student 的**可执行 smoke 起点**应保持 4,096 total length；8K 与 10,240 只是后续阶梯目标，不能直接照抄为正式配置：

```text
student quantization=NF4 double quant
compute_dtype=bf16
LoRA r/alpha=8/16
target_modules=all-linear
attention=SDPA
use_cache=true
per_device_train_batch_size=1

use_teacher_server=true
teacher_model_server_url=http://127.0.0.1:8000
lmbda=1.0
beta=1.0
loss_top_k=1
num_generations=1
generation_batch_size=4  # 稳定后试 8

# 第一阶梯：先验证完整 OPD 回传
max_prompt_length<=3072
max_completion_length<=1024
max_length=4096

# 后续目标，只有前一阶梯通过才启用
target_2_total_length=8192
target_3_total_length=10240  # 原卡 8192 prompt + 2048 completion
```

外部 teacher server 且 `beta>0` 时，当前 TRL 文档要求 `loss_top_k=1`；不能因双卡而直接改为 top-32 或 full-vocabulary reverse KL。TRL DistillationTrainer 仍在 experimental namespace，实际字段必须按执行卡锁定版本重新 spike。

### 5.2 方案 B：两卡训练 student，teacher 外置

若目标是 16K SFT/OPD，技术上更干净的资源布局是：

- 本机 GPU0–1：student 的 FSDP + sequence/context parallel；
- 第三张 GPU 或外部实例：teacher vLLM server。

这会把两张本地卡都用于解决单序列激活显存，teacher 不参与本机显存竞争。代价是端到端实际至少需要 **2 张本地 student GPU + 1 份 teacher GPU 服务**，并需要验证跨机 teacher logprob 传输与吞吐。FSDP 主要减少模型状态，sequence/context parallel 才直接切分长序列激活；当前尚未选定能同时兼容 Gemma4 shared KV、QLoRA、TRL 1.9.2 和 SDPA 的具体实现。

### 5.3 方案 C：teacher 与 student 均跨两卡、分阶段 sleep/wake

候选流程：

1. teacher 用 TP=2 在两卡上评分；
2. 评分完成后让 vLLM teacher 进入 sleep mode，卸载权重并丢弃 KV；
3. student 跨两卡执行长上下文反向；
4. 下一批再唤醒 teacher。

该方案理论上能最大化两张卡的可用显存，但上述四步还不是完整生命周期：student rollout 在何处执行、teacher TP=2 常驻时 student 权重/optimizer 如何驻留、sleep 是否能跨进程释放到足以启动训练、每轮 wake/sleep 的代价，都尚未回答。它需要定制 OPD 调度，并承担频繁 sleep/wake、通信竞争和版本兼容风险；不是执行卡的现成配置，不应作为第一实现。

## 6. 相比原内容可调整与应保持的参数

### 6.1 可以调整

- GPU 角色固定与 `CUDA_VISIBLE_DEVICES`。
- teacher 的 `gpu_memory_utilization`、`max_model_len`、`max_num_seqs`、prefix caching。
- student on-policy generation 的 `generation_batch_size`。
- 梯度累积数，但两方案仍应按相同 optimizer-step/token 预算比较。
- 两卡都用于 student 时的 FSDP/sequence-context parallel 配置。
- OPD 预算可在最小 smoke 通过后由 10M 向原建议上限 30M token 扩大。

### 6.2 第一版不应调整

- `lmbda=1.0`、`beta=1.0`、`loss_top_k=1`。
- teacher 默认继续使用蓝图规定的 FP8；BF16 teacher 可以另立小型 A/B，但属于新旋钮。
- student 的 NF4 QLoRA、bf16、LoRA rank/alpha、冻结模板与 loss mask。
- holdout、early stopping 与评测合同。

## 7. 推荐的分阶段路线（尚未拍板）

1. **SFT 阶段**：两张 96GB 都用于 student，重新测试 8K/16K，目标优先冻结 16K。
2. **OPD 基线**：GPU0 teacher、GPU1 student，先完成最小 prompt 集的 rollout→teacher score→loss backward。
3. **OPD 长度阶梯**：分别测试 4K、8K、10,240 total length，不预设一定通过。
4. 如果接受“16K SFT + 较短 OPD polish”，可考虑方案 A；“短 OPD 不会损害已学长上下文”目前只是待评测假设，必须用长上下文留出集比较 SFT checkpoint 与 OPD checkpoint，不能当成既成事实。
5. 如果要求“OPD 也必须覆盖 16K”，优先增加第三张 teacher GPU/外部 teacher；只有资源受限时才研究方案 C。
6. 任一新长度通过后，重新全量渲染、检查各家族可训练保留率、重算 token 预算与配方计划；现有 4096 计划不复用。

## 8. 请求独立评审的问题

请评审者重点回答：

1. 在 Gemma4 E4B 必须保持正确 KV 共享语义的前提下，哪一种两卡训练实现最可能稳定支持 16K？
2. 能否在不触发 `use_cache=False` 错误路径的情况下使用 activation checkpointing？需要修改模型实现还是可通过现有框架配置解决？
3. FSDP+QLoRA 对 Gemma4 的 shared KV layers、bitsandbytes storage dtype、adapter checkpoint/merge 有哪些具体风险？
4. 双卡仅有 2×96GB 时，16K OPD 应选择 teacher/student 专卡、共享 sleep/wake，还是接受较短 OPD？
5. teacher FP8 与 BF16 在 top-1 reverse-KL teacher server 模式下，是否值得做质量 A/B？
6. 以当前 4K/8K 显存实测推断，16K 所需的最小并行技术组合是什么？
7. 应为长 trace 预注册什么数据保留门槛，例如按家族的“裁后仍有监督 token”比例，以避免再次出现程序合规但数据目标失效？
8. 16K smoke 的通过门槛应如何同时覆盖：不 OOM、loss 与短序列基线一致、shared-KV 语义正确、最低吞吐、checkpoint 可恢复、adapter 可合并和多 rank 数据预算一致？

下一版执行卡还应预注册按家族/task_type 的可训练记录保留率与监督 token 保留率下限；仅验证“程序无失败”不足以证明长 trace 数据目标成立。
